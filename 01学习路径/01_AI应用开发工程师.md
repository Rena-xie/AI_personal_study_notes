## 2 编程语言与软件工程基础设施

### 2.1 现代化 Python 工程化工具链

* **是什么**：由 uv、Ruff、pytest 构建的现代化 Python 项目管理与质量保障工具链。
* **为什么需要**：传统 pip + virtualenv 配置繁琐，Flake8 / Black / isort 组合工具链较慢，且缺乏严格的自动化测试保障，容易在生产环境导致依赖冲突或语法崩溃。
* **工具链工作机制与要求**：
  * **uv 包管理器**：基于 Rust 编写的极速 Python 包与环境管理工具。要求项目中使用 `uv` 进行环境隔离与依赖锁定，统一使用 `uv run <command>` 执行所有脚本与测试，禁止使用全局 python 或 pip。
  * **Ruff 静态检查器**：代替 Black、Flake8 和 isort 的高性能 Linter。硬性遵守静态检查与 Import 排序规则（如 I001 规则：严格区分 Python 标准库、第三方库、本地模块分组）。
  * **pytest 测试框架**：编写单元测试与集成测试，验证后端函数与 RAG 数据流的正确性，规避测试模块重名问题，确保高基名唯一性 Unique Basename。

### 2.2 异步高并发与速率控制

* **是什么**：基于 asyncio 事件循环 Event Loop 与 Semaphore 信号量的非阻塞异步编程范式，用于控制最大并发请求数量。
* **解决什么问题**：LLM API 调用、批量 Embedding 计算、海量网页抓取等属于典型 I/O 密集型任务。传统同步阻塞代码按顺序等待响应，吞吐量极低（如处理 1000 个请求耗时上千秒）。异步协程可以在网络等待空闲期切换处理其他任务，将耗时缩短数十倍。
* **工作机制与并发限流**：
  * **事件循环**：通过 `async def` 定义协程，在网络请求等待处使用 `await` 挂起，释放 CPU 执行权。
  * **`asyncio.Semaphore`**：精准控制同一时间允许并发执行的协程上限。必须防止无限制并发引发三类生产事故：1）触发大模型提供商速率拦截（429 Too Many Requests，RPM/TPM 配额超限）；2）目标服务器 IP 封禁；3）内存与句柄资源耗尽。

### 2.3 强类型数据校验与契约约束

* **是什么**：Pydantic v2 是基于 Python Type Hints 运行的高性能强类型数据校验与建模库。
* **为什么需要**：LLM 本质上生成非结构化自由文本，而真实软件系统中的下游数据库、API 接口及前端渲染需要格式确定、字段明确的 JSON 数据。
* **工作机制与应用场景**：
  * **自动类型校验与转换**：解析 JSON 字符串，校验字段类型，失败时抛出明确的 `ValidationError`。
  * **结构化输出 Structured Output**：将定义的 `Pydantic BaseModel` 自动转换为 OpenAI / Anthropic 规范的 JSON Schema 字典，注入给 LLM 作为格式契约，实现 100% 稳定提取。
  * **Tool / Function Calling 定义**：为 Agent 工具函数提供输入参数的契约描述与 Schema 解析。

### 2.4 网页抓取与知识库文本清洗

* **是什么**：基于 httpx 与 BeautifulSoup4 构建的 HTTP 请求、HTML DOM 树解析与数据清洗流水线。
* **为什么需要**：遵循 RAG 黄金法则“Garbage in, Garbage out”（垃圾输入导致垃圾输出）。原始网页充斥导航栏、侧边栏、广告弹窗、页脚版权等噪音，若直接向量化会严重污染索引并降低检索准确率。
* **清洗工作流程**：使用 `httpx` / `requests` 获取源码，使用 BeautifulSoup4 构建 DOM 树，剔除 `<script>`、`<style>`、`<nav>`、`<footer>`、`<aside>` 等非正文节点，定位 `<article>` 或正文 DOM，配合正则表达式过滤连续空行，提取干净文本。

## 3 大模型交互与 Prompt 工程

### 3.1 LLM API 与 SDK 集成

* **API 接入**：熟练对接 OpenAI、Anthropic (Claude)、Google Gemini、DeepSeek 及国产主流模型 API / SDK，掌握统一调用抽象。
* **核心物理参数控制**：
  * `temperature`：控制输出随机性与采样分布。数值越低（如 0.0~0.2），输出越确定、事实性越强；数值越高（如 0.7~1.0），输出越具创造性。
  * `top_p`（核采样）：控制累计概率阈值，通常与 `temperature` 二选一调优。
  * `max_tokens`：限定最大生成 Token 数，防止死循环或超出预算。
  * **Token 物理机制与 Context Window**：理解字符与 Token 的转换比例，精细化管理上下文窗口，防止溢出截断。

### 3.2 提示词架构设计

* **消息层级划分**：严格区分 System Prompt（角色设定、安全护栏、硬性规则）、User Prompt（当前输入与上下文）、Assistant Prompt（历史回答或引导前缀）。
* **常用高级范式**：
  * **Few-Shot 少样本提示**：提供 2~3 个高质量“输入-输出”范例，极大提升输出格式与推理逻辑的稳定性。
  * **CoT思维链**：引导大模型“一步步思考（Let's think step by step）”，显式输出中间推理过程，显著提高复杂逻辑分析与数学推理的正确率。
  * **正反双向约束**：不仅声明“应该做什么”，还必须明确声明“严禁做什么 Negative Constraints”。
* 完整的提示词分层与模板写法见 [[01_提示词]]。

### 3.3 Function Calling 与工具调用握手机制

**（1）握手流程**

* **工作原理**：开发者将工具函数的名称、功能描述及入参 JSON Schema 发送给 LLM；LLM 根据用户意图不直接返回文本，而是返回包含工具名与提取参数的 `tool_calls` JSON 结构；后端代码接收该结构，在本地执行工具函数，并将结果以 Tool Message 返回给 LLM，LLM 总结后给出最终回答。

```text
用户输入请求
→ LLM 接收 User Input 与工具列表 JSON Schema
→ LLM 判断需要调用工具，返回 tool_calls 指令（包含函数名与 JSON 参数）
→ 后端应用拦截指令，解析参数并通过 Pydantic 校验
→ 本地/远程执行工具函数（如数据库查询、API 请求）
→ 将工具执行结果包装为 Tool Message 返回给 LLM
→ LLM 结合工具结果进行最终汇总推理
→ 输出最终文本结果给用户
```

**（2）关键术语与设计逻辑**

| 术语 | 准确定义 | 通俗解释 | 相关概念 |
| --- | --- | --- | --- |
| **Pydantic** | Python 中基于类型提示的高性能强类型数据校验与建模库 | 接口和数据的“安检员”，确保数据类型和格式完全正确 | Type Hints、JSON Schema、FastAPI |

* **机制设计逻辑**：让大模型专注于逻辑推理与参数提取，将实际的物理操作（写库、发邮件、算术）交由确定性的代码执行。
* 工具定义、注册与多轮调用的完整实现见 [[02_工具调用]]。

## 4 RAG 检索增强与知识库流水线

### 4.1 全流水线 8 步架构


1. 文档解析
2. 清洗过滤
3. 切片 Chunking
4. 向量化 Embedding
5. 向量 / 关系存储
6. 混合检索 Retrieval
7. 重排序 Reranker
8. Context 拼装生成

### 4.2 切片策略

* **传统切分**：按固定字符数 / Token 数量切分（如 `RecursiveCharacterTextSplitter`），需设置重叠窗口 Overlap（如 10%~20%）保留切片边界语义。
* **按标题层级切片**：解析 Markdown 或 PDF 目录树，保持章节标题与正文段落的完整层级结构。
* **父子分段 Parent-Child Chunking**：小切片 Child Chunk 用于向量检索以保证高相似度匹配；匹配成功后，提取其对应的更大上下文母切片 Parent Chunk 提交给 LLM，解决“高精准检索”与“完整上下文”之间的矛盾。
* 具体切分参数与边界策略见 [[02_文本分块策略]]。

### 4.3 向量数据库与存储选型

* **专有向量数据库**：
  * `Chroma`：本地轻量级嵌入式向量库，适合 PoC 验证与单机开发。
  * `Qdrant`：基于 Rust 开发的高性能专有向量库，内存控制优异，原生支持 HNSW 索引、Payload 标量过滤与混合检索，是企业级生产首选。
  * `Milvus`：云原生分布式向量库，计算与存储分离，适合百亿级海量向量场景。
* **关系型扩展 PostgreSQL + `pgvector`**：直接在 PostgreSQL 中增加 vector 字段并创建 HNSW / IVFFlat 索引，实现业务数据与向量统一存储、统一 SQL 联合查询与 ACID 事务，极大地降低运维成本。
* Embedding 模型选型与相似度度量见 [[03_向量化原理及选型]]。

### 4.4 混合检索与重排序

* **为什么需要混合检索**：纯向量语义检索 Dense Retrieval 擅长理解上下文语义，但对产品型号、专有名词、代码符号等精确关键词匹配较弱；BM25 稀疏检索 Sparse Retrieval 基于词频倒排索引，擅长精准匹配。
* **混合检索机制**：同时启动“稠密向量检索 + 稀疏 BM25 检索”双路召回，通过 RRF（Reciprocal Rank Fusion 倒排排名融合）算法对结果打分融合。
* **重排序 Reranking**：初筛召回 20~50 个切片后，调用 CrossEncoder 重排序模型（如 BGE-Reranker）对“查询-切片”对进行深度交叉注意力打分，过滤不相关噪音，仅保留前 3~5 个高精切片拼装 Context，大幅提升忠实度。
* 查询改写、融合与重排的完整链路见 [[04_查询工程与混合检索重排]]。

### 4.5 高级 RAG 演进范式

* **Anthropic Contextual Retrieval 语境注入**：在切片向量化前，利用大模型为每个切片生成一段包含文档全局背景的简短说明，防止独立切片失去上下文语境。
* **Self-RAG 与 CRAG**：智能体自我反思检索结果相关性，检索质量不足时触发网络搜索修正。
* **GraphRAG**：结合知识图谱提取实体与关系，实现跨文档全局摘要与复杂关联检索。

## 5 Agent 智能体编排与框架选型

### 5.1 Agent 核心范式与架构

* **架构理念**：Agent = Model + Harness。模型负责语义理解与动态决策，Harness 宿主 / 框架负责提供状态管理、工具交互接口、安全沙箱与执行循环。
* **核心机制**：掌握 ReAct（Reason + Act + Observe）循环推理范式，支持 Memory（工作内存与长期记忆）动态管理。
* 运行架构与工具边界见 [[01_Agent基础认知与运行架构]]。

### 5.2 三大主流框架定位与解耦

* **LlamaIndex**：数据与知识引擎。专注于外部数据加载 Readers、文档索引 Indexing、数据摄取流水线 IngestionPipeline 与 Query Engine 高级检索，是处理非结构化数据与 RAG 的“数据图书馆”。
* **LangChain**：应用编排与工具框架。提供统一的模型抽象 Model I/O、LCEL 声明式管道语法（`chain = prompt | model | parser`）、工具库与 OutputParsers。
* **LangGraph**：生产级有状态编排引擎 Orchestration Runtime。专为复杂、长周期、带循环重试 Agent Loop、有状态持久化 Stateful 与人工干预 Human-in-the-Loop 的智能体设计。

### 5.3 LangGraph 核心构件与运行机制

**（1）四大核心构件**

* **共享状态 State**：使用 `TypedDict` 或 `Pydantic` 定义贯穿整个图运行过程的数据结构，通过 Reducer 函数（如 `add_messages`）增量更新。
* **节点 Nodes**：图中的原子 Python 函数，执行特定业务（如大模型推理、RAG 检索、工具调用）。
* **边与条件边 Edges / Conditional Edges**：普通边固定步骤流向；条件边根据 State 字段进行动态路由分发（如判断是否需要调用工具）。
* **持久化存档与恢复 Checkpoints**：在节点执行前后将 State 自动快照存入 PostgreSQL 或 Redis，原生支持故障续传、状态回滚与人工审批 Human-in-the-Loop 挂起。

**（2）有状态图运行机制**

```text
输入初始 State
→ 进入起始节点 Node（执行特定 Python 函数）
→ 节点函数更新 State（通过 Reducer 增量合并消息）
→ 写入 Checkpoints 快照（持久化至 PostgreSQL/Redis）
→ 评估条件边 Conditional Edge（根据 State 字段判断分支）
  ├─ 满足条件 A → 路由至工具节点 Execute Tool → 返回节点重新推理（Agent Loop 闭环）
  ├─ 需要人工确认 → 挂起 Interrupt 等待 Human-in-the-Loop 审批
  └─ 任务完成 → 路由至 END 结束节点并输出最终结果
```

* **机制设计逻辑**：解决传统线性 Chain 无法循环重试、状态丢失与无法人工干预的问题，提供工业级的容错与控盘能力。
* 状态图编排的工程实践见 [[07_工作流编排]]。

### 5.4 低代码平台与二次开发

* Dify / Coze / n8n 等低代码平台适合在 PoC 阶段快速验证产品思路。
* 面对 Code 节点等复杂业务逻辑、自定义签名鉴权、重试熔断及私有化部署对接 SSO 时，必须依赖 FastAPI + LangGraph 的 Python 代码进行自主工程重构。

## 6 后端 API 服务化与数据持久化

### 6.1 FastAPI 接口封装与流式传输

* **异步 Web 架构**：FastAPI 基于 ASGI 标准，原生支持 `async/await`，在 I/O 密集型场景下具备极高吞吐量。
* **SSE（Server-Sent Events）流式响应**：采用 `media_type="text/event-stream"` 媒体类型，后端通过异步生成器 async generator 配合 `StreamingResponse` 逐 Token 推送数据，前端实现打字机效果。

### 6.2 生产鲁棒性控制

* **异步并发限流**：使用 `asyncio.Semaphore` 限制最大并发，防止请求击垮后端向量库或触发大模型 API 429 速率限流。
* **重试与降级**：引入指数退避重试 Exponential Backoff 与超时中断机制；当主模型服务故障时，系统自动 Fallback 切换至备用模型。

### 6.3 数据库持久化与缓存架构

* **关系型业务库**：PostgreSQL / MySQL + Alembic ORM 版本迁移，存储用户权限、订单、Agent State 快照 Checkpoints 与日志。
* **高性能缓存 Redis**：
  * **短期会话 Memory**：毫秒级读写 Thread State。
  * **语义缓存 Semantic Cache**：利用 Redis 缓存高频提问与响应匹配，命中的请求直接返回，大幅降低延时与 Token 成本。
  * **分布式限流**：基于 Redis 实现滑动窗口 API 限流。

## 7 LLMOps、评估与工程安全

### 7.1 评估驱动开发 EDD

* **黄金测试集 Golden Dataset**：构建包含真实业务问题 Question、期望检索切片 ID Expected Chunk IDs 与标准答案 Ground Truth 的测试集。
* **评估指标体系**：
  * **检索层**：测量 Recall@K、Precision@K、MRR、NDCG。
  * **生成层**：测量 Faithfulness（回答忠实度）、Answer Relevance（回答相关性）、Context Precision（上下文精准度）。
* **自动化打分**：结合 `Ragas` 框架或自建评估脚本，在 `pytest` 中跑自动化回归测试，确保系统更新不出现性能倒退。
* 指标定义与评测集构建见 [[05_自动化评测]]。

### 9.1 企业级知识库后端异步流式服务范例

```python
from fastapi import FastAPI, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field
import asyncio
import json

app = FastAPI(title="企业级 RAG 知识库服务", version="1.0")

class RAGQueryRequest(BaseModel):
    query: str = Field(description="用户提问内容")
    stream: bool = Field(default=True, description="是否开启 SSE 流式响应")

async def rag_pipeline_stream_generator(query: str):
    # 模拟 RAG 检索与大模型流式响应过程
    # 1. 模拟向量与 BM25 检索
    await asyncio.sleep(0.2)
    yield f"data: {json.dumps({'event': 'retrieval', 'message': '已完成混合检索与 Reranker 精排'})}\n\n"

    # 2. 模拟 LLM 逐字吐出 Token
    response_text = f"针对问题 '{query}'，结合企业知识库分析如下：系统已采用 Qdrant 向量库与 CrossEncoder 进行重排序，确保回答高准确度。"
    for char in response_text:
        yield f"data: {json.dumps({'event': 'token', 'content': char})}\n\n"
        await asyncio.sleep(0.03)

    yield "data: [DONE]\n\n"

@app.post("/api/v1/rag/chat")
async def rag_chat_endpoint(request: RAGQueryRequest):
    if not request.query.strip():
        raise HTTPException(status_code=400, detail="查询内容不能为空")

    if request.stream:
        return StreamingResponse(
            rag_pipeline_stream_generator(request.query),
            media_type="text/event-stream"
        )
    else:
        return {"answer": f"针对 '{request.query}' 的一次性完整回答"}
```

### 9.2 LangGraph 状态图定义范例

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages

# 1. 定义共享状态 State
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    needs_tool: bool

# 2. 定义节点函数 Node
def reasoning_node(state: AgentState):
    latest_msg = state["messages"][-1]
    # 模拟逻辑推理判断
    if "查询" in latest_msg:
        return {"needs_tool": True}
    return {"needs_tool": False}

def tool_node(state: AgentState):
    # 执行工具逻辑并增量更新消息
    return {"messages": ["工具执行结果: 数据匹配成功"]}

# 3. 构建状态图
workflow = StateGraph(AgentState)
workflow.add_node("reasoning", reasoning_node)
workflow.add_node("tools", tool_node)

# 4. 设置动态条件边
def route_decision(state: AgentState):
    if state["needs_tool"]:
        return "tools"
    return END

workflow.set_entry_point("reasoning")
workflow.add_conditional_edges("reasoning", route_decision)
workflow.add_edge("tools", "reasoning")

# 5. 编译图运行引擎
app_agent = workflow.compile()
```

### 9.3 核心工具选型速记

* **包与环境管理**：`uv`（统一使用 `uv run`）。
* **静态检查与测试**：`Ruff` + `pytest`。
* **Web 后端与流式**：`FastAPI` + `StreamingResponse (media_type="text/event-stream")`。
* **向量数据库**：`Qdrant`（高性能专有）/ `PostgreSQL + pgvector`（统一关系向量）。
* **Agent 编排**：`LangGraph`（状态图）+ `LlamaIndex`（RAG 节点）。
* **评估与监控**：`Ragas` + `LangSmith` / `Langfuse`。
