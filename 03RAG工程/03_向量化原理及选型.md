## 1 向量化原理与相似度度量

### 1.1 为什么需要 Embedding

关键词检索的天然缺陷在于它只能匹配字面。用户问“轿车保养周期”，文档写“汽车维护间隔”，两者没有一个字重合，但指的是同一件事；再叠加口语化提问、代词指代和同义改写，纯字面匹配的漏召回会非常严重。人工打标签、建规则同样不可行：标签体系覆盖不了企业知识的表达多样性，也跟不上知识更新速度。

更根本的问题是，文本是离散的符号序列、长度不一，本身不存在“距离”的定义，机器无法直接计算两段文字的相似程度。要做语义检索，就必须先把文本映射到一个连续空间，让“语义接近”变成可以计算的几何距离——这正是 Embedding 要解决的问题。

### 1.2 Embedding 的核心定义与物理本质
Embedding 是一种将真实世界中的复杂、高维数据对象（如文本、图片、音频等）转换为数学上易于处理的、固定长度的一维数值数组（即稠密向量）的技术。由 Embedding 模型接收数据对象后，将其映射为形如 `[0.16, 0.29, -0.88, ...]` 的向量表示。

在 Embedding 构建的连续几何向量空间中，**语义上相似的数据对象，其对应向量在几何空间中的距离更近；而语义不相关的对象，其向量距离更远**。向量不是随机数值的堆砌，而是对数据深层语义与上下文关系的数学编码。

### 1.3 向量为什么能表达语义

“语义相似的文本，向量距离更近”不是巧合，而是训练目标的结果：Embedding 模型在训练时反复见到语义相关的文本对，通过对比学习不断把这类样本在向量空间中拉近、把无关样本推远。模型学到的不是词表，而是“什么样的表达在语义上等价”。

因此 Embedding 不等于关键词编码：它不保留字面，只保留语义。好处是同义词、改写句、跨语言表达都能匹配；代价是<u>精确编号、产品型号、函数名这类必须字面对齐的内容容易被忽略</u>。这也解释了为什么纯向量检索不够，还需要混合检索补上关键词那一路。

### 1.4 三种相似度度量指标与选用原则
为了在数学上精确衡量高维向量间的“距离”或“相似度”，通常使用以下 3 种物理指标：

* **余弦相似度**：通过计算高维空间中两个向量夹角的余弦值，评估语义方向的一致性。取值范围在 `[-1, 1]` 之间，值越接近 1 说明方向越一致、语义越相似。这是 RAG 系统中最常用的度量方式。
* **点积**：计算两个向量的乘积和。当向量经过归一化处理（模长为 1）后，点积在数学上完全等价于余弦相似度。
* **欧氏距离**：计算两个向量在空间中的绝对几何直线距离。距离越小，说明两者的空间接近度越高、语义差异越小。

三种指标本身没有优劣，关键在于“谁训练、谁检索就用谁”：

* **各自比较什么**：余弦相似度比较方向，忽略向量长度；点积同时受方向和模长影响；欧氏距离比较空间中的绝对位置。
* **什么时候需要关心**：多数 Embedding 模型在训练与推理时使用余弦相似度或归一化后的点积，检索时应沿用模型约定的度量方式；向量已归一化时点积与余弦等价，不同度量不能混用去重建索引，否则相似度排序会失真。

### 1.5 RAG 语义检索通用工作流
Embedding 是 RAG 系统中语义检索的数学基石，其标准通用流转管道包含 4 个阶段：

1. **离线索引构建**：将知识库文档进行物理切分后，使用 Embedding 模型将每个文档块转换为向量，存入向量数据库中。
2. **在线查询检索**：当用户提出问题时，使用**同一个** Embedding 模型将用户输入的 Query 转换为查询向量。
3. **相似度计算**：在向量数据库中，计算“问题向量”与数据库中所有“文档块向量”的相似度得分。
4. **召回上下文**：选取相似度最高的 Top-K 个文档块作为补充上下文，与原始问题一同拼接后送给大语言模型生成答案。

### 1.6 本篇在 RAG 链路中的位置

* **上游**：Chunk 是向量化的单位，分块质量决定向量表征的上限，见 [[02_文本分块策略]]。
* **本环节**：用同一个 Embedding 模型，把知识库 Chunk 与用户 Query 映射到同一向量空间。
* **下游**：检索引擎在这个空间里找最近邻，再经融合与重排产出上下文，见 [[04_查询工程与混合检索重排]]。

## 2 向量模型选型矩阵

不同的向量模型在语言偏向、上下文长度、向量维度及部署成本上存在显著差异。选择合适的 Embedding 模型是保障检索召回率的第一道关卡。

### 2.1 国内主流模型
* **BGE 系列（北京人工智能研究院 BAAI）**：开源界顶尖模型，包含 BGE-Large、BGE-M3 等。BGE-M3 支持多语言（100+种）、多粒度及长文本（最大 8192 Tokens），在中文语义理解与复杂检索任务中表现极其突出。
* **M3E 系列**：通用中文 Embedding 模型，轻量化且易于部署，适合中小规模文本库快速落地。
* **商业 API 方案**：包含阿里 Qwen Embedding（通义）、智谱 GLM Embedding 等，开箱即用，免去 GPU 显存部署开销。

### 2.2 国外主流模型
* **OpenAI text-embedding-3 系列**：包含 `text-embedding-3-small` 和 `text-embedding-3-large`，支持动态维度裁剪调优，兼具高质量表现与高泛化能力。
* **Cohere Embed**：针对多语言与企业级搜索、推荐场景进行了深度优化的商业 Embedding API，支持对检索意图进行显式建模。

### 2.3 模型选型维度对比

| 维度    | 说明                                         |
| ----- | ------------------------------------------ |
| 语言支持  | 中文、英文还是多语言；中文知识库优先看中文语义表现                  |
| 上下文长度 | 512 / 8192 Tokens 等，需要覆盖实际 Chunk 的长度       |
| 向量维度  | 768 / 1024 / 1536 等，维度越高表达力越强，但存储与检索成本同步上升 |
| 部署方式  | 本地开源模型（可控、需要显存）与商业 API（免运维、按量计费、需评估数据合规）   |
| 能力范围  | 是否同时支持稀疏向量、多向量等，决定能否简化混合检索链路               |

### 2.4 模型兼容性与重新向量化

* **Query 与 Document 必须同源**：查询向量与文档向量要来自同一个或同一系列兼容的模型。不同模型各自定义自己的向量空间，跨模型计算相似度没有意义。
* **换模型等于重建索引**：更换 Embedding 模型后，库中所有存量向量都失去可比性，必须全量重新向量化并重建索引。这是按 Chunk 数量计的算力与时间成本，属于上线前必须评估的架构决策。
* **同一模型内的维度裁剪是兼容调整**：像 `text-embedding-3` 系列支持的维度裁剪，属于同一模型内的表示调整，但仍需按新维度重新生成向量。

## 3 向量数据库的数据模型与关键技术

### 3.1 存储三要素
在向量数据库中，单条知识记录必须完整且强绑定以下三个部分：

1. **知识文本**：切片后的原始文本内容。
2. **语义向量**：通过 Embedding 模型计算得到的稠密数值数组。
3. **元数据**：描述切片的附加 JSON 对象（包含文件名、章节路径、页码、权限标签、创建时间等）。

### 3.2 索引、过滤、Top-K 与分区
* **向量索引**：用于加速高维向量空间匹配的高级算法结构（如 HNSW 图结构，分层可导航小世界），避免全量暴力计算。HNSW 通过构建多层“邻居图”，让 Query 不需要遍历所有向量，而是从粗到细地快速接近目标向量。
* **近似最近邻搜索**：在高维空间中，牺牲极小比例的数学精度来换取成百上千倍的检索速度提升，是毫秒级高并发查询的物理支撑。
* **元数据过滤**：支持在向量相似度计算前或计算后，根据附加的标量属性执行硬性条件过滤。
* **数据分区**：在大规模向量存储中，将数据划分为逻辑或物理分区，缩小单次检索的搜索域，大幅提高查询性能与吞吐量。
* **权限隔离**：多租户与多业务线的数据隔离依赖“身份认证 ➔ 角色解析 ➔ 元数据过滤条件 ➔ 底层强过滤”的链路，详见 [[06_LLMOps与可观测性运维]]。

## 5 索引与检索算法

### 5.1 为什么需要向量索引

不做索引就是精确搜索：每次查询都要与库中所有向量逐一计算距离，开销随向量数量线性增长。知识库到十万、百万级时，单次查询要遍历百万次距离计算，毫秒级响应无法实现。

向量索引的作用，是把近似最近邻检索 ANN 变成“只访问少量候选”：牺牲极小比例的召回精度，换取数量级的延迟下降。代价是引入了新的可调参数，例如 HNSW 的 efSearch、IVF 的 nprobe，参数越大召回越全、延迟越高。

需要说明的是，索引并非越复杂越好：数据量在十万级以内时，用 FLAT 做精确搜索反而更简单，召回率还是 100%。

### 5.2 主要向量索引类型对比
选择合适的向量索引是在**查询性能、召回率和内存占用**之间做出权衡的艺术：

| 索引类型 | 工作原理 | 核心优缺点 | 适用场景 |
| ------ | ------ | ------ | ------ |
| **FLAT** | 暴力搜索，计算查询向量与所有向量的实际距离。 | 优点：100% 召回率，结果最准确；缺点：速度慢，内存占用大。 | 对精度要求极高，且数据规模较小（百万级以内）的场景。 |
| **IVF 系列 (倒排文件索引)** | 通过聚类将向量划分到多个“桶”，查询时先定位最相似的桶，再在桶内精确搜索。 | 优点：大幅缩小搜索范围，提高吞吐量；缺点：召回率非 100%（相关向量可能落在未搜桶中）。 | 通用场景，尤其适合高吞吐量的大规模数据集。 |
| **HNSW (基于图的索引)** | 构建多层邻近图，从最上层稀疏图快速定位，再在下层密集图中精确搜索。 | 优点：检索极快，召回率极高；缺点：内存占用非常大，索引构建时间长。 | 对查询延迟有严格要求（如实时推荐、在线搜索）的场景。 |
| **DiskANN (基于磁盘的索引)** | 为 SSD 等高速磁盘优化的图索引结构。 | 优点：支持远超内存容量的海量数据集（十亿级+），保持低延迟；缺点：延迟略高于纯内存索引。 | 数据规模巨大、无法全部载入内存的场景。 |

### 5.3 HNSW 基础认知

HNSW 是当前最常用的向量索引之一，理解它只需要三层直觉，不必推导数学：

* **分层结构**：底层是包含全部向量的密集图，越往上节点越少、连接越长，负责快速跨越远距离。
* **搜索路径**：查询从最上层的入口点开始，在每一层贪心地向更近的邻居移动，找到局部最近点后再下降到下一层，直到最底层得到结果。
* **为什么快**：整个过程只访问少量邻居节点，不需要遍历全部向量，因此延迟远低于精确搜索。

代价是内存占用大、构建索引慢。工程上主要调整三个参数：M 控制每个节点的邻居数量，efConstruction 控制建索引时的搜索范围，efSearch 控制查询时的搜索范围——前两者影响索引质量，后者直接影响召回与延迟的平衡。

### 5.4 Milvus 数据库的物理结构模型

以 Milvus 为例，工业级向量数据库的数据组织包含以下核心概念：

* **Collection (集合)**：相当于关系型数据库中的一张**表**，是存储、管理和查询向量及相关元数据的最高层容器。
* **Schema (模式)**：定义 Collection 的数据结构与字段规则，包含**主键字段**、**向量字段**及**标量字段**。
* **Partition (分区)**：Collection 内部的逻辑划分。在查询时指定特定分区搜索，可大幅减少数据扫描量，显著提升检索速度。一个 Collection 最多支持 1024 个分区。
* **Alias (别名)**：Collection 的动态“昵称”。支持在不修改上层应用代码的前提下，将别名原子性地从旧 Collection 切换至新 Collection（例如 `v1` 到 `v2`），实现数据更新与索引重构时的无缝升级。
* **Entity (实体)**：相当于数据库中的一条具体记录，包含主键、向量及元数据。

### 5.5 近似最近邻检索与增强检索模式
在构建好 Collection 和 Index 后，系统可以通过以下多种检索模式实现精准召回：

1. **基础向量检索**：利用预先构建好的索引，传入 `anns_field`、`data`（查询向量）、`limit`（Top-K）及 `search_params`，从海量数据中极速找到最相似的片段。
2. **过滤检索**：将标量字段过滤表达式（如价格范围、权限标签、分类等）与向量相似性检索相结合。先筛选符合条件的实体子集，再在子集内执行 ANN 检索，大幅提高查询精准度。
3. **范围检索**：定义距离或相似度的阈值区间，返回所有落在该范围内的实体（常用于人脸识别身份验证或异常点检测）。
4. **多向量混合检索**：在一个请求中同时检索多个向量字段（如密集向量、稀疏向量、图片向量），并通过重排策略（如 `RRFRanker` 或 `WeightedRanker`）融合不同检索流的结果。稀疏与稠密两路的融合原理见 [[04_查询工程与混合检索重排]]。
5. **分组检索**：按特定字段（如 `document_id`）对检索结果进行打散分组，确保每个分组仅返回最高分的结果，从而大幅提升召回结果的多样性，避免同源内容挤占 Top-K 窗口。

## 6 向量检索如何评估

检索质量的完整指标体系与自动化评测方法见 [[05_自动化评测]]，这里只保留向量检索层需要盯住的几项。

### 6.1 Recall@K 与 Precision@K

* **Recall@K**：应该被召回的知识有没有出现在前 K 个结果里，反映索引与模型是否漏掉了正确内容。
* **Precision@K**：前 K 个里有多少是真相关的，反映检索结果是否掺入了过多噪声。

### 6.2 Latency 与 Throughput

* **Latency**：单次查询耗时，直接决定用户感知的响应速度。
* **Throughput**：单位时间能处理的查询量，决定系统能承载多少并发。

### 6.3 Recall 与 Latency 的权衡

向量检索的核心工程权衡就在这两者之间：放宽 efSearch 或 nprobe，召回率上升、延迟上升；收紧则相反。调参时先用黄金测试集测出召回上限，再反向调整参数，把延迟压回可接受区间。

## 7 前沿演进：多模态嵌入

### 7.1 传统纯文本 RAG 的痛点
在传统 RAG 中，向量模型仅能处理纯文本。对于包含系统架构图、折线趋势图、产品外观照片或复杂图文表格的文档，传统方式通过“PDF ➔ OCR 提取文字 ➔ 纯文本切块”处理，会将视觉空间几何与拓扑关系完全打碎，造成极高的信息损耗。

### 7.2 异构编码与跨模态对齐原理
多模态嵌入通过直接捕捉图像与文本的联合语义，实现了“所见即所得”的无损向量化。其核心原理包含两个阶段：

1. **异构特征编码**：图像侧采用视觉编码器（如 Vision Transformer / ViT、SigLIP）将图片切分为 Patch 并提取视觉特征；文本侧采用标准 Transformer 文本编码器提取语言特征。
2. **跨模态对齐**：通过对比学习训练，使描述某张图的文字与该图片本身在高维向量空间中的坐标无限靠近。最终使得文本向量与图片向量可以**直接计算余弦相似度**。

### 7.3 开源实践与选型演进趋势
以 `bge-visualized-m3` 为代表的现代多模态嵌入模型，支持“图文联合输入”，例如同时提交架构草图与文字说明进行综合检索，并支持 8192 Tokens 长文本与 100+ 种语言。

新型 **Omni / 统一多模态嵌入模型**（如 Jina v5-omni、BGE-Visualized、ColQwen2）不仅能同时理解图文，还能高精度处理高分辨率的复杂排版页面，是高级 RAG 架构升级演进的核心方向。

## 8 小结

* 关键词匹配只能对齐字面，文本检索需要先把语义映射到可计算的向量空间，这是 Embedding 存在的理由。
* Embedding 表达的是语义而不是字面，所以能匹配同义表达，但会漏掉精确编号，需要混合检索补齐。
* 选型的第一约束是模型兼容：Query 与 Document 必须同源，换模型意味着全量重新向量化与重建索引。
* 存储侧的核心是 Chunk、向量、元数据三位一体，检索侧的核心是索引与过滤条件。
* 索引决定检索的延迟上限，评估则要同时看 Recall@K 与 Latency，并在两者之间持续调参。
