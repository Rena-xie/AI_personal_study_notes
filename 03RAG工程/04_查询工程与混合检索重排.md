## 1 检索前查询工程

### 1.1 为什么不能直接拿原 Query 检索
在检索增强生成系统中，传统的检索流程假设用户输入的原始提问可以直接作为检索关键字或向量。然而在实际应用场景中，用户原始提问通常存在诸多天然缺陷：
* **表达口语化与语法不规范**：用户倾向于输入简短、含糊或充满口语套话的语句。
* **上下文与主语缺失**：在多轮对话中，用户提问往往包含大量的代词（如“它的原理是什么”、“前者和后者有什么区别”），脱离上文上下文直接检索会导致严重的检索偏离。
* **信息过于具体或过于抽象**：过于具体的问题容易缺乏通用的背景知识，过于抽象的问题则难以直接匹配具体的文档切片。
* **跨多实体复合提问**：单条提问中可能同时包含多个不同的实体和查询子需求（如“对比 ResNet 与 DenseNet 梯度传递与参数量的异同”）。
* **语义空间错配：用户使用的提问词汇（短文本、问题视角）与知识库文档（长文本、答案视角）在向量空间中存在内在的语义表达差异。

因此，必须在 **Query → Retriever → Context → LLM** 的链路中引入“检索前智能查询处理层”。其核心思想是将大语言模型从单纯的“文本生成器”升级为“意图解析器与规划器”，先精准理解用户真实意图，再将原始 Query 转化为最适合知识库检索的形式。

### 1.2 查询重构六大技术

#### 1.2.1 查询重写
* 利用 LLM（大语言模型）将用户原始问题改写为**语义更明确、更完整、更适合检索的 Query**。

典型处理：- 语法纠错- 补充省略信息- 代词指代还原- 多轮对话上下文融合- 补充必要实体- 消除歧义- 将口语化表达转换成更适合搜索的表达
Rewrite 过宽→ 可能 Precision ↓
Rewrite 过窄→ 可能 Recall ↓

Query Rewrite 的目标是：**保持原始用户意图，同时提高检索可用性。**
实践中可以保留原 Query，并同时生成 Rewrite Query，避免改写错误导致信息损失。
#### 1.2.2 多查询
一个用户问题可能存在多个合理的表达方式。Multi-Query 使用 LLM 从不同角度生成多个 Query，然后分别检索，最后合并结果。

查询数量 ↑
→ Retrieval 次数 ↑
→ 计算 / API 成本 ↑
→ Latency（延迟）↑
→ 候选结果 ↑
→ 噪声可能 ↑

因此通常需要后续：Fusion+Reranker进行结果合并和去噪。
#### 1.2.3 查询扩展
给原始 Query 增加同义词、相关术语、关键词或其他检索表达，其目的是扩大 Query 与知识库词汇之间的覆盖范围。
#### 1.2.4 子问题拆解
针对包含多个独立意图或多个实体的复杂问题，将一个复杂问题拆成多个逻辑上独立的子问题。
#### 1.2.5 退一步提示
先从具体问题退到更高层次、更一般的原理问题，再检索基础知识，比较适合：- 技术原理解释
- 复杂专业问题- 需要基础理论支撑的推理问题- 法规 / 标准中的具体条款理解- 科学知识问答

#### 1.2.6 假设性文档嵌入
* 把“问题检索文档”转换为“假设性文档检索真实文档”，让查询表示更接近知识库中的文档表示，从而跨越语义鸿沟，提升高难度提问的召回效果。
* 假设性文档由 LLM 生成，因此存在四类副作用：可能包含事实错误、添加原问题没有的信息、引入偏差，以及增加一次 LLM 调用。因此 **HyDE 不是必然提升召回率，而是一种需要通过 Retrieval Evaluation 验证的 Query Engineering 策略。**

```
Query Rewrite
→ Query 更清晰
→ 可能提高 Precision
→ 过度具体可能降低 Recall

Multi-Query
→ 检索覆盖面扩大
→ Recall 可能提高
→ 候选数量和噪声增加

Query Expansion
→ 增加词汇覆盖
→ 可能改善词法匹配

Sub-question Decomposition
→ 复杂问题拆开
→ 更容易分别找到所需知识

Step-back
→ 补充基础理论
→ 有助于复杂问题的知识召回

HyDE
→ 改善 Query-to-Document 表达匹配
→ 可能改善语义检索 Recall
```

最终都应该通过：
Recall@K、Precision@K、MRR、NDCG、Context Recall、Context Precision、Answer 、orrectness、Faithfulness，进行验证，而不是凭感觉认为某种 Query 技术一定更好。

```
                    User Query
                        ↓
               Query Understanding
                        ↓
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
       简单明确       模糊/缺上下文      复杂问题
          ↓             ↓             ↓
      直接检索       Query Rewrite   Decomposition
                                      /
                                 Multi-Query
          └─────────────┬─────────────┘
                        ↓
              Dense + Sparse Retrieval
                        ↓
                     Fusion
                        ↓
                    Reranker
                        ↓
                     Context
                        ↓
                       LLM
```

### 1.3 查询构建与结构化筛选

在现实业务中，知识库不仅包含非结构化文本，还附带丰富的结构化元数据（如创建时间、作者、部门分类、密级等）。传统的向量检索无法处理硬性过滤条件。

#### 1.3.1 元数据过滤提取
利用 LLM 将自然语言提问自动解析拆解为两部分：
* **语义检索词**：用于向量数据库的相似度搜索。
* **结构化过滤条件**：提取出表达式（如 `year == 2024 AND category == 'technical'`），在向量计算前强行过滤数据库元数据。

#### 1.3.2 结构化数据查询扩展
* **Text2SQL**：针对关系型数据库，利用 LLM 理解数据库 Schema、表关联字段描述及少样本示例，将自然语言直接转换为标准 SQL 查询，并结合 SQL 执行器反馈进行自动报错重试。
* **Cypher 语句生成**：针对 Neo4j 等知识图谱，将自然语言转换为图查询语言，用于提取复杂实体拓扑关系。

## 2 智能查询路由

### 2.1 智能路由的核心定位
在一个企业级复杂系统中，知识可能分散在不同的存储介质与处理服务中。如果对所有问题都无脑发起全盘向量搜索，不仅效率低下，还会引入大量噪声。智能查询路由的核心任务是：在检索发生前，根据用户 Query 的意图，精准决定该查询应该分发给“谁”去处理。

### 2.2 三大分发维度
* **数据源路由**：决定查询去往何种底层存储（如产品文档去向量库，用户订单去 SQL 数据库，股权关系去知识图谱，实时新闻去 Web 搜索引擎）。
* **组件/能力路由**：决定调用何种处理链（如简单 FAQ 走基础向量检索，复杂业务逻辑走 Agent 编排，自动化操作走 API Tool）。
* **Prompt 路由**：根据问题领域自动匹配专用的系统提示词（如代码问题路由至 Code Prompt，逻辑推理路由至 CoT Prompt）。

### 2.3 两种路由机制原理与对比

#### 2.3.1 基于大模型的动态路由
* **实现方式**：利用大模型作为分类器，分析用户 Query 的深层意图，通过 `RunnableBranch` 或条件判断分发至对应的执行链。
* **优点**：能够深度理解复杂表达、多重意图与隐性语意，分类极其灵活。
* **缺点**：增加了一次 LLM 调用，带来 100~300ms 额外的延迟和 Token 成本，且可能存在少许输出随机性。

#### 2.3.2 基于语义向量的路由
* **实现方式**：预先为各个候选路由目标（如“客服知识库”、“订单数据库”、“代码工具”）编写几句代表性的描述文本并计算 Embedding 向量。当用户 Query 传入时，计算 Query Vector 与各路由描述向量的余弦相似度，命中最高分路由。
* **优点**：无需调用大语言模型，计算速度达到毫秒级，零 Token 开销，确定性强。
* **缺点**：仅依赖表面语义相似度，对长尾复杂逻辑或无显式特征的提问理解力不如 LLM。

| 路由机制 | 判断方式 | 响应延迟 | Token 成本 | 复杂意图处理能力 | 适用场景 |
| ------ | ------ | ------ | ------ | ------ | ------ |
| **LLM Router** | 大模型语义分类与规划 | 较慢 (100~300ms) | 有成本 | 极强，支持深层推理与多分支 | 复杂业务 Agent、多阶段任务调度 |
| **Embedding Router** | 向量空间余弦相似度 | 极快 (<10ms) | 零成本 | 较弱，依赖表面语义匹配 | 高并发低延迟路由、领域明确的数据源分流 |

## 3 双路混合检索

### 3.1 传统单路向量检索的致命瓶颈
传统的稠密向量检索依赖深度学习 Embedding 模型将文本映射至连续高维向量空间（原理见 [[03_向量化原理及选型]]）。虽然它在概念泛化和理解同义词（如“汽车”与“轿车”）方面表现优异，但在工业级生产环境中存在以下致命短板：
* **对特定专有名词不敏感**：对于特定代码函数名（如 `asyncio.gather`）、配置参数（如 `chunk_overlap`）、专业术语、产品型号（如 `RTX-4090`）、人名或数字缩写，向量模型极其容易因为语义稀释而发生漏召回。
* **未登录词与拼写敏感**：遇到模型预训练未见过的专有缩写或用户拼写微小错误时，向量空间坐标可能会大幅偏转。

### 3.2 稀疏检索：BM25 为什么擅长精确匹配

稀疏检索走的是另一条路：它不压缩语义，而是把文本当成词项集合，用词频统计打分。经典算法 BM25 的得分由三部分组成：

* **词频 TF**：查询词在文档中出现次数越多，相关性得分越高，但增长会饱和——出现 10 次并不比出现 5 次重要一倍。
* **逆文档频率 IDF**：词在整个语料中越稀有，区分度越强、权重越高，这也是罕见编号与型号能被精准命中的原因。
* **文档长度归一化**：用当前文档长度与语料平均长度之比做惩罚，避免长文档仅凭“词多”占到便宜。

BM25 的两个常用参数是 k1（控制词频饱和程度，常用 1.2~2.0）与 b（控制长度归一化强度，常用 0.75）。

正因为它直接匹配字面，BM25 对专有名词、函数名、型号、编号这类精确内容非常可靠，恰好补上了稠密检索的短板。

### 3.3 稠密与稀疏的双路互补架构

为了解决 3.1 的痛点，工业级高精度 RAG 架构普遍采用“稠密向量 + 稀疏文本”并行执行的双路混合检索流水线。

```
                       User Query
                           ↓
          ┌────────────────┴────────────────┐
          ↓                                 ↓
 Dense Retrieval（稠密检索）       Sparse Retrieval（稀疏检索）
          ↓                                 ↓
      Top-K Dense                        Top-K Sparse
          └────────────────┬────────────────┘
                           ↓
                  Fusion（结果融合）
                  ├─ RRF
                  └─ 其他融合方法
                           ↓
                 Candidate Set（候选集）
                           ↓
                Reranker（重排序）
                           ↓
               Top-N 高相关结果
                           ↓
              Context Construction
                           ↓
                          LLM
```

#### 3.3.1 稠密与稀疏检索特性对比

| 维度       | 稠密向量检索 (Dense Retrieval)                          | 稀疏文本检索 (Sparse / BM25)                    |
| -------- | ------------------------------------------------- | ----------------------------------------- |
| **物理原理** | 基于神经网络 Embedding 计算高维向量余弦相似度                      | 基于词频、逆文档频率与倒排索引                  |
| **核心优势** | 擅长理解同义词、近义词、长句上下文与深层语义概念                          | 强可解释性，精确匹配专有名词、代码符号、型号与精确定位               |
| **核心劣势** | 可解释性差，对冷门词、精确数字、专有函数名不敏感                          | 无法理解同义词（“汽车”≠“轿车”），存在“词汇鸿沟”               |
| **代表技术** | BGE-M3, text-embedding-3-small, OpenAI Embeddings | ElasticSearch BM25, Lucene, Qdrant Sparse |

## 4 异构得分融合

混合检索的核心难题在于：稠密向量检索返回的相似度得分（如余弦相似度，范围通常在 `[0, 1]`）与稀疏 BM25 检索返回的得分（如基于词频累加的无界正实数，可能是 `12.5`、`38.2`）属于完全不同的数轴与量纲。**绝对不能将两个系统的原始得分直接相加**。

### 4.1 倒数排名融合

#### 4.1.1 核心原理
RRF 是一种无量纲依赖的排名融合算法。它**完全放弃两套检索系统的原始相似度数值**，仅仅关注每个文档在其各自检索结果列表中的**物理排名位置**。一个文档只要在两路检索结果中都排在靠前的位置，它就能获得极高的综合得分。
#### 4.1.2 数学公式与参数说明
对于任意候选文档 $d$，其 RRF 得分计算公式为：
$$RRF\_Score(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
* $M$：参与融合的检索系统集合（例如 Dense 系统与 Sparse 系统）。
* $r_m(d)$：文档 $d$ 在检索系统 $m$ 中的排名位置（从 1 开始，排第 1 名则 $r_m(d)=1$）。若文档未在系统 $m$ 的召回列表中出现，则该项为 0。
* $k$：平滑常数，通常在工程中固定设置为 $60$。其作用是防止排名第一的文档（$1/1$）得分比排名靠后的文档过高，起到平衡高低排名的离散平滑作用。

#### 4.1.3 工程优势
* **无标尺依赖**：无需对得分进行复杂的归一化校准，对评分分布离群点具备极强的鲁棒性。
* **高稳健性**：能极其稳健地将向量召回列表与 BM25 召回列表融合成一个统一的高质量 Top-K 列表。

### 4.2 线性归一化与加权融合

#### 4.2.1 计算逻辑
若业务场景需要对语义和关键字进行人工权重干预，可采用 Min-Max 归一化后再进行加权计算：
1. 对 Dense 得分与 Sparse 得分分别执行 Min-Max 归一化，将得分全部缩放至 `[0, 1]` 空间。
2. 设定语义权重因子 $\alpha$（$0 \le \alpha \le 1$），最终融合分数为：
$$Hybrid\_Score = \alpha \cdot Dense\_Score_{norm} + (1 - \alpha) \cdot Sparse\_Score_{norm}$$
#### 4.2.2 权重的场景调优策略
* **偏向语义场景（$\alpha = 0.7 \sim 0.8$）**：智能客服问答、自然语言意图理解、学术概念研讨。
* **偏向关键字场景（$\alpha = 0.2 \sim 0.3$）**：代码仓库搜索、产品型号与规格参数查询、法律条文与编号检索。

## 5 两阶段精排重排序

### 5.1 两阶段架构设计哲学
在实际生产中，直接将多路混合检索粗排召回的前 50~100 个文本片段全部塞给 LLM 极其低效。这会导致推理 Token 成本激增、首字延迟大幅延长，并且极易触发大模型的“中间失真/中间丢失”现象（即 LLM 会忽略长提示词中间段落的关键信息，导致生成幻觉）。

因此，工业级 RAG 必须采用 **初筛 + 精排** 的两阶段检索架构：
* **初筛阶段**：由混合检索负责，注重 **高召回率**。目标是以极快速度（毫秒级）从百万级海量 Chunk 中快速捞出 Top 20~50 个潜在相关的候选片段。
* **精排阶段**：由交叉编码器负责，注重 **高精准度**。目标是以深度交叉注意力重新逐一比对，挑选出最精准的 Top 3~5 个精选片段送入 LLM。

```
全量知识库 (百万级 Chunk)
       │
       ▼ 【初筛：Bi-Encoder 混合检索】(高召回、毫秒级、粗粒度)
候选列表 (Top 30~50)
       │
       ▼ 【精排：Cross-Encoder Reranker】(高精度、逐字深度交互)
精选上下文 (Top 3~5)
       │
       ▼
投喂给 LLM 生成最终回答
```

### 5.2 Bi-Encoder 与 Cross-Encoder 对比

```
【Bi-Encoder 架构】                      【Cross-Encoder 架构】
Query ───► [Encoder] ──► Vector Q ┐      Query  ┐
                                  ├─► 点积/余弦  └─► [Query + Document] ──► [Encoder] ──► 相关性得分 (0~1)
Doc   ───► [Encoder] ──► Vector D ┘      Doc    ┘   (全量 Cross-Attention)
```

#### 5.2.1 Bi-Encoder
* **原理**：Query 和 Document 分别由独立的 Embedding 模型编码为固定长度的向量。文档向量在离线阶段即计算完毕并建库；检索时仅需在线计算 Query 向量与库中向量的点积或余弦相似度。
* **优点**：计算解耦，速度极快（可利用 ANN 索引达毫秒级高并发），极其适合在大规模数据集里做范围筛选。
* **缺点**：Query 与 Document 在编码过程中**没有任何词级别的交叉注意力交互**，导致局部细节匹配度不足。

#### 5.2.2 Cross-Encoder
* **原理**：将 Query 文本与候选 Document 文本进行物理拼接，作为单一输入整体喂入 Transformer 神经网络。在模型的每一层中，Query 中的每一个 Token 都会与 Document 中的每一个 Token 执行深度交叉注意力计算。
* **优点**：能够捕捉 Query 与文档之间极其微小、复杂的词级语法与语义比对，输出的相关性得分极高且极其精准。
* **缺点**：无法预先计算向量，每一个待评估的 `Query-Doc` 对都需要实时通过深度网络进行推理，计算耗时长，不适合直接对海量数据全量运行。

#### 5.2.3 职责边界与深度对比

| 维度 | Bi-Encoder (双编码器 / 向量模型) | Cross-Encoder (交叉编码器 / 重排模型) |
| ------ | ------ | ------ |
| **交互机制** | Query 与 Doc 独立编码向量，无 Token 级交叉注意力 | Query 与 Doc 拼接输入，全量 Token 级 Cross-Attention 比对 |
| **计算耗时** | 极低（毫秒级，利用向量索引加速） | 较高（十到数百毫秒级，随候选文档数增加） |
| **精度 (Precision)** | 中等（用于大范围初筛召回） | 极高（用于 Top 3~5 的最终挑选） |
| **架构定位** | 第一阶段：粗排 Recall | 第二阶段：精排 Rerank |

分工可以概括为一句话：**Retriever 负责召回得够全，Reranker 负责排序得够准**。Sentence Transformers 官方文档把这一组合称为 Retrieve & Re-Rank——检索阶段用 Bi-Encoder 换取速度，重排阶段用 Cross-Encoder 换取精度。

### 5.3 Reranker 主流模型选型
* **商业 API 标杆**：`Cohere Rerank`，在多语言与复杂企业级场景中准确率表现卓越。
* **高性能开源模型**：BAAI 开源的 `BGE-Reranker` 系列（如 `bge-reranker-large`、`bge-reranker-m3`），对中文及跨语言支持极佳。
* **轻量级 CPU/本地部署方案**：`FlashRank`、`Jina Reranker`，体积微小、响应延迟极低，非常适合纯 CPU 容器化部署。

### 5.4 Reranker 如何评估

重排效果用排序类指标衡量：

* **Recall@K**：先看正确片段有没有进入候选集——候选里没有，重排再强也没用。
* **MRR**：看第一个正确结果排在多靠前，适合“只需要一条最优证据”的问答场景。
* **NDCG**：看整体排序质量，对多个相关结果的相对顺序更敏感。

调参时的典型做法是固定同一份候选集，对比“重排前 / 重排后”的 MRR 与 NDCG 变化，指标定义见 [[05_自动化评测]]。

## 6 检索后处理与上下文构建

### 6.1 为什么需要上下文构建

即使经过了两阶段精排，召回的候选 Chunk 中依然可能包含与问题无关的噪声（例如一个 1000 字的 Chunk 中只有 100 字在回答问题）。检索后处理的目标，就是把召回结果精炼成最纯净的“知识干货”。

“物理相关”不等于“适合直接投喂”：重排序侧重评估切片与查询的语义匹配度，但这些切片往往存在三类问题。

* **信息冗余与重复**：多路检索与多查询扩展会让不同切片包含大量重叠的背景信息。
* **局部相关与噪声干扰**：一个 1000 Tokens 的长切片中可能只有 200 Tokens 在回答问题，其余 800 Tokens 都是无关上下文，直接拼接会浪费大量 Token。
* **注意力分散**：过长的非核心信息容易让模型的注意力被稀释。

上下文构建的本质，是在 **相关性**、**信息覆盖度** 与 **Token 成本** 三者之间找平衡，用尽可能少的 Token 为模型提供精准、完整且互补的证据。

### 6.2 上下文构建的完整流水线

上下文构建位于精排重排序之后、大模型生成之前，包含六个严格的前后依赖步骤：

1. **重排序输出**：接收交叉编码器选出的前 N 个相关候选切片。
2. **去重与合并**：清除完全相同或高度近似的切片内容。
3. **上下文压缩**：提炼切片中的关键信息，剔除废话与冗余过渡句。
4. **上下文重排序**：调整切片排列顺序，优化大模型的注意力分配。
5. **Token 预算分配**：对系统提示词、历史对话、检索上下文及用户问题进行额度计算与动态截断。
6. **上下文窗口装载**：组装最终 Prompt 并投喂给大语言模型生成答案。

### 6.3 去重与近重复检测

在混合检索与查询扩展场景下，不同检索路径极易召回相同或语义高度重合的内容。

去重包含两个层级：

* **精确去重**：通过哈希匹配（如 MD5、SHA-256）或字符串精确比对，剔除内容完全一致的重复切片。
* **近重复检测**：对于表达略有差异但核心语义高度重叠的切片（例如分别介绍同一概念定义与原理的两段文字），用语义相似度阈值或局部敏感哈希识别并合并，避免重复占用上下文空间。

### 6.4 上下文压缩

上下文压缩的目标是保留与 Query 深度强相关的核心事实，删除无用的背景修饰，提升信息密度。

目前主流的两种压缩路线对比如下：

| 维度 | 抽取式压缩 | LLM 生成式压缩 |
| ------ | ------ | ------ |
| 机制 | 从原始切片中直接筛选与 Query 强相关的句子 | 利用轻量级 LLM 对切片做摘要提炼与重构 |
| 优点 | 不改变原文事实，计算速度快，无幻觉风险 | 压缩率高，表达连贯，提炼灵活 |
| 缺点 | 语言连贯性可能受损，无法跨句融合信息 | 增加一次 LLM 调用的延迟与成本，存在信息遗漏或幻觉风险 |
| 适用场景 | 对事实准确度要求极高的法律、医疗、金融领域 | 允许语义重组的通用问答与摘要场景 |

### 6.5 上下文重排序

大语言模型对长上下文不同位置的信息处理能力存在内在偏差，这一现象被称为“中间信息丢失”：

* **开头**：模型关注度高，信息利用与理解效果最好。
* **结尾**：靠近输出端，利用效果较好。
* **中间**：注意力容易下降，关键细节容易被忽略或混淆。

为缓解这一瓶颈，上下文重排序会把最关键、最直接的证据放在上下文的开头和结尾，把次要补充信息放在中间，通过重排切片顺序最大化利用模型的注意力机制。

### 6.6 Token 预算管理与窗口控制

上下文窗口是大语言模型单次推理能够处理的最大输入与输出 Token 总额，它不是知识库的存储上限。实际调用中必须建立 Token 预算管理，对输入结构做额度划分：

* **系统提示词**：固定预留空间（通常 1K~2K Tokens）。
* **对话历史**：按滑动窗口或总结压缩动态分配（如 2K~4K Tokens）。
* **用户当前提问**：按实际长度保留（通常 100~500 Tokens）。
* **检索上下文**：占用剩余可用额度。

若检索到的切片总长度超出预算，必须按重排序优先级截断或二次压缩，防止触发模型截断错误、响应延迟剧增或推理成本飙升。

### 6.7 结构化切片后处理范式

结构化切片后处理依赖索引侧的特别设计，通过“索引小块、生成大块”的解耦，同时兼顾向量检索的高精度与模型理解的高完整度。

#### 6.7.1 句子窗口后处理

* **机制**：索引阶段把文本切成独立的“单句话”作为向量节点（检索粒度极细），同时在节点元数据中保存该句前后 $N$ 句的文本。
* **后处理流程**：向量检索命中单句节点后，由后处理器（如 MetadataReplacementPostProcessor）拦截，读取元数据并把单句替换扩展为包含前后 $N$ 句的完整上下文窗口，再交给模型。

#### 6.7.2 父子切块反向召回

* **机制**：向量库只存小粒度（200~400 Tokens）的子块用于精确匹配，大粒度（1000~2000 Tokens）、语义完整的父块存在 Key-Value 存储（如 Redis）中。
* **后处理流程**：子块命中后，后处理引擎读取其绑定的 `parent_id`，去 KV 存储反向拉取对应的父块，用更连贯完整的大块替换小块交给模型。

### 6.8 上下文质量评估

上下文构建的效果可以用指标量化，主要看三项：

| 指标 | 核心含义 | 判定方式 |
| ------ | ------ | ------ |
| Context Recall 上下文召回率 | 回答问题所需的关键事实是否完整进入上下文 | 越接近 100% 越好 |
| Context Precision 上下文精确率 | 上下文中相关信息的占比 | 相关切片越靠前、无关信息越少，得分越高 |
| Noise Sensitivity 噪声敏感度 | 存在无关干扰切片时模型产生错误回答的频率 | 取值 0~1，越低代表鲁棒性越强 |

三项指标要结合生成侧的忠实度一起看：Context Recall 低，说明检索与后处理漏掉了关键证据；Context Recall 高但忠实度低，说明证据给到了、模型却没用上或被打扰。完整定义见 [[05_自动化评测]]。

## 7 生成层：从上下文到答案

检索工程的终点是把证据交给模型，但答案质量还取决于最后一环怎么拼、怎么约束。

### 7.1 Context + Prompt + Query → Answer

生成阶段的输入由三部分组成：检索并精炼后的上下文、系统提示词（角色、格式与约束）、用户原始问题。模型在这三者共同约束下产出答案，因此上下文排序、引用格式、拒答规则都应该在这一层显式约定。

### 7.2 有据生成与引用溯源

* **有据生成**：要求模型只依据提供的上下文作答，证据不足时明确拒答，而不是依赖参数记忆补全。
* **引用溯源**：把结论绑定到具体来源（文档、章节、页码），既方便用户核查，也给评测提供可验证的抓手。

Ragas 等评测框架在生成侧提供了 Response Groundedness 与 Answer Accuracy 两项指标，分别对应“回答是否有依据”与“答案是否正确”。

### 7.3 忠实度、答案正确性与幻觉

* **忠实度**：答案是否完全由给定上下文支撑，衡量模型有没有编造。
* **答案正确性**：答案与标准答案或客观事实的一致程度。
* **幻觉**：模型生成了上下文中并不存在、也不符合事实的内容。

三者配合使用才能区分两类问题：检索没找到证据（6.8 节的 Context Recall 低），还是找到了但模型没用上（忠实度低）。指标定义见 [[05_自动化评测]]。

## 8 工业级检索流水线落地全景架构

总结完整 RAG 系统的离线文档工程线与在线智能查询流水线：

```
====================== 【离线数据工程流水线】 =================─────
原始文档 ──► 结构化解析/去噪 ──► 父子/句子窗口切片 ──► 文本/上下文 Embedding ──► 向量库与倒排索引

====================== 【在线智能查询流水线】 =================─────
1. 原始提问 Query ──► [查询工程 Layer] (重写/扩展/HyDE/Self-Query)
                         │
2. 意图分发       ──► [智能路由 Router] (分类去往 Vector DB / SQL / KG)
                         │
3. 粗排召回       ──► [双路混合检索] (Dense 向量 + Sparse BM25)
                         │
4. 异构得分融合   ──► [RRF 算法] (按排名位置无量纲融合召回 Top 30)
                         │
5. 精排重排序     ──► [Cross-Encoder Reranker] (深度交叉注意力精选 Top 3~5)
                         │
6. 检索后处理     ──► [上下文扩展/压缩/C-RAG] (句子窗口替换/不相关拦截)
                         │
7. 最终响应生成   ──► [LLM 配合 Context 生成] (带精准 Metadata 溯源引用)
```

## 9 小结

* 原始 Query 往往不能直接拿去检索，需要在检索前做改写、扩展、拆解或路由。
* 混合检索用稠密向量补语义、用 BM25 补精确字面；两路得分量纲不同，不能直接相加，要靠 RRF 或归一化加权融合。
* 两阶段架构的分工是：Bi-Encoder 负责召回得够全，Cross-Encoder 负责排序得够准。
* 排序之后还要做上下文构建——去重、压缩、排序、Token 预算，目的是用最少的 Token 提供足够且互补的证据。
* 每一步都要用指标闭环验证：检索看 Recall@K，排序看 MRR 与 NDCG，上下文看 Context Recall 与 Context Precision，生成看忠实度与答案正确性。

> **检索工程的每一步，都是在召回与精度、效果与成本之间做取舍。**
