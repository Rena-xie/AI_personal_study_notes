## 1 双路混合检索与异构得分融合

### 1.1 稠密检索的局限与稀疏检索的互补优势

在 RAG 系统中，仅依赖基于向量的稠密检索（Dense Retrieval）往往无法满足高精度搜索需求，原因在于稠密检索存在以下局限：
*   **专有名词不敏感**：针对特定的代码函数名（如 asyncio.gather）、配置参数（如 chunk_overlap）、专业术语、产品型号（如 RTX-4090）、人名或数字缩写，向量模型极其容易因为语义稀释而发生漏召回。
*   **未登录词与拼写敏感**：遇到模型预训练阶段未见过的专有缩写或用户发生的微小拼写错误，向量空间坐标可能会发生大幅偏转。

稀疏检索（Sparse Retrieval）通过词频统计打分弥补了这一短板。经典算法 BM25 的得分由三部分构成：
*   **词频（TF）**：查询词在文档中出现次数越多，相关性得分越高，但得分增长存在饱和效应（出现 10 次的权重并不比 5 次高出一倍）。
*   **逆文档频率（IDF）**：词在整个语料库中越稀有，区分度越强、赋予的权重越高，这也是罕见编号与型号能够被精准命中的本质原因。
*   **文档长度归一化**：通过当前文档长度与语料平均长度的比值做惩罚，避免长文档仅凭借词数多而占优。

稀疏检索直接进行字面匹配，对专有名词、函数名、规格型号与编号极其可靠，与稠密检索形成了天然的优势互补。

### 1.2 稠密与稀疏的双路互补架构

工业级 RAG 架构普遍采用“稠密向量 + 稀疏文本”并行执行的双路混合检索流水线，其整体流转架构如下：

```text
                       User Query
                           │
          ┌────────────────┴────────────────┐
          ▼                                 ▼
 Dense Retrieval（稠密检索）       Sparse Retrieval（稀疏检索）
          │                                 │
      Top-K Dense                        Top-K Sparse
          └────────────────┬────────────────┘
                           │
                  Fusion（结果融合）
                  ├─ RRF
                  └─ 其他融合方法
                           │
                 Candidate Set（候选集）
                           │
                Reranker（重排序）
                           │
               Top-N 高相关结果
                           │
              Context Construction
                           │
                          LLM
```

### 1.3 异构得分融合机制与权重调优

由于稠密检索输出的是余弦相似度或点积得分，而稀疏检索（如 BM25）输出的是无界限的统计得分，两者的得分量纲不同，无法直接相加。

**倒排融合算法（RRF）与 Min-Max 归一化加权**

若业务场景需要对语义和关键字进行人工权重干预，可采用 Min-Max 归一化后再进行加权计算：
1. 对 Dense 得分与 Sparse 得分分别执行 Min-Max 归一化，将得分全部缩放至 [0, 1] 空间。
2. 设定语义权重因子 $\alpha$（$0 \le \alpha \le 1$），最终融合分数为：

$$Hybrid\_Score = \alpha \cdot Dense\_Score_{norm} + (1 - \alpha) \cdot Sparse\_Score_{norm}$$

**权重的场景调优策略**
*   **偏向语义场景（$\alpha = 0.7 \sim 0.8$）**：适合智能客服问答、自然语言意图理解、学术概念研讨等场景。
*   **偏向关键字场景（$\alpha = 0.2 \sim 0.3$）**：适合代码仓库搜索、产品型号与规格参数查询、法律条文与编号检索等场景。

## 2 两阶段精排重排序

### 2.1 初筛与精排的两阶段架构

针对百万级海量数据，系统采用“初筛 + 精排”的两阶段检索架构，兼顾检索速度与结果精度：
*   **初筛阶段**：由混合检索负责，注重高召回率。目标是以毫秒级速度从海量切片中快速捞出 Top 20~50 个潜在相关的候选片段。
*   **精排阶段**：由交叉编码器（Cross-Encoder）负责，注重高精准度。目标是通过深度交叉注意力比对，挑选出最精准的 Top 3~5 个精选片段投喂给 LLM。

```text
全量知识库 (百万级 Chunk)
       │
       ▼ 【初筛：Bi-Encoder 混合检索】(高召回、毫秒级、粗粒度)
候选列表 (Top 30~50)
       │
       ▼ 【精排：Cross-Encoder Reranker】(高精度、逐字深度交互)
精选上下文 (Top 3~5)
       │
       ▼
投喂给 LLM 生成最终回答
```

### 2.2 Bi-Encoder 与 Cross-Encoder 的对比

```text
【Bi-Encoder 架构】                      【Cross-Encoder 架构】
Query ───► [Encoder] ──► Vector Q ┐      Query  ┐
                                  ├─► 点积/余弦  └─► [Query + Document] ──► [Encoder] ──► 相关性得分 (0~1)
Doc   ───► [Encoder] ──► Vector D ┘      Doc    ┘   (全量 Cross-Attention)
```

*   **Bi-Encoder（双编码器 / 向量模型）**： Query 和 Document 分别由独立的 Embedding 模型编码为固定长度的向量。文档向量可离线预先计算并建库；检索时仅在线计算 Query 向量与库中向量的点积或余弦相似度。优点是计算解耦、速度达到毫秒级，适合大范围初筛；缺点是 Query 与 Document 在编码过程中没有 Token 级别的交叉注意力交互，局部细节匹配度不足。
*   **Cross-Encoder（交叉编码器 / 重排模型）**： 将 Query 文本与候选 Document 文本进行物理拼接，作为单一输入喂入神经网络。在模型每一层中，Query 的每一个 Token 都会与 Document 的每一个 Token 执行深度 Cross-Attention 计算。优点是能捕捉极其微小的词级语义比对，相关性得分极准；缺点是无法预先计算向量，每一个待评估对都需要实时进行深度网络推理，计算耗时长，无法全量运行。

两者在职责边界上的对比说明如下：

| **维度** | **Bi-Encoder** | **Cross-Encoder** |
| ------ | ------ | ------ |
| 交互机制 | Query 与 Doc 独立编码向量，无 Token 级交叉注意力 | Query 与 Doc 拼接输入，全量 Token 级 Cross-Attention 比对 |
| 计算耗时 | 极低（毫秒级，利用向量索引加速） | 较高（十到数百毫秒级，随候选文档数增加） |
| 精度 | 中等（用于大范围初筛召回） | 极高（用于 Top 3~5 的最终挑选） |
| 架构定位 | 第一阶段：粗排召回 | 第二阶段：精排重排 |

核心分工可概括为：**Retriever 负责召回得够全，Reranker 负责排序得够准**。

### 2.3 Reranker 主流模型选型与评估指标

**主流模型选型**
*   **商业 API 标杆**：Cohere Rerank，在多语言与复杂企业级场景中准确率表现卓越。
*   **高性能开源模型**：BAAI 开源的 BGE-Reranker 系列（如 bge-reranker-large、bge-reranker-m3），对中文及跨语言支持极佳。
*   **轻量级 CPU/本地部署方案**：FlashRank、Jina Reranker，体积微小、响应延迟极低，适合纯 CPU 容器化部署。

**评估指标**
*   **Recall@K**：衡量正确片段是否进入了前 K 个候选集。若候选集中不存在目标片段，重排模型无法生效。
*   **MRR（平均倒数排名）**：评估第一个正确结果排在第几位，适合仅需单条最优证据的问答场景。
*   **NDCG（归一化折损累计增益）**：评估整体排序质量，对多个相关结果的相对位置顺序高度敏感。

### 2.4 向量索引类型及选型权衡

选择合适的向量索引是在查询性能、召回率与内存占用之间取得折衷：

| **索引类型** | **工作原理** | **核心优缺点** | **适用场景** |
| ------ | ------ | ------ | ------ |
| FLAT | 暴力搜索，计算查询向量与所有向量的实际距离。 | 优点：100% 召回率，结果最准确；缺点：速度慢，内存占用大。 | 对精度要求极高且数据规模较小（百万级以内）的场景。 |
| IVF 系列 | 通过聚类将向量划分到多个桶，查询时先定位最相似的桶，再在桶内精确搜索。 | 优点：大幅缩小搜索范围，提高吞吐量；缺点：召回率非 100%（相关向量可能落在未搜桶中）。 | 通用场景，尤其适合高吞吐量的大规模数据集。 |
| HNSW | 构建多层邻近图，从最上层稀疏图快速定位，再在下层密集图中精确搜索。 | 优点：检索极快，召回率极高；缺点：内存占用非常大，索引构建时间长。 | 对查询延迟有严格要求的实时推荐与在线搜索场景。 |
| DiskANN | 为 SSD 等高速磁盘优化的图索引结构。 | 优点：支持远超内存容量的海量数据集（十亿级以上），保持低延迟；缺点：延迟略高于纯内存索引。 | 数据规模巨大、无法全部载入内存的场景。 |

## 3 检索后处理与上下文构建

### 3.1 上下文构建的必要性与核心目标

经过两阶段精排后，召回的切片仍可能存在三类问题：
*   **信息冗余与重复**：多路检索与多查询扩展会导致不同切片包含大量重叠的背景信息。
*   **局部相关与噪声干扰**：长切片中可能仅有少数段落回答问题，其余内容构成无关上下文，直接拼接会浪费 Token。
*   **注意力分散**：非核心信息过长容易稀释大模型的注意力。

上下文构建的本质，是在相关性、信息覆盖度与 Token 成本三者之间取得平衡，用尽可能少的 Token 为模型提供精准、完整且互补的证据。

### 3.2 上下文构建的 6 步处理流水线

上下文构建位于精排重排序之后、大模型生成之前，包含以下六个递进步骤：
1.  **重排序输出**：接收交叉编码器选出的前 N 个相关候选切片。
2.  **去重与合并**：清除完全相同或高度近似的切片内容。
3.  **上下文压缩**：提炼切片中的关键信息，剔除无用修饰与冗余过渡句。
4.  **上下文重排序**：调整切片排列顺序，优化大模型的注意力分配。
5.  **Token 预算分配**：对系统提示词、历史对话、检索上下文及用户问题进行额度计算与动态截断。
6.  **上下文窗口装载**：组装最终 Prompt 并投喂给大语言模型生成答案。

### 3.3 去重与近重复检测

*   **精确去重**：通过哈希匹配（如 MD5、SHA-256）或字符串精确比对，剔除内容完全一致的重复切片。
*   **近重复检测**：对于表达略有差异但核心语义高度重叠的切片，利用语义相似度阈值或局部敏感哈希识别并合并，避免重复占用上下文空间。

### 3.4 上下文压缩策略对比

上下文压缩旨在保留与 Query 深度强相关的核心事实，提升信息密度：

| **维度** | **抽取式压缩** | **LLM 生成式压缩** |
| ------ | ------ | ------ |
| 机制 | 从原始切片中直接筛选与 Query 强相关的句子 | 利用轻量级 LLM 对切片做摘要提炼与重构 |
| 优点 | 不改变原文事实，计算速度快，无幻觉风险 | 压缩率高，表达连贯，提炼灵活 |
| 缺点 | 语言连贯性可能受损，无法跨句融合信息 | 增加一次 LLM 调用延迟与成本，存在信息遗漏或幻觉风险 |
| 适用场景 | 对事实准确度要求极高的法律、医疗、金融领域 | 允许语义重组的通用问答与摘要场景 |

### 3.5 上下文重排序与 Token 预算管理

** Lost in the Middle 现象与上下文重排序**
大语言模型对长上下文不同位置的信息处理能力存在内在偏差：开头关注度最高，结尾靠近输出端利用较好，而中间位置的注意力容易下降，关键细节容易被忽略或混淆。
上下文重排序策略将最关键、最直接的证据摆放在上下文的开头和结尾，把次要补充信息存放在中间，以此最大化利用模型的注意力机制。

**Token 预算管理**
上下文窗口是大语言模型单次推理能处理的最大 Token 总额。实际调用中必须建立动态预算管理：
*   **系统提示词**：固定预留空间（通常 1K~2K Tokens）。
*   **对话历史**：按滑动窗口或总结压缩动态分配（通常 2K~4K Tokens）。
*   **用户当前提问**：按实际长度保留（通常 100~500 Tokens）。
*   **检索上下文**：占用剩余可用额度。若超出预算，按重排序优先级截断或二次压缩。

### 3.6 结构化切片后处理范式

结构化切片后处理利用“索引小块、生成大块”的解耦机制，兼顾向量检索高精度与模型理解完整度：
*   **句子窗口后处理**：索引阶段将文本切分为单句作为向量节点，并在节点元数据中保存前后 N 句的文本。向量检索命中单句节点后，由后处理器读取元数据，将单句替换扩展为包含前后 N 句的完整上下文窗口。
*   **父子切块反向召回**：向量库仅存储小粒度（200~400 Tokens）子块用于精确匹配，大粒度（1000~2000 Tokens）父块保存在 Key-Value 存储（如 Redis）中。子块命中后，引擎读取其绑定的 parent_id，去 KV 存储拉取对应的完整父块投喂给模型。

### 3.7 上下文质量评估指标

| **指标** | **核心含义** | **判定方式** |
| ------ | ------ | ------ |
| 上下文召回率（Context Recall） | 回答问题所需的关键事实是否完整进入上下文 | 越接近 100% 越好 |
| 上下文精确率（Context Precision） | 上下文中相关信息的占比 | 相关切片越靠前、无关信息越少，得分越高 |
| 噪声敏感度（Noise Sensitivity） | 存在无关干扰切片时模型产生错误回答的频率 | 取值 0~1，越低代表鲁棒性越强 |

## 4 生成层：从上下文到答案

### 4.1 答案生成的三要素与约束

生成阶段的输入由三部分共同构成：
1.  **检索并精炼后的上下文**：提供事实依据。
2.  **系统提示词（Prompt）**：设定角色、输出格式与作答约束。
3.  **用户原始提问（Query）**：明确核心回答目标。

模型在三者约束下产出答案，上下文排序、引用格式与拒答规则均在这一层进行显式约定。

### 4.2 有据生成、引用溯源与质量评估

*   **有据生成**：要求模型严格依据提供的上下文作答，在证据不足时明确拒答，避免依赖模型参数记忆进行无根据补充。
*   **引用溯源**：将结论绑定到具体来源（文档、章节、页码），便于用户核查与评测验证。

生成质量关键评估维度：
*   **忠实度（Faithfulness）**：评估答案是否完全由给定上下文支撑，衡量模型是否存在虚构。
*   **答案正确性（Answer Accuracy）**：评估答案与标准答案或客观事实的一致程度。
*   **幻觉（Hallucination）**：评估模型是否生成了上下文中不存在且不符合事实的内容。

## 5 工业级检索流水线落地全景架构

### 5.1 离线与在线双流水线架构

完整的工业级 RAG 系统包含离线数据工程线与在线智能查询流水线：

```text
====================== 【离线数据工程流水线】 =================─────
原始文档 ──► 结构化解析/去噪 ──► 父子/句子窗口切片 ──► 文本/上下文 Embedding ──► 向量库与倒排索引

====================== 【在线智能查询流水线】 =================─────
1. 原始提问 Query ──► [查询工程 Layer] (重写/扩展/HyDE/Self-Query)
                         │
2. 意图分发       ──► [智能路由 Router] (分类去往 Vector DB / SQL / KG)
                         │
3. 粗排召回       ──► [双路混合检索] (Dense 向量 + Sparse BM25)
                         │
4. 异构得分融合   ──► [RRF 算法] (按排名位置无量纲融合召回 Top 30)
                         │
5. 精排重排序     ──► [Cross-Encoder Reranker] (深度交叉注意力精选 Top 3~5)
                         │
6. 检索后处理     ──► [上下文扩展/压缩/C-RAG] (句子窗口替换/不相关拦截)
                         │
7. 最终响应生成   ──► [LLM 配合 Context 生成] (带精准 Metadata 溯源引用)
```

### 5.2 核心结论与工程取舍小结

*   **查询重构与路由**：原始 Query 通常不适合直接检索，需在检索前完成改写、扩展、拆解或路径分发。
*   **混合检索与得分融合**：混合检索利用稠密向量互补语义、利用 BM25 互补精确字面；两路得分量纲不同，需采用 RRF 或归一化加权融合。
*   **两阶段精排架构**：Bi-Encoder 负责大范围快速召回（召回得全），Cross-Encoder 负责深度注意力精排（排序得准）。
*   **上下文构建与精炼**：重排序后必须执行去重、压缩、重排序与 Token 预算管理，用最少的 Token 提纯最高密度的证据。
*   **指标闭环验证**：检索看 Recall@K，重排看 MRR 与 NDCG，上下文看 Context Recall 与 Context Precision，生成看忠实度与答案正确性。检索工程的每一步均是在召回率与精确率、输出效果与计算成本之间做出工程取舍。
