## 1 查询工程的目标

### 1.1 原始 Query 的问题

* **表达不完整**：口语化、语法不规范或缺少关键限定条件。
* **上下文缺失**：多轮对话中的代词和省略信息脱离历史后无法独立理解。
* **粒度错配**：问题过具体时缺少背景，过抽象时难以匹配具体切片。
* **复合意图**：一个问题包含多个实体或子需求。
* **语义空间错配**：用户使用短问题表达，而知识库通常以完整文档或答案形式编写。

**核心判断**：
* Query 工程不是简单地“改写得更好看”，而是补全检索条件并选择正确查询路径。
* 改写必须保留原始意图；不确定时应保留原 Query，并与改写版本共同检索。

* **语义检索路径**：输出检索用 Query 与 Metadata Filter。
* **结构化路径**：输出 SQL、Cypher 或 API 参数。
* **错误代价**：改写或路由错误会在检索开始前直接丢失正确证据。
## 2 查询重构技术

### 2.1 查询改写

* **Query Rewrite（查询重写）**：
  * *机制*：语法纠错、指代还原、补全省略信息、融合对话上下文并消除歧义。
  * *输出*：一个更完整、更适合检索的 Query。
  * *限制*：可能新增实体或改变意图；高风险场景保留原 Query 作为回退。
* **Multi-Query（多查询）**：
  * *机制*：从一个问题生成多个不同表达或视角的完整 Query，分别检索后合并结果。
  * *适用*：措辞不唯一、单一路径召回不足。
  * *限制*：增加检索次数；合并结果可能重复或引入语义漂移。
* **Query Expansion（查询扩展）**：
  * *机制*：向查询中加入同义词、相关术语、关键词或其他检索表达。
  * *适用*：用户词汇与知识库术语不一致。
  * *限制*：扩展词过宽会降低精确率，必须用检索评测验证。

**关键区别**：
* **Rewrite**：改成一个更清楚的 Query。
* **Multi-Query**：保留多个独立候选 Query。
* **Expansion**：扩充实体的词汇覆盖范围。
### 2.2 问题拆解

* **Sub-query Decomposition（子问题拆解）**：
  * *机制*：把多实体、多意图问题拆成独立子问题，分别检索后汇总。
  * *示例*：比较 A 与 B 的差异 → 检索 A → 检索 B → 对比证据。
  * *适用*：多跳推理、多实体比较和复合业务问题。
  * *限制*：子问题与原始意图的关系必须在最终合并时保留。
### 2.3 抽象与文档空间转换

* **Step-back Prompting（退一步提示）**：
  * *机制*：先从具体问题上升到一般原理或背景问题，再检索基础知识。
  * *适用*：技术原理、复杂专业问题、法规解释和科学问答。
  * *限制*：抽象问题可能丢失具体限定条件，通常应与原 Query 联合使用。
* **HyDE（假设性文档嵌入）**：
  * *机制*：先让 LLM 生成可能的答案或文档，再用假设文档的向量检索真实知识。
  * *目的*：缩短“问题表示”与“文档表示”之间的语义鸿沟。
  * *限制*：假设内容可能含事实错误、额外信息或偏差，并增加一次 LLM 调用。
  * *判断依据*：HyDE 必须通过同一测试集证明召回收益，不能默认启用。
### 2.4 策略选择

* **指代或上下文缺失**：Query Rewrite。
* **表达方式不唯一**：Multi-Query。
* **专业术语不匹配**：Query Expansion。
* **多实体或多意图**：Sub-query Decomposition。
* **需要先理解一般原理**：Step-back Prompting。
* **问题与答案文档存在明显语义鸿沟**：试验 HyDE。

**默认顺序**：先使用原始 Query 建立 Baseline，再按错误类型逐项增加重构策略。
## 3 查询构建与筛选

### 3.1 Metadata 过滤条件

* **输入**：自然语言 Query，以及知识库可用的时间、作者、部门、密级等字段。
* **输出**：
  * 语义检索词：用于向量或全文检索。
  * 结构化过滤条件：如 `year == 2024 AND category == 'technical'`。
* **作用**：把“查什么”与“只能查哪些数据”分离，缩小候选范围并执行权限约束。
* **执行边界**：过滤可在向量计算前、向量计算后或索引内部完成，顺序取决于数据库能力。
**工程要求**：
* 只允许模型使用预定义的字段、操作符和值域。
* 过滤表达式必须经过解析、类型校验和权限校验。
* 不能把 LLM 生成的原始过滤字符串直接拼接执行。
### 3.2 结构化查询生成

* **Text2SQL**：
  * *机制*：LLM 读取数据库 Schema、字段说明和 Few-Shot 示例，将自然语言转换为 SQL；执行器返回错误后可触发受控重试。
  * *适用*：订单、库存、指标等关系型数据查询。
  * *限制*：可能写错字段、表关联或聚合条件；必须限制只读权限、查询范围和执行资源。
* **Cypher 生成**：
  * *机制*：将自然语言转换为图查询，提取实体关系、路径和多跳拓扑。
  * *适用*：知识图谱中的关联查询。
  * *限制*：依赖图谱 Schema 和实体链接质量；复杂路径查询同样需要语法与权限校验。

**判断依据**：自然语言中同时包含语义描述和硬条件时，优先拆成“语义检索 + 结构化查询/过滤”，再按路由结果组合。
### 3.3 查询路由

**（1）路由维度**

* **数据源路由**：产品文档 → 向量库；订单 → SQL；实体关系 → 知识图谱；实时信息 → Web 搜索。
* **能力路由**：简单 FAQ → 基础向量检索；复杂业务 → Agent 编排；自动操作 → API Tool。
* **Prompt 路由**：按代码、推理、客服等任务领域选择专用系统提示词。

**（2）路由机制**
* **LLM Router**：
  * *判断方式*：大模型执行语义分类、意图解析和多分支规划。
  * *表现*：可处理复杂意图
  * *适用*：复杂业务 Agent、多阶段任务调度。
* **Embedding Router**：
  * *判断方式*：比较 Query 与路由示例的向量相似度。
  * *表现*：复杂意图判断较弱
  * *适用*：高并发、低延迟、领域边界明确的数据源分流。

**（3）工程控制**
* 设置置信度阈值；低置信度时回退到 LLM Router、默认链路或人工确认。
* 先做便宜的 Embedding 路由，再用 LLM 处理困难样本，可控制成本与延迟。
* 记录路由结果、置信度和依据，便于定位错误召回。
* 路由只决定处理路径，不能替代鉴权；最终数据访问仍由底层强过滤保证。
## 4 评测与落地顺序

### 4.1 分层评测

* **检索质量**：Recall@K、Precision@K、MRR、NDCG。
* **上下文质量**：Context Recall、Context Precision。
* **生成质量**：Answer Correctness、Faithfulness。
* **路由质量**：路由准确率、错误数据源比例、回退触发率。
* **系统成本**：额外 LLM 调用、Token、延迟和失败重试次数。

### 4.2 对照实验

1. 建立原始 Query 基线。
2. 固定知识库、Embedding、过滤条件和检索参数。
3. 分别测试 Rewrite、Multi-Query、Expansion、Decomposition、Step-back 与 HyDE。
4. 同时比较召回指标、最终答案、延迟和成本。
5. 按错误类型决定是否组合策略，不能只看总体平均分。

### 4.3 默认落地顺序

1. 原 Query 基线。
2. 指代和上下文缺失时增加 Query Rewrite。
3. 明确数据范围时增加 Metadata 过滤。
4. 出现多数据源时增加查询路由。
5. 仍然召回不足时，再按失败类型增加 Multi-Query、Decomposition 或 HyDE。
