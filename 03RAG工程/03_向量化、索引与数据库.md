## 1 Embedding：从对象到向量

### 1.1 核心原理

* **Embedding**：把文本、图片、音频等对象映射为固定长度的稠密数值数组，如 `[0.16, 0.29, -0.88, ...]`。
* **机制**：由 Embedding 模型编码对象；相似对象在向量空间中距离更近，不相关对象距离更远。
* **工程要求**：知识库和 Query 必须使用同一个 Embedding 模型及一致的前处理方式，否则向量空间不可比较。
### 1.2 相似度度量

* **Cosine Similarity（余弦相似度）**：
  * *机制*：计算两个向量夹角的余弦值。
  * *表现*：值越接近 1，方向越一致；常用范围为 `[-1, 1]`。
  * *场景*：RAG 文本向量检索的常用度量。
* **Dot Product（点积）**：
  * *机制*：计算两个向量的乘积和。
  * *表现*：向量归一化后，点积与余弦相似度等价。
  * *场景*：部分模型和索引针对点积进行优化。
* **Euclidean Distance（欧氏距离）**：
  * *机制*：计算向量空间中的直线距离。
  * *表现*：距离越小，向量越接近。
  * *场景*：需要绝对距离且模型训练目标与之匹配时使用。

**选择依据**：相似度度量要与 Embedding 模型训练方式、向量是否归一化以及索引实现保持一致。
## 2 向量索引类型

### 2.1 常见索引

* **FLAT（暴力搜索）**：
  * *机制*：计算 Query 与所有向量的实际距离。
  * *优势*：100% 召回率，结果最准确。
  * *限制*：速度慢，内存占用大。
  * *适用*：精度要求极高且数据规模较小，如百万级以内。
* **IVF（倒排文件索引）**：
  * *机制*：先聚类划分桶，查询时定位相近桶，再在桶内搜索。
  * *优势*：缩小搜索范围，提高吞吐量。
  * *限制*：相关向量可能落在未搜索的桶中，召回率非 100%。
  * *适用*：高吞吐的大规模数据。
* **HNSW（分层可导航小世界）**：
  * *机制*：多层邻近图，高层快速定位，低层细粒度搜索。
  * *优势*：检索快，召回率高。
  * *限制*：内存占用大，索引构建时间长。
  * *适用*：低延迟在线检索。
* **DiskANN**：
  * *机制*：面向 SSD 等高速磁盘优化的图索引。
  * *优势*：支持远超内存容量的十亿级以上数据并保持低延迟。
  * *限制*：延迟略高于纯内存索引。
  * *适用*：数据规模巨大、无法全部装入内存。
## 3 向量数据库选型

### 3.1 开源与自部署方案

* **Qdrant**：
  * *定位*：Rust 实现，支持 HNSW、复杂 Metadata Filtering 和量化。
  * *适用*：高性能敏感、高并发和中小规模部署。
  * *性能*：内存占用极低，RPS > 4000，保持极低延迟。
* **Milvus**：
  * *定位*：面向大规模向量和高并发场景的分布式数据库。
  * *能力*：多种索引算法、GPU 加速和水平扩展。
  * *适用*：亿级数据、大型企业、高吞吐检索和工业级向量基础设施首选。
* **pgvector**：
  * *定位*：PostgreSQL 向量扩展。
  * *适用*：已有 PostgreSQL 架构、希望减少异构数据库的中小团队。
  * *优势*：复用现有事务、备份、权限和运维体系；运维开销极低，轻量且即插即用。
* **Weaviate**：
  * *定位*：支持 GraphQL API、20+ AI 模块和多模态数据的向量数据库。
  * *适用*：需要图、向量和全文混合检索统一管理的场景。
* **Chroma**：
  * *定位*：本地优先、无外部依赖、零配置的轻量级向量数据库。
  * *适用*：新手入门、原型、小型项目和快速验证。
  * *表现*：安装简单，资源消耗低。
* **FAISS**：
  * *定位*：Facebook AI Similarity Search，高性能相似性搜索与密集向量聚类算法库。
  * *机制*：索引通常保存为本地文件，如 `.faiss` 索引和配套映射文件。
  * *适用*：本地实验、快速原型、批量检索和把索引嵌入自有服务。
  * *关键区别*：FAISS 是算法库，不是带完整数据管理、权限和容灾能力的数据库服务。
### 3.2 商业与云服务方案

* **Pinecone**：
  * *定位*：全托管、Serverless、存储计算分离的向量数据库。
  * *能力*：自动扩展、负载均衡和托管运维。
  * *性能*：99.95% SLA，检索延迟 `<100ms`。
* **Elasticsearch Vector / OpenSearch**：
  * *定位*：在全文检索系统中增加向量检索能力。
  * *适用*：已有 ES / OpenSearch 架构的企业直接升级接入，复用查询、聚合、权限和运维体系。
  * *关键判断*：适合混合检索，不代表向量性能一定优于专用向量数据库。
### 3.3 场景选择

* **原型和小型项目**：Chroma 或 FAISS，优先降低接入成本。
* **已有 PostgreSQL**：pgvector，优先复用现有数据库基础设施。
* **高性能、高并发、中小规模**：Qdrant，重点验证过滤、量化和内存占用。
* **亿级数据和分布式扩展**：Milvus，重点评估集群运维和资源成本。
* **全托管生产环境**：Pinecone，重点评估成本、区域、数据合规和供应商锁定。
* **已有全文检索架构**：Elasticsearch Vector 或 OpenSearch，重点验证混合检索和过滤能力。
### 3.4 选型维度

* **数据规模**：向量数量、维度、原始文本大小和增长速率。
* **检索目标**：召回率、延迟、吞吐和过滤复杂度。
* **写入模式**：批量导入、实时增量、更新频率、删除和重建成本。
* **过滤能力**：预过滤、后过滤、混合查询和多租户隔离。
* **运维能力**：备份、恢复、监控、扩缩容、升级和故障转移。
* **安全合规**：私有部署、权限、加密、审计和数据驻留。
* **成本**：计算、内存、存储、网络、托管服务和团队维护成本。
* **锁定风险**：数据导出、API 兼容、索引格式和迁移成本。

**选择依据**：先用代表性 Query 和知识库数据做同口径测试，再比较召回、延迟、成本和运维复杂度；不要只看公开性能数字。
## 4 Milvus 数据组织模型

### 4.1 核心对象

* **Collection**：
  * *定位*：最高层数据容器，类比关系数据库中的表。
  * *作用*：存放向量、文本或主键、Metadata，并接受查询。
* **Schema**：
  * *定位*：Collection 的字段和类型规则。
  * *作用*：定义主键、向量维度、向量类型和标量字段。
* **Partition**：
  * *定位*：Collection 内部的逻辑划分。
  * *作用*：查询时限定分区，缩小搜索范围。
  * *边界*：一个 Collection 最多支持 1024 个分区。
* **Alias**：
  * *定位*：Collection 的动态入口名。
  * *作用*：新 Collection 建好并完成验证后，原子切换到新别名，避免上层应用修改代码。
* **Entity**：
  * *定位*：一条具体记录。
  * *组成*：主键、向量及标量 Metadata。
