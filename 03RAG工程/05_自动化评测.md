## 1 评估驱动开发的核心理念

### 1.1 靠感觉 vs 数据驱动：为什么需要自动化评测
在传统或初创级的 RAG 系统开发中，开发者往往依赖“随便提几个问题，感觉回答还行”的主观试错方式。这种靠主观感知、缺乏量化标准的开发模式在工程落地中会遇到以下严重痛点：
* **难以感知系统劣化**：调整了切片大小、修改了 Prompt 或更换了 Embedding 模型后，无法准确判断整体系统表现是变好了还是变差了。
* **参数调优盲目**：面对 Top-K 数量、混合检索权重、Rerank 阈值等众多复杂参数，只能凭空猜测，缺乏科学实验依据。
* **线上边界场景崩溃**：遇到复杂问题或偏僻领域词时，缺乏覆盖性的测试用例，上线后频繁发生幻觉或答非所问。

评估驱动开发将传统软件工程的测试思维引入 AI 系统建设中，其核心是把“感觉有效”转化为“数据驱动、量化测量”。

### 1.2 评估驱动开发的三大核心原则
1. **建立量化基线**：在进行任何配置微调、提示词改写或架构重构前，先用标准测试集跑出当前系统的性能基线分数。
2. **两阶段解耦拆控评估**：把 RAG 解耦为检索召回阶段与生成回答阶段，分别测量检索召回率与生成忠实度，精准定位性能瓶颈。
3. **数据驱动迭代**：每一次代码变更、参数调整或提示词更新，都必须重新运行自动化评估脚本，严格根据各项指标的涨跌决定是否上线发布。

### 1.3 RAG 评测整体地图

RAG 的问题可能出在链路的任何一段，所以评测必须按层拆开看：

| 评测层次 | 评什么 | 常用指标 |
| ------ | ------ | ------ |
| 数据质量 | 解析与分块的产物是否完整可切 | 抽样检查、断句与断表比例 |
| 检索 | 该找到的知识有没有被召回 | Recall@K、Precision@K |
| 排序 | 正确结果排得够不够靠前 | MRR、NDCG |
| 上下文 | 送进模型的证据是否相关且充分 | Context Recall、Context Precision、Noise Sensitivity |
| 生成 | 答案是否忠于证据、是否正确 | 忠实度、答案正确性、答案相关性 |

后面各章按这张地图依次展开：第三章讲评测数据，第四章讲指标，第五章讲工作流，第六章讲工具链。

其中数据质量层的判据（抽样检查、是否断句断表）见 [[01_数据解析策略]] 与 [[02_文本分块策略]]。

## 2 评估核心维度与评估三元组

### 2.1 RAG 评估三元组
RAG 评估三元组是一种标准的诊断性评估架构（在 TruLens 等工具中被深度应用），它把系统质量解耦为三个核心维度：

#### 2.1.1 上下文相关性
* **评估目标**：检索器的性能。
* **核心问题**：检索系统召回的上下文内容是否与用户的原始查询高度相关？
* **工程意义**：检索是 RAG 响应流的第一步。如果召回的上下文包含大量无关噪声或缺失关键事实，无论后续生成的语言模型多强大，均无法给出准确答案。

#### 2.1.2 忠实度与可信度
* **评估目标**：生成器的可靠性与抗幻觉能力。
* **核心问题**：模型生成的答案是否完全且严格基于所提供的检索上下文信息？
* **工程意义**：该维度主要用于量化大语言模型的“知识幻觉”程度。高忠实度意味着模型严格遵守上下文事实；若得分较低，说明模型过度自由发挥或引入了外部不实知识。

#### 2.1.3 答案相关性
* **评估目标**：系统的端到端综合表现。
* **核心问题**：最终生成的答案是否直接、完整且有效地解答了用户的原始提问？
* **工程意义**：这是用户最直观的体验维度。回答可能完全基于上下文（高忠实度），但若答非所问或仅回答部分问题，其相关性仍较低。

### 2.2 辅助评估与运维维度
在实际生产落地中，除评估三元组外，还需覆盖以下扩展维度：
* **答案正确性与完整性**：对比标准参考答案，校验核心结论与推导步骤是否完整准确。
* **拒答能力**：当检索上下文不足以回答提问或属于越权/敏感问题时，评估系统是否能精准识别并合理拒答。
* **运维与性能指标**：首字响应延迟、端到端延迟、吞吐量以及 Token 调用成本。

## 3 黄金测试集与冷启动

### 3.1 黄金测试集的三元组结构
黄金测试集是整个评估驱动开发体系的基石，是一组经过严格校验、涵盖典型业务场景且包含标准答案的标注数据。每个标准评估样本均需包含以下 3 个核心要素：
* **问题**：模拟真实用户提问的代表性查询语句。
* **期望检索切片或目标章节**：回答该问题所需的正确文本块标识或文档位置，用于评估检索层。
* **标准参考答案**：由业务专家编写或校验的标准答案，用于评估生成层。

### 3.2 黄金测试集构建方法
* **人工提取与业务标注**：由业务专家从真实的客服日志、用户历史提问、业务手册中提取 20–50 个最具代表性的边界案例与高频问题进行人工标注。
* **LLM 自动化合成测试集**：利用大语言模型对知识库文档块进行逆向解析，快速合成批量测试用例，再经过人工二次清洗与校验。

### 3.3 解决冷启动：合成数据集管道
在系统新建或上线初期，缺少真实用户提问日志（冷启动阶段），可利用强语言模型反向生成「问题、答案、上下文」三元组。

#### 3.3.1 合成管道的四步流程
1. **分步文档切片**：按规则将知识库文档精细切分为语义相对完整的文本块。
2. **多角色多视角提问**：将文本块输入给强语言模型，引导其模拟不同角色和背景的用户，设计三类场景问题：
   * *具体事实题*：例如“基于这段文本，公司报销餐补的上限是多少？”
   * *模糊意图题*：例如“在公司发票抬头填什么？”
   * *跨段落推理题*：例如“比较甲项目与乙项目的交付周期差异。”
3. **提取金标标准答案**：强迫 LLM 严格且仅依据当前 Chunk 提供的语义事实生成标答，严禁联想与自由发挥。
4. **裁判模型质量双检**：引入独立的裁判 LLM 对生成的 QA 对进行一致性与偏离度打分，无情剔除表意含糊、过分直白或答案无法在 Chunk 中闭环的劣质样本，确保评测集的高纯度。

## 4 核心量化指标与计算公式

### 4.1 检索与排序指标
检索质量评估侧重于衡量检索算法与重排算法的有效性：

#### 4.1.1 检索精确率 Precision@k
衡量检索结果的准确性，计算前 k 个返回结果中相关文档的比例：
$$\text{Precision}@k = \frac{\text{检索到的 } k \text{ 个结果中的相关文档数}}{k}$$

#### 4.1.2 检索召回率 Recall@k
衡量检索结果的完整性，计算前 k 个返回结果中包含的相关文档占数据集中全部相关文档的比例：
$$\text{Recall}@k = \frac{\text{检索到的 } k \text{ 个结果中的相关文档数}}{\text{数据集中所有相关的文档总数}}$$

#### 4.1.3 F1 分数
精准率和召回率的调和平均数，用于综合平衡准确性与完整性：
$$F1 = 2 \cdot \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$

#### 4.1.4 平均倒数排名 MRR
评估系统将首个相关文档排在靠前位置的能力。对于单条查询，倒数排名是首个相关文档位置的倒数。MRR 是所有查询倒数排名的平均值，适用于用户仅关注首个正确答案的场景：
$$\text{MRR} = \frac{1}{|Q|} \sum_{q=1}^{|Q|} \frac{1}{\text{rank}_q}$$
其中 $|Q|$ 为查询总数，$\text{rank}_q$ 为第 $q$ 个查询的首个相关文档排名。

#### 4.1.5 平均准确率均值 MAP
综合评估检索精准率与相关文档的排名位置。先计算单条查询的平均准确率 AP，再对所有查询求均值：
$$\text{MAP} = \frac{1}{|Q|} \sum_{q=1}^{|Q|} \text{AP}(q)$$

#### 4.1.6 归一化折损累计增益 NDCG

NDCG 用于衡量多个相关结果的整体排序质量。它先用折损累计增益把每个结果的增益按位置打折，再用理想排序下的最大增益做归一化，使不同查询之间可以横向比较：

$$\text{DCG}_p = \sum_{i=1}^{p} \frac{2^{rel_i} - 1}{\log_2(i+1)}$$
$$\text{NDCG}_p = \frac{\text{DCG}_p}{\text{IDCG}_p}$$

其中 $rel_i$ 是第 $i$ 位结果的分级相关性，$p$ 是截断位置，IDCG 是理想排序下的 DCG。与 MRR 只看第一个正确结果不同，NDCG 能反映"多个相关结果排得好不好"。

#### 4.1.7 指标速查表

| 指标 | 中文名 | 核心问题 |
| ------------------ | ------ | ------------------ |
| Recall@K | 前 K 召回率 | 该找到的知识有没有找到？ |
| Precision@K | 前 K 查准率 | 找到的东西有多少是真相关？ |
| MRR | 平均倒数排名 | 第一个正确结果排得够不够靠前？ |
| NDCG | 归一化折损累计增益 | 多个结果的相关程度和排序是否合理？ |
| Answer Correctness | 答案正确性 | 最终答案对不对？ |
| Faithfulness | 忠实度 | 答案有没有忠实依据上下文？ |
| Context Recall | 上下文召回率 | 答案所需信息有没有被取回来？ |
| Context Precision | 上下文查准率 | 上下文中有多少是有用的？ |

### 4.2 向量 RAG 四大黄金指标
在现代化 RAG 评估框架中，重点关注以下四大核心指标：
* **上下文召回率**：解答问题所需的全部关键知识点是否都被成功召回，衡量检索召回能力。
* **上下文精确度**：检索结果中高相关性切片是否排在最前列、噪声切片占比多少，衡量重排序能力。
* **忠实度**：生成的回答是否完全基于检索到的上下文，严防知识幻觉。
* **答案相关性**：回答是否精准针对用户提问，有无答非所问或冗余信息。

在这四项之外，还可以补一项 **Noise Sensitivity**：衡量系统在使用相关或不相关检索文档时给出错误回答的频率，取值 0~1，越低越好，用于诊断"被噪声带偏"的情况。

### 4.3 响应评估方法
响应评估衡量用户感知的最终输出质量，主要分为两类评估范式：

#### 4.3.1 基于大模型的语义评估
利用中立且高性能的大模型作为评估者，进行深度语义理解与打分：
* **忠实度评估**：将生成的回答拆解为一系列独立的声明，逐一在检索上下文中校验真伪，计算被上下文证实的断言比例。
* **答案相关性评估**：同时分析用户提问与生成的回答，惩罚答非所问、信息缺失或包含无关细节的回答。

#### 4.3.2 基于词汇重叠的经典指标
通过比较生成回答与标准答案之间的 n-gram 词汇重叠度进行打分：
* **ROUGE**：召回率导向，衡量标准答案中的词汇被生成回答覆盖的程度，常用于评估内容完整性。常用变体包含 ROUGE-N（n-gram 匹配）与 ROUGE-L（最长公共子序列）：
$$\text{ROUGE-N} = \frac{\text{匹配的 } n\text{-gram 数量}}{\text{参考答案中 } n\text{-gram 的总数}}$$

* **BLEU**：精确率导向，衡量生成回答中有效词汇的占比，并引入长度惩罚因子防止生成过短语句，适合评估流畅度与准确性：
$$\text{BLEU} = \text{BP} \times \exp \left( \sum_{n=1}^N w_n \log p_n \right)$$

* **METEOR**：兼顾精确率和召回率的调和平均，支持词干与同义词匹配及语序惩罚，评估结果与人类主观判断相关性更高：
$$F_{\text{mean}} = \frac{P \cdot R}{\alpha P + (1 - \alpha)R}$$
$$\text{METEOR} = F_{\text{mean}} \times (1 - \text{Penalty})$$

#### 4.3.3 向量相似度与人工评估

* **向量相似度评估**：把生成回答与参考答案分别向量化，用余弦相似度衡量语义接近程度。它比词汇匹配宽容得多——同义改写不会被判错，但也会放过“语义相近却事实相反”的回答。Ragas 的 Semantic Similarity 指标就是这一类实现。
* **人工评估**：由标注人员按相关性、正确性、可读性等维度打分，或做 A/B 盲评。成本最高、最慢，但它是校验自动指标是否可信的基准，通常用于上线前的抽样验收与指标校准。

#### 4.3.4 评测方法对比与融合策略
| 评估范式 | 核心代表 | 优势 | 局限 | 工程落地定位 |
| ------ | ------ | ------ | ------ | ------ |
| **语义裁判** | Ragas / TruLens / GPT-4o | 具备深层语义与逻辑理解能力，打分与人类主观体验高度一致 | API 成本较高、评估速度慢，可能存在模型偏见 | 用于精细化打分、最终质量把关与复杂推理校验 |
| **经典词汇匹配** | ROUGE / BLEU / METEOR | 确定性强、毫秒级响应、0 成本，客观透明 | 无法理解同义词与意图重构，对语义相同但表达不同的回答误判率高 | 用于 CI/CD 快速批量初筛、字面一致性回归测试 |

在工程实践中，普遍采用“经典指标低成本批量初筛 + 大模型裁判深度打分”的双层复合评估策略；对上线前的关键样本，再用人工评估做最终校准。

## 5 评估工作流与数据闭环

### 5.1 七步评估闭环
一套可复用的工业级 RAG 评估工作流包含以下七个关键步骤：
1. **明确评估目标**：确定本轮验证的假设（如减少幻觉、提升关键召回率或改善拒答表现），根据目标设定针对性指标。
2. **建立评估数据集**：收集真实问题或审核合成数据集，补充问题类型、难度、是否可回答等属性标签。
3. **记录标准化运行数据**：对每条测试样本完整保存输入与运行元数据，通常包含输入与标注数据（问题、参考答案、目标文档 ID）、系统运行结果（检索上下文、最终回答、延迟、异常日志）以及实验元数据（数据集版本、模型版本、Prompt 模板、检索参数）。
4. **运行基线实验**：固定一套可复现的基线配置，获取逐样本打分结果。后续实验严格保持单变量原则。
5. **分层分析结果**：除了观察整体平均分，还需按问题类型、难度、数据源切片分析，重点关注失败样本与低分样本。
6. **分析 Bad Case**：回溯具体问题、检索上下文、模型回答与评分理由，将失败原因归因到：检索缺失、上下文噪声、生成幻觉、答非所问或评估器误判。
7. **设置回归门槛**：将确认后的 Bad Case 沉淀为回归测试集。依据项目基线和业务风险设定门槛（如相对分数变化上限、核心样本零失败等）。

### 5.2 检索优化迭代路径
针对向量检索层的优化迭代，遵循标准的数据闭环五步法：
1. **建立 Baseline 基线**：以最小化的单路纯向量检索作为初始 Baseline，记录各项指标得分。
2. **构建黄金测试集**：整理 20~50 个涵盖典型场景的真实业务问题，标注 Ground Truth 与目标 Chunk ID。
3. **叠加混合检索**：引入 BM25 关键词检索与 RRF 融合机制，对比纯向量基线，量化评估 Recall@K 的提升。
4. **引入精排模型**：加入重排序模块，测试 Precision@K、MRR 及 NDCG 排序指标的变化。
5. **优化切片结构**：引入父子分段或上下文补全，观察端到端忠实度与正确率的提升。

### 5.3 单变量实验与典型实验清单
评估驱动的参数调优严格遵循单变量实验科学流程：
* **测定基线**：在初始配置（如纯向量检索、固定 Chunk Size=500）下运行评估，记录初始 Recall@K、Precision@K 及忠实度分数。
* **单变量假设与实验对比**：保持其他变量恒定，仅调整单一参数。
* **指标回归与版本固化**：仅当新配置在黄金测试集上的综合指标显著优于基线且无明显退化时，才合入主干代码上线。

常见实验清单：

| 实验 | 变量 | 主要观察指标 |
| ------ | ------ | ------ |
| 切片大小实验 | Chunk Size 300 / 500 / 800 | Recall@K、Context Recall |
| 向量模型实验 | Embedding 模型 A / B | Recall@K、Precision@K |
| 检索方式实验 | 纯向量 / 混合检索 | Recall@K |
| 重排开关实验 | Reranker 开 / 关 | MRR、NDCG |
| 查询改写实验 | 改写开 / 关 | Recall@K、端到端正确率 |

切片类实验的参数含义见 [[02_文本分块策略]]，检索与重排类实验的机制见 [[04_查询工程与混合检索重排]]。

### 5.4 A/B 测试

离线指标涨了，不等于线上体验变好。A/B 测试的做法是：把流量随机分成两组，一组跑旧方案、一组跑新方案，在相同时间窗口内对比业务指标（采纳率、引用点击率、追问率等）。

随机分组与"只变一个变量"是它成立的前提。RAG 场景中常用的线上指标包括答案采纳率、引用点击率与负反馈率。

### 5.5 回归测试与 CI/CD

回归测试回答的是“新版本有没有把旧能力弄坏”：

* **固化测试集**：把线上坏例与人工确认过的边界样本沉淀成回归集，随版本一起演进。
* **接进流水线**：把评估脚本挂到 CI 上，每次改动自动跑一遍，指标跌破门槛就阻断合并。
* **守住门槛**：门槛可以设成“核心样本零失败 + 综合指标不退化”，而不是单纯追求分数上涨。

## 6 评估工具链与运维落地

### 6.1 主流评估框架选型
* **Ragas**：专门针对 RAG 系统的开源评估框架，基于 LLM-as-a-Judge 机制自动打分，支持与 LangChain、LlamaIndex 深度集成。
* **DeepEval / TruLens**：支持以 Pytest 单元测试形式将评估规则融入 CI/CD 流程，对 RAG 各流转节点自动运行测试。
* **LangSmith**：LangChain 官方运维评测平台，提供可视化的数据集运行监控与打分跑分功能。
* **DSPy（斯坦福开源）**：前沿提示词编译器，通过算法结合自动化评估测试集，在后台全自动调整、编译 System Prompt 并智能更新检索权重，摆脱人工调优模式。

### 6.2 自建 Python 评估执行器示例
通过自建评估执行代码与 pytest 框架结合，针对不同检索策略自动批量运行黄金测试集并输出结构化对比报告：

```python
import pytest
from typing import Any, Dict, List, Tuple

class RetrievalEvaluationRunner:
    def __init__(self, retrieval_service):
        self.service = retrieval_service

    async def run(self, dataset: List[Dict[str, Any]], strategies: Tuple[str, ...], top_k: int = 5) -> Dict[str, Any]:
        results = {}
        for strategy in strategies:
            total_recall = 0.0
            total_precision = 0.0
            for sample in dataset:
                query = sample["question"]
                target_ids = set(sample["expected_chunk_ids"])

                # 执行指定策略检索
                retrieved_chunks = await self.service.retrieve(query, strategy=strategy, top_k=top_k)
                retrieved_ids = [c.id for c in retrieved_chunks]

                # 计算检索指标
                hits = len(set(retrieved_ids) & target_ids)
                recall = hits / len(target_ids) if target_ids else 0.0
                precision = hits / top_k

                total_recall += recall
                total_precision += precision

            results[strategy] = {
                "Recall@K": round(total_recall / len(dataset), 4),
                "Precision@K": round(total_precision / len(dataset), 4)
            }
        return results

# Pytest 自动化测试集成
@pytest.mark.asyncio
async def test_rag_retrieval_performance(retrieval_service, golden_dataset):
    runner = RetrievalEvaluationRunner(retrieval_service)
    report = await runner.run(
        dataset=golden_dataset,
        strategies=("dense", "sparse", "hybrid"),
        top_k=5
    )
    # 断言混合检索效果必须优于单路纯向量
    assert report["hybrid"]["Recall@K"] > report["dense"]["Recall@K"]
```

### 6.3 可观测性与追踪平台

## 7 小结

* 评测的本质是把“感觉不错”换成可比较的数字：先有基线，再谈优化。
* 评测要按层拆开看：数据质量、检索、排序、上下文、生成，各层有各自的指标。
* 指标分两类用法：经典词汇指标做低成本批量初筛，语义裁判与向量相似度做深度打分，人工评估负责最终校准。
* 单变量实验、A/B 测试与回归测试三者配合，才能既发现提升、又保证线上不退化。
* 所有指标都必须跑在同一份黄金测试集上，否则版本之间无法比较。

> **没有评测的 RAG 迭代，只是在凭感觉换参数。**
