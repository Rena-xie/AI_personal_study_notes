## 1 可观测性

### 1.1 为什么 AI 系统需要可观测性

在传统的确定性软件工程中，系统遵循固定的代码逻辑路径，可以通过标准的日志与指标监控定位故障。然而在大语言模型、检索增强生成以及智能体系统中，系统具备自主规划、多轮推理、非确定性生成与动态工具调用的能力，这带来了极大的工程不确定性。

传统日志无法有效应对以下生产级痛点：

* **黑盒决策定位难题**：当系统返回错误答案、产生幻觉或答非所问时，无法仅凭最终输出判断是 Prompt 不当、模型推理失误、检索未命中，还是工具调用参数格式错误。
* **分层排查需求**：必须具备对数据采集与解析层、切片与检索召回层、重排序层、模型推理层以及工具调用层的分层追踪能力。
* **隐性成本与延迟膨胀**：智能体在运行循环中可能陷入死循环或重复调用工具，导致单次请求的 Token 消耗暴增、首字响应时间与端到端延迟严重推高。
* **上下文窗口退化**：随着多轮对话与工具观察结果的不断累加，Prompt 上下文容易发生杂讯污染或超出 Token 预算。

### 1.2 执行轨迹与链路追踪机制

为实现 AI 系统调用的透明化，可观测性体系通过树状链路精准记录单次请求的完整执行轨迹：一次请求对应一条 Trace，Trace 由若干 Span 组成，每个 Span 代表一个工作单元，例如一次检索或一次工具调用。

树状链路的核心追踪要素包括：

* **系统提示词与动态上下文**：记录传入模型的原始提示词、历史上下文以及运行时动态插值的变量。
* **思考与规划过程**：捕获大模型的思维链推理步骤、条件路由决策以及工具选择逻辑。
* **工具调用与参数**：记录触发的工具名称、传入的 JSON 参数格式及时间戳。
* **工具观察结果**：捕获工具在沙箱环境真实执行后返回的数据，包括成功响应与异常报错信息。
* **Token 消耗与成本**：分步统计 Prompt Token、Completion Token 以及单次循环产生的费用开销。

### 1.3 RAG 全链路 Trace

一次 RAG 请求要拆成八段来记录，任何一段缺失都会让排障变成猜谜：

```
Query → Rewrite → Retrieval → Fusion → Rerank → Context → LLM → Answer
```

* **Query**：用户原始提问、会话 ID、身份与过滤条件。
* **Rewrite**：改写后的查询、扩展出的多路查询、路由决策。
* **Retrieval**：召回的候选与分数、命中的索引与分区。
* **Fusion**：多路结果的融合方式与融合后的排名。
* **Rerank**：重排前后的顺序变化与相关性分数。
* **Context**：最终进入 Prompt 的切片、Token 数与来源元数据。
* **LLM**：模型名、Prompt Token 与 Completion Token、耗时、是否命中缓存。
* **Answer**：输出内容、引用角标、是否被护栏拦截。

### 1.4 日志、指标与追踪的分工

OpenTelemetry 把可观测数据分为三类信号，三者互补而不是互相替代：

* **日志**：记录“发生了什么”的离散事件，适合看异常堆栈与业务打点。
* **指标**：可聚合的数值，适合看趋势与设置告警阈值，如延迟、错误率、成本。
* **追踪**：一次请求的完整调用链，由若干 Span 组成；一个 Span 代表一个工作单元，记录名称、起止时间、父 Span、属性与状态。

### 1.5 可观测性监控核心指标矩阵

生产环境监控需要建立多维度的定量指标矩阵：

* **成本与资源指标**：监控总 Token 消耗与单次调用 Token 数，当发现 Token 突增时触发上下文压缩。
* **性能与延迟指标**：监控首字响应时间与总延迟，拆解瓶颈是在模型生成环节还是外部 API 或工具执行环节。
* **可靠性与异常指标**：监控工具执行错误率与 HTTP 5xx / 429 报错率，当特定工具频繁报错时驱动修正其 Docstring 描述或 Input Schema。
* **任务闭环指标**：监控智能体循环迭代次数，及时触发最大迭代数终止保护，防止进入无限循环。
* **检索质量指标**：在线统计空召回率与 Top-K 命中情况，并结合用户负反馈定位漏召回；指标定义见 [[05_自动化评测]]。

生产级 LLMOps 基础设施需要实现从本地调试到线上监控的全生命周期覆盖。主流平台与协议选型如下：

| 可观测性平台 / 协议 | 底层架构与部署模式 | 核心功能特性 | 适用场景与工程选择 |
| ------ | ------ | ------ | ------ |

## 2 故障定位与根因分析

### 2.1 分层定位法：检索 / 重排 / 上下文 / 生成

答案是错的，但错在哪一层？结合 1.3 的全链路 Trace，可以按下面的顺序排除：

| 现象 | 可疑环节 | 先看什么 |
| ------ | ------ | ------ |
| 知识库里明明有，却答不出来 | 检索 | 召回列表里有没有正确切片；没有就是召回问题 |
| 正确切片召回了，却没进最终候选 | 融合或重排 | 融合前后的排名变化、重排分数是否异常 |
| 进了上下文，答案却没用到 | 上下文或生成 | 上下文是否被截断、是否被无关内容淹没、忠实度评分 |
| 上下文和答案都对不上问题 | 查询工程 | 改写是否偏离原意、路由是否走错路径 |

定位原则是从上游往下游查：上游没给到正确证据，下游再强也救不回来。

### 2.2 根因归因与修复闭环

定位到环节之后，还要把个案沉淀成机制：

1. **记录证据**：保留该次请求的完整 Trace 与输入输出，作为可回放的样本。
2. **归因**：把失败原因归类到检索缺失、上下文噪声、生成幻觉、答非所问或评估器误判。
3. **修复**：按环节改配置——补混合检索、调 Top-K、改切片、改 Prompt 或换模型。
4. **回流**：把样本加入回归集，确认修复有效且没有引入新退化，流程见 [[05_自动化评测]]。

## 3 LLMOps 数据飞轮与质量闭环

### 3.1 在线数据飞轮

在 LLMOps 治理体系中，可观测性、评估与生产落地存在密不可分的递进关系：

* 没有可观测性，评估就是无源之水——缺乏真实运行轨迹。
* 没有量化评估，生产落地就是开盲盒——无法感知 Prompt 修改或模型升级带来的能力倒退。
* 没有生产控制机制，应用就是危险裸奔——死循环、成本暴涨与越权风险。

基于可观测性构建在线数据飞轮的标准闭环路径为：

1. **线上轨迹捕获**：通过 Langfuse / LangSmith 全量记录线上用户真实请求及其轨迹。
2. **坏例筛选与标记**：过滤出用户负反馈、响应超时、抛出异常或得分较低的在线坏例。
3. **测试集回流**：把清洗后的坏例作为边界用例追加进离线黄金测试集。
4. **自动化回归测试**：在 Prompt 重构、模型升级或参数微调时运行回归测试，防止能力倒退。

### 3.2 端到端评估矩阵

评估机制需要覆盖从底层检索到端到端任务完成的全链路：

* **检索层评估**：用 Recall@K、Precision@K、MRR、NDCG 评估检索切片质量，定义见 [[05_自动化评测]]。
* **RAG 三元组评估**：用 Ragas / TruLens 评估上下文相关性、上下文召回率、上下文精确度、生成回答的忠实度与答案相关性。
* **Agent 端到端评估**：评估任务完成率、意图路由准确率、工具 JSON 参数合规率、无效重复调用率以及越权拦截成功率。

### 3.3 技术栈三阶段演进路线

根据业务复杂度、并发要求、预算及研发成熟度，AI 系统技术栈通常经历三个阶段的演进：

| 演进阶段 | 推荐技术栈组合 | 核心特征与工程折中 |
| ------ | ------ | ------ |
| **V1.0（MVP 快速上线）** | Dify / LangChain + pgvector | 搭建速度最快、成本极低、零门槛，快速验证业务可行性。痛点是无法应对复杂非结构化文档，易发生事实漏检与幻觉。 |
| **V2.0（生产级精度优化）** | LlamaParse + Qdrant + Cohere Rerank + Ragas + Langfuse | 升级高精度 Ingestion 解析，启用语义与关键词混合检索及 Reranker 重排序。通过 Ragas 建立量化数据底座基准，结合 Langfuse 进行日常线上监控。 |
| **V3.0（复杂场景 / Agent 化）** | LangGraph / LlamaIndex Workflows + GraphRAG + DSPy 自动调优 | 解决跨文档全局总结、多步推理和图谱关系。大模型通过多轮“自反思 -> 重写 -> 路由 -> 自纠错”实现自适应控制流，并实现 Prompt 算法自动进化。 |

## 4 生产级后端架构与高性能服务

### 4.1 异步非阻塞与流式响应

将 LLM / RAG / Agent 推向生产环境，需要建立高性能的 API 后端架构：

* **FastAPI + asyncio 异步架构**：基于 Python FastAPI 搭建异步非阻塞 IO 服务，防止网络请求或外部工具 API 阻塞主线程，提升系统并发吞吐量。
* **Pydantic v2 强类型契约**：对输入请求与输出响应做严格的强类型校验，避免非法字段进入系统管道。
* **SSE 流式推送**：借助 `StreamingResponse` 暴露流式接口，实现打字机效果的输出，把用户感知的首字响应时间降低至毫秒级。

### 4.2 高并发限流与级联容错

生产级系统必须具备抵御外部供应商 API 不稳定与高并发大流量冲击的抗压能力：

* **并发限流**：在后端服务中使用 `asyncio.Semaphore` 限制单节点与全局的最大并发请求，防止触发供应商的 HTTP 429 报错。
* **模型平滑降级**：当主模型响应超时或抛出 5xx 错误时，捕获异常并自动切换至备用模型继续推理。
* **工具重试与优雅降级**：当工具执行抛出超时或网络异常时，把错误信息回填给模型重试（最多 3 次）；若仍失败则降级为兜底回复，向用户说明原因。

### 4.3 缓存与可扩展性

* **缓存**：对完全相同的请求直接复用结果；对语义高度相似的请求也可以复用，但要设相似度阈值并接受一定的错配风险。缓存同时降低延迟与成本，代价是数据更新后必须主动失效。
* **水平扩展**：无状态的服务层可以横向扩容；向量库、状态存储与队列独立部署，避免成为单点瓶颈。
* **可用性**：为关键链路设置超时与降级策略，供应商故障时保证“慢一点”而不是“直接不可用”。

## 5 有状态运行与长周期控制流

编排层的状态模型与串并行控制见 [[07_系统编排与工具链接]] 第 5 章；本篇侧重生产运行视角——怎么落库、怎么恢复、怎么设边界。

### 5.1 状态持久化快照与断点续传

在生产环境中，复杂任务往往需要长时间执行，单纯依靠内存保存状态无法满足高可用要求：

* **状态持久化快照**：在状态图或工作流的每个节点执行完毕后，把当前共享状态序列化并快照保存到持久化数据库（如 PostgreSQL、Redis）。
* **故障重试与断点续传**：若服务因网络抖动、模型 API 超时或容器重启而中断，重启后读取最近一次快照恢复状态，沿中断节点继续执行，无需从头重跑。

### 5.2 人工介入与审批节点

对于高风险操作，不能完全交由模型自主决定，必须建立确定性的人工介入机制：

* **挂起与等待**：在即将触发数据库写操作、执行删除命令、发送外部邮件或发起支付等高风险动作前自动中断工作流，把系统状态置为“等待审批”。
* **审批与反馈接口**：向管理员呈报拟执行的工具名称与入参，管理员可选择批准、拒绝或修正入参，提交后恢复执行。

### 5.3 终止条件与安全边界控制

为防止智能体陷入死循环或推高 Token 账单，必须设置多重确定性终止保护：

* **明确目标达成**：模型判断当前观察结果已足够回答问题，输出最终答案并显式退出循环。
* **最大迭代次数**：硬性限制循环的最大轮数（如最多 10 轮），超限强行终止。
* **Token 与成本预算上限**：实时监控单次任务的累计 Token 消耗与费用，超过预算硬上限时停止执行。

## 6 生产级安全、隐私与权限

### 6.1 四层护栏纵深防御

为应对提示注入、越狱攻击与敏感信息泄露，系统需要纵深防御：

* **L1 级正则与规则引擎（0~1ms 延迟）**：第一道防线，用正则做敏感数据脱敏（API Key、手机号、身份证），并拦截已知的硬编码注入特征。
* **L2 级轻量语义分类器（10~30ms 延迟）**：用轻量安全模型（如 Moderation API、Llama-Guard）识别变体与语义越狱攻击。
* **L3 级系统提示词与定界符隔离**：在 Prompt 模板中用 `<context>` 与 `<question>` 等标签，把系统控制逻辑与外部不可信输入严格隔开。
* **L4 级输出质检**：在响应返回前端前做二次安全审查与事实性校验，拦截凭空捏造的幻觉与违规言论。

### 6.2 代码与命令执行沙箱隔离

针对需要执行 Python 代码或 Shell 命令的智能体，必须做环境层面的严格隔离：

* 严禁在宿主机直接执行任何模型生成的代码或命令。
* 代码执行逻辑必须部署在轻量级容器、WebAssembly 或受限沙箱环境（如 Firecracker、E2B）中，并设置单次执行超时与资源限制（CPU、内存、网络白名单）。

### 6.3 隐私与敏感数据

个人身份信息指可用于识别特定个人的信息，如姓名、手机号、身份证号、银行卡号与邮箱。RAG 系统有两条泄露路径：知识库本身含有这类信息，以及用户提问里夹带后被写进日志。

* **识别与脱敏**：在入口与出口两侧做检测，命中即脱敏（掩码或替换），不要等进了日志再处理。
* **访问范围**：按最小必要原则限制谁能检索到哪些切片，与 6.5 的权限过滤共用同一套元数据条件。
* **留存策略**：日志与轨迹里的原文按合规要求设置保留期，到期删除，避免长期堆积成为泄露源。

### 6.4 不可信内容与数据投毒

检索回来的内容本身可能就是攻击载荷，典型风险有两类：

* **间接提示注入**：恶意文档里藏着“忽略以上指令”之类的语句，被检索进上下文后触发越权操作。防护靠 6.1 的定界符隔离与输出质检。
* **数据投毒**：攻击者在知识库中植入错误或误导性内容，让系统长期输出被污染的事实。防护靠入库审核、来源可信度标记与定期抽检，抽检做法见 [[01_数据解析策略]]。

### 6.5 基于 RBAC 的企业级数据权限隔离

在企业级数据合规要求下，RAG 知识库检索必须与企业的权限管理体系无缝打通：

1. **身份认证**：用户通过 IAM 或 OIDC 完成统一身份认证。
2. **角色解析**：权限系统解析该用户的角色及其数据权限标签。
3. **动态拼接过滤条件**：把权限条件转换为数据库元数据过滤器，例如 `{"department": "HR", "clearance_level": 3}`。
4. **底层强过滤**：向量数据库在底层计算相似度的同时强制执行过滤，仅返回该用户有权查阅的切片，从根源防止越权泄露。

### 6.6 元数据打标与引用溯源

为建立可追溯的生成质量：

* 在数据清洗与切片阶段，为每个 Chunk 注入来源、章节、页码等元数据。
* 在 Prompt 模板与输出模型中加入强约束，要求模型在回答中或末尾标注引用角标（如 `[Chapter 3, Page 105]`），实现页码级的可视化溯源。

## 7 版本与知识库运维

知识库不是一次建好就不再变动的，它需要持续更新；每次更新都要回答“改什么、重算什么、怎么切换”。

### 7.1 文档版本与增量更新

* **文档版本**：每份文档保留版本号与更新时间，更新时先解析新版本再决定替换范围，避免新旧内容混在同一份索引里。
* **增量更新**：只对发生变更的分片重新解析、重新向量化（做法见 [[02_文本分块策略]]），其余分片保持不动，把更新成本压到与变更量成正比。

### 7.2 向量与索引版本

* **向量版本**：更换向量模型后，库中所有存量向量都失去可比性，必须全量重算，见 [[03_向量化原理及选型]] 的 2.4。
* **索引版本**：索引参数变化同样需要重建索引；重建期间用别名原子切换，避免服务中断。

### 7.3 删除、失效与重建索引

* **删除与失效**：文档下架时不能只删原文，还要同步清理向量与缓存，并对历史引用做失效标记。
* **重建与灰度**：全量重建耗时长，建议新索引先跑离线评测（见 [[05_自动化评测]]），指标达标后再切流量。

## 8 小结

* 可观测性是 AI 系统能被维护的前提：一次请求要能在 Trace 里完整回放，日志、指标、追踪三者缺一不可。
* 排障要按链路分段定位、从上游往下游查；找到原因后把样本回流成回归集。
* LLMOps 的闭环是“线上轨迹 → 坏例 → 测试集 → 回归”，技术栈按 V1.0 到 V3.0 逐步演进。
* 生产化要解决四件事：后端扛住并发、控制流可中断可恢复、安全隐私有纵深防线、知识库能增量更新与安全重建。
* 越是自主的系统，越需要确定性的边界——终止条件、审批节点与权限过滤都属于这一类边界。

> **可观测性与运维能力，决定了 RAG 系统能跑多久，而不只是能跑多好。**
