## 1 向量化原理与相似度度量

### 1.1 Embedding 核心原理与利弊
Embedding 是一种将真实世界中的复杂、高维数据对象（如文本、图片、音频等）转换为数学上易于处理的、固定长度的一维数值数组（即稠密向量）的技术。由 Embedding 模型接收数据对象后，将其映射为形如 [0.16, 0.29, -0.88, ...] 的向量表示。

在 Embedding 构建的连续几何向量空间中，语义上相似的数据对象，其对应向量在几何空间中的距离更近；而语义不相关的对象，其向量距离更远。向量不是随机数值的堆砌，而是对数据深层语义与上下文关系的数学编码。

Embedding 不保留字面，只保留语义：
* **优势**：同义词、改写句、跨语言表达都能实现精准匹配。
* **代价**：精确编号、产品型号、函数名这类必须字面对齐的内容容易被忽略。

### 1.2 三种相似度度量指标
为了在数学上精确衡量高维向量间的距离或相似度，通常使用以下三种物理指标：
* **余弦相似度**：通过计算高维空间中两个向量夹角的余弦值，评估语义方向的一致性。取值范围在 [-1, 1] 之间，值越接近 1 说明方向越一致、语义越相似。这是 RAG 系统中最常用的度量方式。
* **点积**：计算两个向量的乘积和。当向量经过归一化处理（模长为 1）后，点积在数学上完全等价于余弦相似度。
* **欧氏距离**：计算两个向量在空间中的绝对几何直线距离。距离越小，说明两者的空间接近度越高、语义差异越小。

### 1.3 RAG 语义检索通用工作流
Embedding 是 RAG 系统中语义检索的数学基石，其标准通用流转管道包含四个阶段：
1. **离线索引构建**：将知识库文档进行物理切分后，使用 Embedding 模型将每个文档块转换为向量，存入向量数据库中。
2. **在线查询检索**：当用户提出问题时，使用同一个 Embedding 模型将用户输入的 Query 转换为查询向量。
3. **相似度计算**：在向量数据库中，计算问题向量与数据库中所有文档块向量的相似度得分。
4. **召回上下文**：选取相似度最高的 Top-K 个文档块作为补充上下文，与原始问题一同拼接后送给大语言模型生成答案。

### 1.4 本篇在 RAG 链路中的位置
* **上游**：Chunk 是向量化的单位，分块质量决定向量表征的上限，见 [[02_文本分块策略]]。
* **本环节**：用同一个 Embedding 模型，把知识库 Chunk 与用户 Query 映射到同一向量空间。
* **下游**：检索引擎在这个空间里找最近邻，再经融合与重排产出上下文，见 [[04_查询工程]]。

## 2 向量数据库的数据模型与关键技术

### 2.1 存储三要素
在向量数据库中，单条知识记录必须完整且强绑定以下三个部分：
1. **知识文本**：切片后的原始文本内容。
2. **语义向量**：通过 Embedding 模型计算得到的稠密数值数组。
3. **元数据**：描述切片的附加 JSON 对象（包含文件名、章节路径、页码、权限标签、创建时间等）。

### 2.2 核心技术机制
* **向量索引**：用于加速高维向量空间匹配的高级算法结构（如 HNSW 图结构，即分层可导航小世界），避免全量暴力计算。HNSW 通过构建多层“邻居图”，让 Query 不需要遍历所有向量，而是从粗到细地快速接近目标向量。
* **近似最近邻搜索**：在高维空间中，牺牲极小比例的数学精度来换取成百上千倍的检索速度提升，是毫秒级高并发查询的物理支撑。
* **元数据过滤**：支持在向量相似度计算前或计算后，根据附加的标量属性执行硬性条件过滤。
* **数据分区**：在大规模向量存储中，将数据划分为逻辑或物理分区，缩小单次检索的搜索域，大幅提高查询性能与吞吐量。
* **权限隔离**：多租户与多业务线的数据隔离依赖“身份认证 ➔ 角色解析 ➔ 元数据过滤条件 ➔ 底层强过滤”的链路，详见 [[06_LLMOps与可观测性运维]]。

## 3 向量数据库选型矩阵与场景化建议

### 3.1 开源与自部署方案
* **Qdrant**：基于 Rust 语言编写，内存占用极低，检索性能优异。原生支持复杂的元数据过滤语法、HNSW 索引与二进制量化技术，性能可达 RPS > 4000 且保持极低延迟，非常适合性能敏感、高并发及中小规模部署。
* **Milvus**：专门针对亿级以上大规模向量、高并发分布式场景打造的开源数据库，支持 GPU 加速与多种索引算法，具备极强的水平扩展能力，是大型企业构建工业级向量基础设施的首选。
* **pgvector**：PostgreSQL 关系型数据库的开源向量扩展插件。非常适合已有 PostgreSQL 架构的中小团队，无需引入新的异构数据库，运维开销极低，轻量且即插即用。
* **Weaviate**：支持 GraphQL API 的 AI 集成向量数据库，提供 20+ AI 模块与多模态支持，支持图、向量与全文混合检索。
* **Chroma**：轻量级开源向量数据库，采用本地优先设计，无外部依赖，零配置安装，低资源消耗，适合新手入门、原型开发与小规模应用。
* **FAISS**：Facebook AI Similarity Search，高性能相似性搜索与密集向量聚类算法库。本质上是一个算法库，将索引直接保存为本地文件（一个 .faiss 索引文件和一个 .pkl 映射文件），无需运行数据库服务，轻量高效，极适合快速原型设计与本地应用。

### 3.2 商业与云服务方案
* **Pinecone**：完全托管的云原生 Serverless 向量数据库，采用存储计算分离架构，提供自动扩展与负载均衡，保证 99.95% 的 SLA，实现低延迟（<100ms）检索，特别适合企业级生产环境。
* **Elasticsearch Vector / OpenSearch**：传统全文检索大厂的向量化扩展方案，极度适合已有 ES 搜索架构的企业直接升级接入。

## 4 工业级向量数据库物理结构模型

### 4.1 Milvus 数据组织核心概念
以 Milvus 为例，工业级向量数据库的数据组织包含以下核心概念：
* **Collection**：集合，相当于关系型数据库中的一张表，是存储、管理和查询向量及相关元数据的最高层容器。
* **Schema**：模式，定义 Collection 的数据结构与字段规则，包含主键字段、向量字段及标量字段。
* **Partition**：分区，Collection 内部的逻辑划分。在查询时指定特定分区搜索，可大幅减少数据扫描量，显著提升检索速度。一个 Collection 最多支持 1024 个分区。
* **Alias**：别名，Collection 的动态“昵称”。支持在不修改上层应用代码的前提下，将别名原子性地从旧 Collection 切换至新 Collection（例如 v1 到 v2），实现数据更新与索引重构时的无缝升级。
* **Entity**：实体，相当于数据库中的一条具体记录，包含主键、向量及元数据。
