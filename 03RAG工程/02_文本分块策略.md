## 1 文本分块基础

### 1.1 分块的定义与作用

* **Chunk（分块）**：后续向量化和检索的基本知识单元。
* **输入**：Markdown 或 JSON 元素及其元数据。
* **核心约束**：解析阶段保留的标题、段落、表格和代码结构，直接决定分块能用的语义边界。

**为什么需要分块**：

* **突破输入限制**：Embedding 模型和 LLM 都存在单次 Token 上限。
* **减少语义稀释**：长文档混合多个主题，整篇向量化会降低与具体问题的匹配精度。
* **控制成本与延迟**：小块检索减少送入 LLM 的无关 Token，并缩短首字延迟。
* **减少无关信息**：提供聚焦上下文，降低无关内容诱发错误回答的概率。

### 1.2 分块大小的权衡

* **过小**（如小于 100 Tokens）：
  * *风险*：截断句子和限定条件，导致语义不完整。
  * *结果*：检索命中局部词句，却缺少解释问题所需的上下文。
* **过大**（如大于 1000 Tokens）：
  * *风险*：混入多个主题，造成语义稀释。
  * *结果*：向量匹配变模糊，生成阶段也可能忽略中间信息。
* **常用起点**：
  * 分块长度：约 256～512 Tokens。
  * 重叠长度：约为分块长度的 10%～20%。
  * 大块上下文：约 1000～2000 Tokens。
  * 小块检索单元：约 200～400 Tokens。
* **参数边界**：上述数字是可调起点，不是通用最优值；应按文档结构、Embedding 模型、查询类型和评测结果调整。
* **查询粒度**：事实查找适合小块，解释型问题通常需要更完整的上下文。

### 1.3 三个核心目标
* 块越小 → 匹配更聚焦 → 上下文更容易破碎。
* 块越大 → 上下文更完整 → 噪声和成本更高。
* 分块策略本质上是在“语义完整、检索精度、上下文效率”之间取舍。
## 2 切块方法与策略

### 2.1 基础切片方法

* **固定长度切片**：
  * *机制*：按固定字符数或 Token 数强制切分，如 300、500 或 800 Tokens。
  * *优势*：实现简单，块大小稳定。
  * *限制*：容易截断句子、表格和代码。
* **重叠窗口切片**：
  * *机制*：相邻块保留 10%～20% 的重叠内容。
  * *优势*：降低边界附近的语义丢失。
  * *限制*：重复内容增加存储、Embedding 和召回成本。
* **结构切片**：
  * *机制*：按 Markdown 标题或自然段落切分。
  * *优势*：优先保持章节、主题和段落完整。
  * *限制*：依赖上游解析质量；章节本身超长时仍需递归降级。
### 2.2 递归切分

* **核心思想**：按分隔符优先级从强到弱递归切分，尽量保留段落和句子边界。
* **执行方式**：先用大边界切分；块仍超限时，再降级到更细的分隔符。
```text
输入大文本
   │
   ▼ 优先按双换行符 "\n\n" 切分（自然段落）
   │
   ▼ (若单个块超过 chunk_size)
   降级按单换行符 "\n" 切分（句子/行）
   │
   ▼ (若单行仍超过 chunk_size)
   降级按空格 " " 切分（单词）
   │
   ▼ (若无空格可切)
   最终按单个字符物理截断
```

**参数与中文本地化**：
* `chunk_size`：目标分块的最大长度，单位为字符或 Token。
* `chunk_overlap`：相邻块保留的重叠长度。
* `separators`：按优先级从高到低排列的分隔符。
* **中文适配**：在默认分隔符之外加入句号、分号、感叹号和问号等中文标点，避免只按英文空格和换行切分。
* **限制**：递归切分仍以字符或规则为主，不保证每个块的主题完整。

### 2.3 基于语义的分块策略

* **核心思想**：用 Embedding 比较相邻文本的语义距离，在主题转折处切分。
* **适用**：主题变化自然、段落长度不均且结构标记不可靠的文本。
* **代价**：切分前需要批量计算句子向量，额外消耗时间和算力。

**处理流程**：
* **原子拆分**：按句子或更细粒度表达单位拆分。
* **句子向量化**：为单句或滑动句子组生成 Embedding。
* **距离计算**：相邻向量距离小表示主题接近，距离大表示可能发生转折。
* **阈值判定**：距离超过阈值时设置切分点。
* **组合出块**：把两个切分点之间的句子组合成 Chunk。

**阈值确定方式**：
* **百分位数法**：
  * *机制*：按全篇距离分布取百分位阈值，如只切前 5% 的高距离点。
  * *适用*：整体结构较统一、希望自适应文档分布。
  * *限制*：长文档的主题密度仍可能不均。
* **标准差法**：
  * *机制*：使用 `Mean + N × Std` 作为阈值。
  * *适用*：希望过滤一般波动，只保留明显异常点。
  * *限制*：距离分布偏斜时不一定稳定。
* **四分位距法**：
  * *机制*：用中位数和 IQR 识别异常高距离。
  * *适用*：长短混杂、排版不均匀的文本。
  * *限制*：仍依赖距离分布和分位数参数。
* **绝对阈值法**：
  * *机制*：直接指定距离阈值，如 0.25。
  * *适用*：实现简单、已有固定 Embedding 模型和业务经验。
  * *限制*：阈值与模型、文本和距离度量强相关，不能跨模型直接复用。

**工程权衡**：
* **优势**：主题聚焦、块大小自适应，有机会减少“结论与前提被拆开”。
* **成本**：需要全量或抽样 Embedding，批处理吞吐和延迟更高。
* **边界**：长段连续论述可能形成超大块，高频转折可能产生碎片块。
* **保护措施**：设置最小块、最大块和相邻块合并规则，避免尺寸失控。

### 2.4 父子切块

* **核心思想**：用小块做精准检索，用大块提供完整生成上下文。
* **检索路径**：Child 命中 → 读取 `parent_id` → 从文档库取 Parent → 送入 LLM。

```text
Parent 原文
→ 切分为 Child
→ 仅计算 Child 向量并写入 VectorDB
→ Child 元数据写入 parent_id
→ Parent 原文写入 DocStore / Redis

Query
→ 向量命中 Child
→ 按 parent_id 取回 Parent
→ 将 Parent 作为回答上下文
```

**三个核心组件**：
* **双轨存储**：向量库存 Child 向量；KV 文档库存 Parent 原文。
* **关系映射**：Child 的 Metadata 写入 `parent_id`。
* **检索重定向**：Retriever 命中 Child 后扩展为 Parent，再送入 LLM。

**块粒度**：
* **Parent**：较大章节或段落，如 1000～2000 Tokens，保留完整上下文。
* **Child**：父块内的小片段，如 200～400 Tokens，负责精准向量匹配。

```text
Parent Chunk（1000～2000 Tokens）
├── Child 1 → Embedding → VectorDB
├── Child 2 → Embedding → VectorDB
└── Child N → Embedding → VectorDB

Child Metadata.parent_id → Parent ID
```

* **优势**：Child 提高匹配精度，Parent 补足生成上下文。
* **限制**：Parent 过大时会重新引入噪声；Child 与 Parent 需要保持版本和删除一致性。
* **工程判断**：只有“小块命中、大块回答”确实优于单级切块时才值得增加双轨存储和映射复杂度。

### 2.5 句窗口切分

* **核心思想**：用中心句做向量匹配，用邻近句子恢复上下文。
* **索引内容**：只计算中心句的 Embedding。
* **窗口内容**：前后 N 句写入 Metadata，不参与 Embedding。
* **检索流程**：命中中心句 → 读取窗口文本 → 替换节点 → 送入 LLM。
## 3 切块策略组合与落地案例

### 3.1 生产环境常用组合

* **结构化父子切块**：
  * *场景*：规章制度、合同、说明书、API 文档和法规。
  * *机制*：标题或版面识别确定 Parent → 递归切分生成 Child → 双轨存储。
  * *目标*：Parent 保结构，Child 保检索粒度。
* **带 Metadata 的递归字符切分**：
  * *场景*：通用知识库、博客、自由格式文本和快速冷启动。
  * *机制*：递归切分 → 注入标题、章节或全局摘要 Metadata。
  * *定位*：通用 Baseline，优先实现、优先评测。
* **句窗口切分**：
  * *场景*：客服问答、参数查询和单句事实检索。
  * *机制*：中心句做向量匹配 → 命中后扩展前后 N 句。
  * *示例*：查询“产品的最大承重是多少” → 命中参数句 → 补入前后解释。

### 3.2 保持简单切分策略的场景条件

* **文档量小或结构统一**：递归切分加 Metadata 通常够用，语义切块主要增加算力成本。
* **瓶颈不在分块**：专有名词漏召回或完全未命中时，先检查检索、过滤和 Reranker，而不是继续细分 Chunk。
* **没有评测手段**：无法量化 `Recall@K`、答案正确性和 Faithfulness 时，引入父子、句窗口等复杂结构会增加排障难度。

**落地顺序**：

1. 先按标题和段落做结构切分。
2. 超长章节再递归降级。
3. 注入标题路径、页码和来源 Metadata。
4. 用评测结果决定是否加入语义切块、父子切块或句窗口。
