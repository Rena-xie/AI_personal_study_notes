## 1 文本分块的基础知识

文本分块是将长文档拆分为多个相对完整知识单元的过程，其中分块（Chunk）是后续向量化与检索的基本单位。分块的处理对象是上游环节输出的结构化文档（Markdown / JSON 元素 + 元数据）。解析阶段保留的标题层级、表格与代码块结构直接决定了分块能够切分的边界位置。

### 1.1 为什么需要文本分块

1. 突破模型上下文限制：大语言模型与向量嵌入模型均存在单次输入的最大 Token 限制，长文档无法一次性直接输入模型。
2. 提高向量检索精准度：长文档包含过多混合主题，直接向量化会导致语义稀释；分块后每个片段语义聚焦，更容易在向量空间与用户提问精准匹配。
3. 降低调用成本与响应延迟：将庞大原文档全部传入大语言模型会大幅增加 Token 费用，并显著增加首字响应时间与推理延迟。精准匹配小块可减少不必要的上下文输入。
4. 减少模型幻觉：提供聚焦且高度相关的背景知识，能让大语言模型准确基于事实回答，避免引入无关信息引发脑补。

### 1.2 分块大小的影响与权衡

分块大小直接决定了知识检索和生成质量的上限，过大或过小都会带来显著的工程风险：

* 分块过小（如小于 100 Tokens）：导致语义断裂与上下文缺失，句子被硬生生截断，丢失关键限定条件，容易造成模型断章取义或理解错误。
* 分块过大（如大于 1000 Tokens）：包含过多无关信息引发语义稀释，降低向量检索相似度得分，极易触发大语言模型的中间遗忘与注意力散射。

### 1.3 决定分块大小的三大核心维度

1. 文本本身的结构特征：代码、法律条文、学术论文或聊天记录对上下文连贯性要求各不相同，需结合段落、标题等自然分隔符进行设计。
2. 向量模型的最佳吞吐区间：不同向量模型在不同文本长度下的表征能力存在差异，通常 256~512 Tokens 是平衡性能与精度的常用区间。
3. 重叠度设置：为防止重要信息恰好落在分块边界而被割裂，通常设置 10%~20% 的重叠区域（约 50~100 Tokens），保持相邻分块间的语义连贯。重叠度是降低边界信息损失的工程手段，但重叠度过大会产生大量重复内容，导致存储增加、向量计算开销上升、检索结果重复、上下文空间浪费与成本增加，因此重叠度本身是一个需要调优的参数。

### 1.4 分块的核心目标与权衡关系

分块的核心目标是在以下三个维度之间寻找平衡：

* 语义完整性：每个分块都应尽量是一个自洽的知识单元，包含完整的主谓语与限定条件，避免断章取义。
* 检索粒度：分块是向量检索的最小单位，粒度过粗会稀释语义，粒度过细会丢失上下文，需要与提问类型高度匹配。
* 上下文效率：进入大语言模型上下文的每个 Token 都应尽量与当前问题相关，减少噪声对注意力与成本的挤占。

上述三个目标存在互相制约关系：粒度越细，检索越准但上下文越破碎；粒度越粗，上下文越全但噪声越多。分块策略的选择，本质上是在这三者之间寻找平衡。

## 2 切块方法与策略

### 2.1 基础切片方法

* 固定长度切片：按固定的 Token 或字符数量（如 300、500 或 800 Tokens）强行切分。
* 重叠窗口切片：在相邻切片之间保留 10%~20% 的重叠区域，防止完整的句子或核心语义在切分边界被割裂。
* 结构切片：依据 Markdown 标题（一级标题、二级标题、三级标题）或天然段落进行划分，保证每一个分块在逻辑上是一个完整的讨论主题。

### 2.2 递归切分

递归切分旨在最大程度保持段落与句子的语义完整性，其核心在于维护一个具有优先级排序的分隔符列表。默认降级切分层级如下：

```text
输入大文本
   │
   ▼ 优先按双换行符 "

" 切分 (自然段落)
   │
   ▼ (若单个块超过 chunk_size)
   降级按单换行符 "
" 切分 (句子/行)
   │
   ▼ (若单行仍超过 chunk_size)
   降级按空格 " " 切分 (单词)
   │
   ▼ (若无空格可切)
   终极按单个字符 "" 强行物理截断
```

#### 2.2.1 中文本土化改造

默认分隔符针对英文设计，处理中文时必须自定义 separators 参数，加入中文句号（。）、分号（；）、感叹号（！）等标点符号，避免中文句子在中间被意外切断。

#### 2.2.2 核心控制参数

* chunk_size：目标分块的最大长度（字符数或 Token 数）。
* chunk_overlap：相邻分块之间重叠保留的长度，通常为 chunk_size 的 10%~20%。
* separators：自定义分隔符列表，按优先级从高到低排列。

### 2.3 基于语义的分块策略

基于语义的分块策略利用向量模型实时计算相邻句子之间的语义相似度，当发现上下文语义发生剧烈变化或主题转折时才触发切分。

#### 2.3.1 工作机制与计算流程（5 步链条）

```text
原始文档 ──> [1. 拆分为单句] ──> [2. 计算句向量] ──> [3. 计算相邻句余弦距离] ──> [4. 阈值判定转折点] ──> 组合成 Chunk
```

1. 原子句拆分：将原始长文本按最细粒度的表达单位（通常是单句话，按句号或感叹号）切开。
2. 句子向量化：使用 Embedding 模型为每一个句子（或包含上下文的滑动句子组）生成对应的语义向量。
3. 距离与相似度计算：计算相邻两个句子向量之间的余弦距离。距离小说明前后讨论同一个主题，距离大说明发生主题转折。
4. 阈值判定：设定语义转折临界点（阈值）。只要相邻句子的语义距离高于该阈值，就在此处划定切分点。
5. 组合出块：将处于两个切分点之间的所有句子组合成一个独立的分块。

#### 2.3.2 四种阈值确定策略

* 百分位数法（工程最常用）：计算整篇文档中所有相邻句子距离的分布，设定百分位数（如 95%）。只有距离排在最前 5% 的剧烈变动点才会被切开，适合整体结构统一的文档。
* 标准差法：以所有距离的平均值加上 N 倍标准差（如 Mean + 1.5 * Std）作为切割线，抗噪声能力较强。
* 四分位距法：利用中位数和四分位距寻找异常高距离点，适合长短混杂、排版不均的文本。
* 绝对阈值法：人为硬性指定一个距离数值（如 0.25），超过即切分。

#### 2.3.3 优缺点分析与工程权衡

* 核心优势：
  * 语义纯度极高：每个分块都是主题独立且完整的知识单元，不会将结论与引言强行切断。
  * 自适应分块大小：探讨同一个概念时保留为大分块，频繁切换主题时自动切成小分块。
  * 显著提升检索精度：存入向量库的片段主题聚焦，大幅减少语义稀释导致的召回率下降。
* 缺点与代价：
  * 计算开销大、延迟高：切分前必须对整篇文档的所有句子运行 Embedding 推理，处理海量文档时消耗大量 API 额度或 GPU 算力。
  * 块尺寸不可控：遇到缺乏转折的长文本时可能产出超大分块，遇到频繁跳跃的文本时会产出大量微型分块（工程上需配置最小与最大字符数保护边界）。

### 2.4 父子切块

父子切块不仅是字符串切分，而是一套涵盖存储、映射与检索拦截的系统级架构：

```text
               ┌────────────────────────────────────────────────────────┐
               │              父子切块架构 (Parent-Child)                │
               └────────────────────────────────────────────────────────┘
                                           │
       ┌───────────────────────────────────┼───────────────────────────────────┐
       ▼                                   ▼                                   ▼
【1. 双轨存储架构】                 【2. 主外键关联机制】         【3. 检索拦截与重定向】
向量库 (VectorDB)                   Child 节点中写入                向量检索命中Child
   └── 存 Child (小块)               Metadata:                不直接送给 LLM，
文档库 (DocStore/Redis)           {"parent_id": "P_001"}    而是拿着 parent_id 
   └── 存 Parent (大块)                                     去 DocStore 换取 Parent
```

#### 2.4.1 三大核心组件与机制

1. 双轨存储设计：系统同时挂载两个数据库：向量数据库（存 Child 向量，用于高精度计算）和 Key-Value 文档数据库（如 Redis、LevelDB，专门存 Parent 原文）。
2. 关系型映射：切片后，系统为 Child 和 Parent 建立主外键式的 parent_id 绑定关系。
3. 检索劫持与扩展：用户提问时，向量数据库算出的最高分结果是 Child；但 Retriever 引擎拦截该结果，解析出 parent_id 后去 KV 数据库以键换值，将真正的 Parent 提取出来喂给大模型。

#### 2.4.2 块粒度与检索召回链路

* 父块与子块粒度：父块将文档切分为较大的段落或章节（如 1000~2000 Tokens），保留完整的上下文信息；子块在父块内部进一步细分为较小的片段（如 200~400 Tokens），专注于表达小粒度的具体语义。

```text
[文档输入] ──> 切分为 [父块 Parent Chunk (1000~2000 Tokens)]
                      │
                      ├──> 细分为 [子块1] ──> 计算 Embedding 存入向量库
                      ├──> 细分为 [子块2] ──> 计算 Embedding 存入向量库
                      └──> 元数据注入 parent_id 指向 父块 ID

[用户提问 Query] ──> 向量检索匹配命中 [子块 Child Chunk]
                             │
                             ▼ (通过 parent_id 反向召回)
                      提取完整 [父块 Parent Chunk] 投喂给 LLM
```

1. 在向量数据库中，仅对高精度的子块（Child Chunk）计算 Embedding 并进行精准向量匹配。
2. 当某颗子块命中后，系统通过元数据中的 parent_id 关联映射，反向将该子块对应的完整父块（Parent Chunk）提取出来，投喂给大模型作为回答上下文。
3. 这种机制既保证了检索阶段的高命中率，又保证了生成阶段上下文的完整连贯。

### 2.5 句窗口切分

句窗口切分将每个句子节点作为一个细粒度检索单元，因此它的 Embedding 表征的是这个中心句；周围窗口保存在 Metadata 中，在检索后再恢复上下文。window metadata 不提供给 Embedding 模型，而是在检索后替换节点，再交给大语言模型。

句窗口切分与 Overlap 的区别：

* Overlap：在切分阶段让相邻分块复制一段字符，重叠内容会参与 Embedding，也会占用向量库存储。
* 句窗口：索引时只对中心句计算向量，前后 N 句只写进 Metadata、不参与 Embedding；命中后再把窗口文本拼回上下文交给大语言模型。

## 3 切块策略组合与落地案例

### 3.1 生产环境三大主流策略组合

1. 结构化父子切块 —— 复杂文档：适用于企业规章制度、合同条款、产品说明书、API 技术文档、法规文件。上游用版面识别或标题正则做 Parent（保证结构完整），下游用递归切分做 Child（保证检索粒度），搭配 Redis 与向量库双轨存储。
2. 带有 Metadata 注入的递归字符切分 —— 通用 Baseline：适用于通用知识库、博客文章、自由格式文本、快速冷启动项目。使用 RecursiveCharacterTextSplitter，结合提取标题或利用大模型为每个分块自动生成全局背景摘要拼接到头部。
3. 句窗口切分 —— 细粒度事实查找：适用于客服问答、参数表查询、单句事实检索（如“产品的最大承重是多少”）。切分时以单句话作为向量存储和检索单位（检索极精准）；命中后，系统自动向左向右扩展 N 句（如扩展前后各 2 句），将完整的上下文窗口组装后喂给大语言模型。

### 3.2 保持简单切分策略的场景条件

在以下场景中应优先保持简单策略，避免盲目增加系统复杂度：

* 文档量小或结构统一：纯文本、博客、说明文档直接用递归切分加 Metadata 即可，上语义分块只会增加算力开销。
* 瓶颈不在分块：如果坏例主要来自专有名词漏召回或压根没命中，应先补混合检索与 Reranker，而不是继续细分 Chunk。
* 没有评测手段：无法量化 Recall@K 与 Faithfulness 变化时，引入父子、句窗口等复杂架构只会让问题更难定位。

### 3.3 企业制度文件三阶段落地流水线案例

企业制度文件（SOP、考勤制度、报销流程）天然具备严密的层级结构，且存在“条文极其简短”与“判定逻辑需要上下文”的矛盾（例如 1.2 节考勤 800 字 Parent 与 1.2.3 款 30 字 Child“未提前 2 小时报备算旷工”）。

采用“结构切分 + 递归降级”与“父子切块”结合的三阶段流水线如下：

```text
原始 Markdown / 制度文件 (.docx / .pdf)
          │
          ▼
【阶段 1：结构切分 (确定 Parent 边界)】
按照 # / ## / ### 标题或 "1. / 1.1 / 1.1.1" 正则切分。
生成【Parent Chunk】(500~1200 Tokens)，提取并绑定 Metadata: {"章": "考勤", "节": "请假"}
          │
          ▼
【阶段 2：递归降级 (确定 Child 边界)】
检查每一个 Parent Chunk：
  ├── 若长度 <= 200 Tokens ──> 直接作为 Child (Parent = Child)
  └── 若长度 > 200 Tokens  ──> 在该 Parent 内部启用 RecursiveCharacterTextSplitter
                              按“句号/分号/换行”切成 100~200 Tokens 的【Child Chunks】
          │
          ▼
【阶段 3：父子架构写入与检索】
  ├── Child Chunks ──> 仅将向量存入 VectorDB (保证检索极度精准)
  └── Parent Chunks ──> 存入 DocStore / Redis (带完整结构与标题 Metadata)
```

结合后的核心优势：

1. 子块绝不跨章节：传统父子切块按固定字符（如 1000 字）切父块，易将上一章结尾与下一章开头切在一起；结构化父块保证了父块本身就是逻辑完备的制度章节。
2. 子块继承语义上下文：子块不仅体型小、易命中，还自动继承了父块的“章-节-条”路径 Metadata。

## 4 主流框架与生态切分器工程解析

### 4.1 Unstructured：视觉与版面感知分块

* 解决痛点：传统切分器对文本是“盲目”的，容易把表格切成两半或把标题与正文撕裂。
* 分块逻辑：先用 OCR 或版面分析算法将文档解析成带有属性的“元素（Elements）”（Header、NarrativeText、Table、ListItem）。在切块时采用 chunk_by_title 智能规则：
  * 表格保护：遇 Table 元素绝对不强行切开，整体作为一个独立 Chunk。
  * 标题聚合：将属于同一个 Title 下的所有 NarrativeText 段落拼在一起，超限时才在段落间划开。

### 4.2 LlamaIndex：节点关系与动态合并分块

* 解决痛点：切块产出包含上下文网络关系的“节点（Node）”，将切块与后续动态检索深度绑定。
* 标志性两大策略：
  1. 句窗口切分：将文档按单句话切成极小 Node。生成每个 Node 时，将其前后 N 句话（如前 2 句 + 后 2 句）作为上下文存入 Metadata。检索时仅用单句算向量相似度（极度精准）；命中后将 Metadata 里的 5 句话上下文窗口直接传给大语言模型。
  2. 自动合并切块：将文档切成多层级树状结构（父节点 2000字 ➔ 中节点 500字 ➔ 子节点 120字）。检索时仅在底层子节点（120字）做向量匹配。若同一个中节点下有超过一定比例（如 50% 以上）的子节点被命中，系统自动触发“合并提权”——不再传零碎子节点，直接调出上一层的中节点甚至父节点投喂大语言模型。
