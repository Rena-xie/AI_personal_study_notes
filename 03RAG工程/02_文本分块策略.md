# 文本分块策略

> 本篇讲 RAG 链路中的第二步：把上游解析出的结构化文档，切成适合检索的知识单元。
> 上游是 [[01_数据解析策略]]，下游是 [[03_向量化原理及选型]]。

## 1 文本分块的基础知识

### 1.1 什么是文本分块

文本分块是把长文档拆分为多个相对完整知识单元的过程。Chunk 是后续向量化与检索的基本单位：Embedding 以 Chunk 为输入，Retrieval 以 Chunk 为返回结果，LLM 也以 Chunk 作为上下文来源。

它的处理对象是 [[01_数据解析策略]] 输出的结构化文档（Markdown / JSON 元素 + 元数据）。因此解析阶段保留的标题层级、表格与代码块结构，直接决定了分块能切在什么位置。

### 1.2 为什么需要文本分块（4 大核心必要性）
1. 突破模型上下文限制：LLM 和 Embedding 模型均有单次输入的最大 Token 限制，长文档无法一次性直接送入模型。
2. 提高向量检索的精准度：长文档包含过多混合主题，直接向量化会导致语义稀释；分块后每个片段语义聚焦，更容易在向量空间与用户提问精准匹配。
3. 降低调用成本与响应延迟：将庞大原文档全部传入 LLM 会大幅增加 Token 费用，并显著增加首字响应时间（TTFT）与推理延迟。精准匹配小块可减少不必要的输入。
4. 减少模型幻觉：提供聚焦且高度相关的背景知识，能让 LLM 准确基于事实回答，避免引入无关信息引发脑补。

### 1.3 分块大小的影响与权衡
分块大小直接决定了知识检索和生成质量的上限，过大或过小都会带来显著的工程风险：

| 分块策略                 | 核心问题       | 工程风险与后果                                  |
| :------------------- | :--------- | :--------------------------------------- |
| 块过小（如 < 100 Tokens）  | 语义断裂与上下文缺失 | 句子被硬生生截断，丢失关键限定条件，导致模型断章取义或理解错误          |
| 块过大（如 > 1000 Tokens） | 信息噪音与语义稀释  | 包含大量无关信息，降低向量检索相似度得分，极易触发 LLM 中间遗忘与注意力散射 |

### 1.4 决定 Chunk Size 的三大核心维度
1. 文本本身的结构特征：代码、法律条文、学术论文或聊天记录对上下文连贯性要求各不相同，需结合段落、标题等自然分隔符进行设计。
2. Embedding 模型的最佳吞吐区间：不同向量模型在不同文本长度下的表征能力存在差异，通常 256~512 Tokens 是平衡性能与精度的常用区间。
3. 重叠度设置：为了防止重要信息恰好落在分块边界而被割裂，通常设置 10%~20% 的重叠区域（约 50~100 Tokens），保持相邻分块间的语义连贯。Overlap 是一种降低边界信息损失的工程手段。而且 Overlap 也不是越大越好，会产生大量重复内容，导致：存储增加、Embedding 增加、检索结果重复、Context 浪费、成本上升。所以 **Overlap 本身也是一个需要调优的参数**。

### 1.5 Chunking 的核心目标

分块不是把文本平均切开，而是要同时满足三个目标：

* **语义完整性**：每个 Chunk 都应尽量是一个自洽的知识单元，包含完整的主谓与限定条件，避免“断章取义”。
* **检索粒度**：Chunk 是向量检索的最小单位，粒度过粗会稀释语义，过细会丢失上下文，需要与问题类型匹配。
* **上下文效率**：进入 LLM 上下文的每个 Token 都应尽量与当前问题相关，减少噪声对注意力与成本的挤占。

三个目标往往互相拉扯：粒度越细，检索越准但上下文越碎；粒度越粗，上下文越全但噪声越多。分块策略的选择，本质上是在这三者之间找平衡。

## 2 切块方法与策略

### 2.1 基础切片方法
* 固定长度切片：按固定的 Token 或字符数量（如 300、500 或 800 Tokens）强行切分。
* 重叠窗口切片：在相邻切片之间保留 10%~20% 的重叠区域，防止完整的句子或核心语义在切分边界被割裂。
* 结构切片：依据 Markdown 标题（H1, H2, H3）或天然段落进行划分，保证每一个 Chunk 在逻辑上是一个完整的讨论主题。
### 2.2 递归切分
最大程度保持段落与句子的语义完整性。其核心在于维护一个具有优先级排序的分隔符列表，默认层级如下：

```
输入大文本
   │
   ▼ 优先按双换行符 "\n\n" 切分 (自然段落)
   │
   ▼ (若单个块超过 chunk_size)
   降级按单换行符 "\n" 切分 (句子/行)
   │
   ▼ (若单行仍超过 chunk_size)
   降级按空格 " " 切分 (单词)
   │
   ▼ (若无空格可切)
   终极按单个字符 "" 强行物理截断
```
#### 2.2.1 中文本土化改造
默认分隔符针对英文设计，处理中文时必须自定义 separators 参数，加入中文句号（。）、分号（；）、感叹号（！）等标点符号，避免中文句子在中间被意外切断。
#### 2.2.2 核心控制参数
* chunk_size：目标 Chunk 的最大长度（字符数或 Token 数）。
* chunk_overlap：相邻 Chunk 之间重叠保留的长度（通常为 chunk_size 的 10%~20%）。
* separators：自定义分隔符列表，按优先级从高到低排列。

### 2.3 基于语义的分块策略

#### 2.3.1 概念与核心理念
语义分块是一种基于文本实际含义（语义）而非物理字符数或固定标点的智能切分策略。其核心理念是：利用向量模型实时计算相邻句子之间的语义相似度，当发现上下文语义发生剧烈变化（主题转折）时才触发切分。
#### 2.3.2 工作机制与计算流程（5 步链条）
```
原始文档 ──> [1. 拆分为单句] ──> [2. 计算句向量] ──> [3. 计算相邻句余弦距离] ──> [4. 阈值判定转折点] ──> 组合成 Chunk
```

1. 原子句拆分：将原始长文本按最细粒度的表达单位（通常是单句话，按句号或感叹号）切开。
2. 句子向量化：使用 Embedding 模型为每一个句子（或包含上下文的滑动句子组）生成对应的语义向量。
3. 距离/相似度计算：计算相邻两个句子向量之间的余弦距离。距离小/相似度高说明前后讨论同一个主题；距离大/相似度低说明发生主题转折。
4. 阈值判定：设定语义转折临界点（阈值）。只要相邻句子的语义距离高于该阈值，就在此处划定切分点。
5. 组合出块：将处于两个切分点之间的所有句子组合成一个独立的 Chunk。
#### 2.3.3 四种阈值确定策略（界定主题转折）
* 百分位数法（工程最常用）：计算整篇文档中所有相邻句子距离的分布，设定百分位数（如 95%）。只有距离排在最前 5% 的剧烈变动点才会被切开，适合整体结构统一的文档。
* 标准差法：以所有距离的平均值加上 N 倍标准差（如 Mean + 1.5 * Std）作为切割线，抗噪声能力较强。
* 四分位距法：利用中位数和四分位距寻找异常高距离点（Outliers），适合长短混杂、排版不均的文本。
* 绝对阈值法：人为硬性指定一个距离数值（如 0.25），超过即切分。
#### 2.3.4 优缺点分析与工程权衡

**核心优势**
* 语义纯度极高：每个 Chunk 都是主题独立且完整的知识单元，不会将结论与引言强行切断。
* 自适应 Chunk 大小：探讨同一个概念时保留为大 Chunk；频繁切换主题时自动切成小 Chunk。
* 显著提升检索精度：存入向量库的片段主题聚焦，大幅减少语义稀释导致的召回率下降。

**缺点与代价**
* 计算开销大、延迟高：切分前必须对整篇文档的所有句子运行 Embedding 推理，处理海量文档时消耗大量 API 额度或 GPU 算力。
* 块尺寸不可控：遇到缺乏转折的长文本时可能产出超大 Chunk；遇到频繁跳跃的文本时会产出大量微型 Chunk（工程上需配置 Min/Max 字符数保护边界）。

### 2.4 基于文档结构与版面的分块策略

**基于文档结构的分块** 直接利用文档作者预设的标题层级、版面元素（PDF 章节/表格）或语法树（代码 Class/Function）作为天然切割边界。

#### 2.4.1 三种主流的结构切分形态
1. **标题层级切分**
   * 适用格式：Markdown、HTML、Docx、EPUB。
   * 工作机制：解析 `#`, `##`, `###` 或 `<h1>`, `<h2>` 标签，将同一个小标题及其包含的所有正文组合为一个独立的 Chunk。
2. **版面/元素级切分**
   * 适用格式：PDF、复杂排版文档、扫描件。
   * 工作机制：依赖上游解析引擎（Docling、MinerU、Unstructured）提取出的 Element 类型（Title、NarrativeText、Table、FigureCaption）。将一个完整的表格划分为一个 Chunk，将“标题 + 对应正文”合并为一个 Chunk，绝对禁止将表格或图片说明从中间打断。
3. **抽象语法树切分**
   * 适用格式：Python、Java、C++、TypeScript 等源码文件。
   * 工作机制：利用语言解析器（如 Tree-sitter）构建 AST，按照类（Class）、函数（Function）或模块（Module）的物理作用域边界切分，确保每一块代码都是语法完备、可单独运行或理解的单元。

#### 2.4.2 核心杀手锏：元数据继承
基于结构切分的最大优势不仅在于“切得准”，更在于能够 **自动提取并注入层级上下文元数据** 。

示例：对于单句文本“该参数默认值为 0.05。”，单独看毫无意义。但在结构切分时，系统会将它所在的标题路径提取出来，直接绑定到该 Chunk 的 Metadata 中：

```json
{
  "page_content": "该参数默认值为 0.05。",
  "metadata": {
    "Header_1": "数据预处理架构",
    "Header_2": "语义分块器 (Semantic Chunker)",
    "Header_3": "阈值策略参数配置",
    "Source": "rag_design.md"
  }
}
```

**工程价值**：在向量检索或喂给 LLM 时，可以将 Metadata 中的标题链拼接到文本头部（如 `[系统架构 > 语义切分 > 参数]: 该参数默认值为 0.05`），从根本上避免了“断章取义”和指代丢失。

#### 2.4.3 生产架构解法：两阶段混合切分
结构分块存在章节长度不受控的天然痛点（如果某个二级标题下写了 5000 字未加小标题，会产生超大 Chunk）。因此，生产级 RAG 系统普遍采用 **两阶段混合策略**：

```
原始文档 ──> [阶段 1: 按 Markdown 标题 / 结构元素切分]
                   │
                   ├── 块尺寸 <= chunk_size ──> 直接输出 (保留完整结构)
                   │
                   └── 块尺寸 > chunk_size ──> [阶段 2: 触发 RecursiveCharacterTextSplitter 降级二次切分]
```

1. **第一阶段（结构优先）**：先按 `#` 标题或版面元素切成逻辑完整的“大块”，并记录当前块的标题层级元数据。
2. **第二阶段（尺寸兜底）**：检查各个大块的 Token 长度。对超长的块，在保留上一步元数据的前提下，使用递归字符切分器（按段落/句子）切成符合 chunk_size 的“小块”。

### 2.5 父子切块
“父子切块”不仅是字符串切分，而是一套涵盖存储、映射与检索拦截的系统级架构：

```
               ┌────────────────────────────────────────────────────────┐
               │              父子切块架构 (Parent-Child)                │
               └────────────────────────────────────────────────────────┘
                                           │
       ┌───────────────────────────────────┼───────────────────────────────────┐
       ▼                                   ▼                                   ▼
【1. 双轨存储架构】                 【2. 主外键关联机制】         【3. 检索拦截与重定向】
向量库 (VectorDB)                   Child 节点中写入                向量检索命中Child
   └── 存 Child (小块)               Metadata:                不直接送给 LLM，
文档库 (DocStore/Redis)           {"parent_id": "P_001"}    而是拿着 parent_id 
   └── 存 Parent (大块)                                     去 DocStore 换取 Parent
```

1. **双轨存储设计**：系统同时挂载两个数据库：向量数据库（存 Child 向量，用于高精度计算）和 Key-Value 文档数据库（如 Redis、LevelDB，专门存 Parent 原文）。
2. **关系型映射**：切片后，系统为 Child 和 Parent 建立主外键式的 `parent_id` 绑定关系。
3. **检索劫持与扩展**：用户提问时，向量数据库算出的最高分结果是 Child；但 Retriever 引擎拦截该结果，解析出 `parent_id` 后去 KV 数据库“以键换值”，将真正的 Parent 提取出来喂给大模型。

父子切片通过拆分“检索单元”与“上下文单元”解决这一痛点：

* **父块**：将文档切分为较大的段落或章节（如 1000~2000 Tokens），保留完整的上下文信息。
* **子块**：在父块内部进一步细分为较小的片段（如 200~400 Tokens），专注于表达小粒度的具体语义。

#### 2.5.1 检索与召回链路

```
[文档输入] ──> 切分为 [父块 Parent Chunk (1000~2000 Tokens)]
                      │
                      ├──> 细分为 [子块 Child Chunk 1 (200~400 Tokens)] ──> 计算 Embedding 存入向量库
                      ├──> 细分为 [子块 Child Chunk 2 (200~400 Tokens)] ──> 计算 Embedding 存入向量库
                      └──> 元数据注入 parent_id 指向 父块 ID

[用户提问 Query] ──> 向量检索匹配命中 [子块 Child Chunk]
                             │
                             ▼ (通过 parent_id 反向召回)
                      提取完整 [父块 Parent Chunk] 投喂给 LLM
```

1. 在向量数据库中，仅对高精度的子块（Child Chunk）计算 Embedding 并进行精准向量匹配。
2. 当某颗子块命中后，系统通过元数据中的 `parent_id` 关联映射，反向将该子块对应的完整父块（Parent Chunk）提取出来，投喂给大模型作为回答上下文。
3. 这种机制既保证了检索阶段的高命中率，又保证了生成阶段上下文的完整连贯。

### 2.6 句窗口切分

**每个句子节点作为一个细粒度检索单元，因此它的 embedding 表征的是这个中心句**；周围窗口保存在 metadata 中，在检索后再恢复上下文。LlamaIndex 官方示例明确说明，window metadata 不提供给 embedding 模型，而是在检索后替换节点，再交给 LLM。

句窗口与 overlap 的区别：

* **Overlap**：在切分阶段让相邻 Chunk 复制一段字符，重叠内容会参与 Embedding，也会占用向量库存储。
* **句窗口**：索引时只对中心句计算向量，前后 N 句只写进 metadata、不参与 Embedding；命中后再把窗口文本拼回上下文交给 LLM。

**实现与代价**：以 LlamaIndex 为例，用 `SentenceWindowNodeParser` 生成窗口节点，检索命中后用 `MetadataReplacementPostProcessor` 把节点替换为完整窗口。优点是单句检索精度极高，缺点是节点数量与索引体积明显膨胀，适合客服问答、参数表查询这类细粒度事实查找。

### 2.7 “结构切分 + 递归降级”与“父子切块”差异对比

| 维度           | 结构切分 + 递归降级                                                 | 父子切块                                                              |
| :----------- | :---------------------------------------------------------- | :---------------------------------------------------------------- |
| **所属环节**     | 文本解析与切片                                                     | 索引构建与检索架构                                                         |
| **解决的核心痛点**  | **“断章取义”与层级丢失**：防止把单条规则从章节中割裂，确保每条规则都继承“章-节-条”的路径 Metadata。 | **“检索精度与回答完整性的矛盾”**：解决小 Block 检索准确但上下文太短、大 Block 上下文完整但向量表征模糊的问题。 |
| **对制度文件的价值** | 保证输出的每一个 Chunk 都是语法逻辑完备的“制度章节”。                             | 保障用户提问极具体时（如“带薪年假几天”），能准确搜到子块，并把整个“年假管理办法”父块送给 LLM。               |
| **单独使用的局限**  | 若某个章节内容极长（如 1500 字），直接入库会导致向量检索精度下降（语义被稀释）。                 | 若不配合结构切分，盲目按字数切父块/子块，子块极易恰好跨越两条不同的制度条款。                           |
## 3 切块策略组合与落地案例

### 3.1 策略组合
在真实生产环境中，行业形成了以下策略组合：

1. **结构化父子切块 —— 复杂文档王者**
   * 适用场景：企业规章制度、合同条款、产品说明书、API 技术文档、法规文件。
   * 策略做法：上游用版面识别/标题正则做 Parent（保证结构完整），下游用递归切分做 Child（保证检索粒度），搭配 Redis + 向量库双轨存储。
2. **带有 Metadata 注入的递归字符切分 —— 通用 Baseline**
   * 适用场景：通用知识库、博客文章、自由格式文本、快速冷启动项目。
   * 策略做法：使用 `RecursiveCharacterTextSplitter`，结合提取标题或利用 LLM 为每个 Chunk 自动生成全局背景摘要拼接到头部。
3. **句窗口切分 —— 细粒度事实查找**
   * 适用场景：客服问答、参数表查询、单句事实检索（如：“产品的最大承重是多少”）。
   * 策略做法：切分时以“单句话”作为向量存储和检索单位（检索极精准）；命中后，系统自动向左向右扩展 $N$ 句（如扩展前后各 2 句），将完整的上下文窗口组装后喂给大模型。

### 3.2 生产落地共识：黄金检索架构
单纯靠优化切块策略只能解决 50% 的问题，生产级完整检索架构黄金搭配为：
$$\text{结构化父子切块} + \text{混合检索 (向量 Dense + BM25 关键字)} + \text{重排模型 (Reranker)}$$
1. **混合检索**：防止向量模型对数字、工号、专有名词（如“错误码 0x8004”）不敏感的问题。
2. **Reranker（重排）**：从初筛出来的候选 Chunk 中，使用交叉编码器（Cross-Encoder，如 BGE-Reranker）精挑出最相关的 3~5 个 Chunk 喂给 LLM，大幅降低大模型幻觉。

### 3.3 前沿策略：Anthropic Contextual Retrieval (上下文增强切片)
**Contextual Retrieval** 是 Anthropic 提出的重磅 RAG 优化策略，专为解决传统切片“断章取义”导致的检索失效问题而设计，能够将检索失败率 **降低高达 67%** 。

#### 3.3.1 核心原理
传统切片中，切片“2023 年 Q2 公司营收增长了 3%”因脱离上下文丢失了主语 ACME 公司。Anthropic 的解法是在对切片进行向量化和 BM25 建索引之前，先利用 LLM 结合 **整篇文档** 为每一个切片自动生成一段 50~100 字的全局上下文前缀并拼接到头部：

Contextualized Chunk=LLM 生成的上下文说明+原始 Chunk

增强后文本：`“【该切片来自 ACME 公司 2023 年 Q2 财报的财务分析章节】2023 年 Q2 公司营收增长了 3%。”`

#### 3.3.2 4 步实施流程
```
原始文档 ──> [1. 基础分块] ──> [2. 结合全文调 LLM 注入 Context] ──> [3. 建立上下文双路索引] ──> [4. 混合检索与重排]
```

1. **提示词工程**：利用 Prompt 将 `<document>` 与 `<chunk>` 输入 LLM，生成 1~2 句定位说明。
2. **成本控制关键：提示词缓存**：将 `<document>` 作为缓存前缀，后续切片直接命中缓存，调用成本降低 ~90%，处理速度提升数倍。
3. **上下文双路索引**：同时建立 Contextual Embedding（向量索引）与 Contextual BM25（词频倒排索引）。
4. **重排集成**：发起双路检索后将前 20~100 个结果送入 Reranker 模型（如 Cohere Rerank / BGE-Reranker）二次精排。

#### 3.3.3 实测效果与量化数据

| 检索方案 | 检索失败率降低幅度 | 说明 |
| :--- | :--- | :--- |
| **传统 Baseline (仅传统向量检索)** | 0% (基准) | 单纯基于未增强切片进行向量搜索。 |
| **仅使用 Contextual Embeddings** | **降低 35%** | 仅仅为向量切片加上上下文前缀，检索错误率即下降 1/3。 |
| **Contextual Embeddings + Contextual BM25** | **降低 49%** | 向量与关键字检索均加入上下文增强，互补性极强。 |
| **Contextual Retrieval + BM25 + Reranking** | **降低 67%** | **最终形态**：上下文增强 + 混合检索 + 重排，检索错误率降幅达 2/3。 |

1. **性价比最高组合**：`Contextual Retrieval` + `BM25 混合检索` + `Reranker` 是目前公认提升 RAG 召回率最立竿见影的工程手段。
2. **适用场景**：极其适合长文档、代词指代多、专业名词密集的行业知识库（如医疗病例、法律卷宗、大型企业 SOP）。
3. **技术前提**：务必开启 Prompt Caching，否则大规模处理海量文档时 API 费用容易超支。

### 3.4 哪些场景没必要复杂化

策略越多不等于效果越好，以下场景应优先保持简单：

* **文档量小或结构统一**：纯文本、博客、说明文档直接用递归切分加 Metadata 即可，上语义分块只会增加算力开销。
* **瓶颈不在分块**：如果坏例主要来自专有名词漏召回或压根没命中，应先补混合检索与 Reranker，而不是继续细分 Chunk。
* **没有评测手段**：无法量化 Recall@K 与 Faithfulness 变化时，引入父子、句窗口等复杂架构只会让问题更难定位。

判断标准很简单：先用递归切分跑出 Baseline，只有当评测证明瓶颈在切分环节时，再引入更复杂的策略（见第 8 章）。

### 3.5 落地案例：企业制度文件三阶段落地流水线

企业制度文件（SOP、考勤制度、报销流程）天然具备严密的层级结构，且存在“条文极其简短”与“判定逻辑需要上下文”的矛盾（例如 1.2 节考勤 800 字 Parent 与 1.2.3 款 30 字 Child“未提前 2 小时报备算旷工”）。

“结构切分 + 递归降级”与“父子切块”结合的三阶段流水线如下：

```
原始 Markdown / 制度文件 (.docx / .pdf)
          │
          ▼
【阶段 1：结构切分 (确定 Parent 边界)】
按照 # / ## / ### 标题或 "1. / 1.1 / 1.1.1" 正则切分。
生成【Parent Chunk】(500~1200 Tokens)，提取并绑定 Metadata: {"章": "考勤", "节": "请假"}
          │
          ▼
【阶段 2：递归降级 (确定 Child 边界)】
检查每一个 Parent Chunk：
  ├── 若长度 <= 200 Tokens ──> 直接作为 Child (Parent = Child)
  └── 若长度 > 200 Tokens  ──> 在该 Parent 内部启用 RecursiveCharacterTextSplitter
                              按“句号/分号/换行”切成 100~200 Tokens 的【Child Chunks】
          │
          ▼
【阶段 3：父子架构写入与检索】
  ├── Child Chunks ──> 仅将向量存入 VectorDB (保证检索极度精准)
  └── Parent Chunks ──> 存入 DocStore / Redis (带完整结构与标题 Metadata)
```

**结合后的核心优势**：

1. **子块绝不跨章节**：传统父子切块按固定字符（如 1000 字）切父块，易将上一章结尾与下一章开头切在一起；结构化父块保证了父块本身就是逻辑完备的制度章节。
2. **子块继承语义上下文**：子块不仅体型小、易命中，还自动继承了父块的“章-节-条”路径 Metadata。
## 4 主流框架与生态切分器工程解析

在真实工程落地中，掌握框架专属组件能解决三大工程问题：掌握框架绑定的高级检索设计、感知开箱即用引擎（如 RAGFlow DeepDoc）的开销、对齐生态元数据字典（`node_id`、`parent_id`、`source`）。

### 4.1 Unstructured：视觉与版面感知分块
* **解决痛点**：传统切分器对文本是“盲目”的，容易把表格切成两半或把标题与正文撕裂。
* **分块逻辑**：先用 OCR 或版面分析算法将文档解析成带有属性的“元素（Elements）”（Header、NarrativeText、Table、ListItem）。在切块时采用 `chunk_by_title` 智能规则：
  * **表格保护**：遇 Table 元素绝对不强行切开，整体作为一个独立 Chunk。
  * **标题聚合**：将属于同一个 Title 下的所有 NarrativeText 段落拼在一起，超限时才在段落间划开。

### 4.2 LlamaIndex：节点关系与动态合并分块
* **解决痛点**：切块产出包含上下文网络关系的“节点（Node）”，将切块与后续动态检索深度绑定。
* **标志性两大策略**：
  1. **句窗口切分**
     * 做法：将文档按单句话切成极小 Node。生成每个 Node 时，将其前后 $N$ 句话（如前 2 句 + 后 2 句）作为上下文存入 Metadata。
     * 效果：检索时仅用单句算向量相似度（极度精准）；命中后将 Metadata 里的 5 句话上下文窗口直接传给 LLM。
  2. **自动合并切块**
     * 做法：将文档切成多层级树状结构（父节点 2000字 ➔ 中节点 500字 ➔ 子节点 120字）。
     * 动态合并机制：检索时仅在底层子节点（120字）做向量匹配。若同一个中节点下有超过一定比例（如 50% 以上）的子节点被命中，系统自动触发“合并提权”——不再传零碎子节点，直接调出上一层的中节点甚至父节点投喂 LLM。

## 6 Chunk 质量如何评估

分块质量不能只靠肉眼判断，建议按“语义 → 结构 → 检索指标”三层验证。指标的定义与计算方式见 [[05_自动化评测]]，本篇只保留分块视角的判据。

### 6.1 语义是否完整

抽查单个 Chunk 是否自洽：能否读懂它在说什么，是否包含完整主谓与限定条件。像“该参数默认值为 0.05”这种脱离标题就无意义的句子，说明切分位置不合理。

### 6.2 是否出现断句 / 断表 / 断代码

* **断句**：句子被硬切在两块之间，前后都读不通。
* **断表**：表格被从中间切开，表头与数据分离。
* **断代码**：代码块丢失缩进或被截断，无法独立理解。

这三类问题会直接破坏下游 Embedding 与生成质量，应在入库前抽样检查。

### 6.3 Recall@K 与 Precision@K

* **Recall@K**：该找到的知识有没有被召回，反映分块是否切得太碎或边界不合理。
* **Precision@K**：Top-K 里有多少是真相关的，反映 Chunk 是否混入过多无关内容。

### 6.4 MRR 与 NDCG

* **MRR**：第一个正确结果排得够不够靠前。
* **NDCG**：多个结果的相关程度与排序是否合理。

两者用于观察切分粒度变化后，正确 Chunk 的排名位置是否改善。

### 6.5 Context Recall 与 Context Precision

* **Context Recall**：回答问题所需的信息是否都进入了 Context。
* **Context Precision**：进入 Context 的内容有多少真正有用。

这两项最接近“分块对最终回答的影响”，适合作为端到端验证指标。

## 7 Chunking 与前后阶段的关系

```
Parsing → Structure → Chunking → Embedding → Retrieval
```

* **上游 Parsing（[[01_数据解析策略]]）**：解析质量决定可用结构（标题、表格、代码块）与可继承的元数据，是分块的前置条件。
* **本环节 Chunking**：同时决定“检索单元”（Child）与“上下文单元”（Parent）。
* **下游 Embedding（[[03_向量化原理及选型]]）**：向量化的单位就是 Chunk，Chunk 的语义是否聚焦直接决定向量表征质量。
* **下游 Retrieval**：Chunk 粒度决定召回与排序的上限——召回不到的知识，后面的 Reranker 与 LLM 都无法补救。


## 8 典型 Chunking Pipeline 与决策路径

### 8.1 不同文档类型如何选择策略

先用决策树判断文档该走哪条切分路径：

```text
                    文档
                       ↓
              文档结构是否明确？
                 /           \
               是             否
               ↓              ↓
        Structure-aware    Recursive /
               ↓           Fixed-size
        Section 是否过长？
          /           \
        否             是
        ↓              ↓
     直接 Chunk     Recursive
                       ↓
                是否需要更细粒度？
                    /      \
                  是        否
                  ↓          ↓
         Semantic /      普通 Chunk
        Sentence Window
                  ↓
       是否需要更大上下文？
             /       \
           是         否
           ↓           ↓
      Parent-Child   直接返回
```

### 8.2 如何建立 Baseline 并通过评测迭代

推荐的落地顺序：

1. **建立 Baseline**：先用带 Metadata 注入的递归切分跑通全流程，记录 Recall@K 与 Faithfulness。
2. **按结构升级**：文档层级明确时，换成结构切分 + 递归降级，观察指标变化。
3. **按粒度升级**：需要更细的事实定位时，再引入父子切块或句窗口。
4. **按效果收口**：指标不再提升就停止增加复杂度。

一句话原则：Chunk 越合理，Embedding 得到的语义单元越集中，检索越容易召回正确 Chunk，Reranker 也更容易把它排到前面，LLM 最终获得的证据就越完整。迭代方式见 [[05_自动化评测]] 的单变量实验闭环。

## 9 小结

* 分块是 RAG 的第二步，Chunk 同时是 Embedding 的输入与 Retrieval 的返回单位。
* 目标是语义完整性、检索粒度与上下文效率三者的平衡。
* 六种主流策略（固定大小、递归、语义、结构、父子、句窗口）按文档结构与检索需求组合使用。
* 生产共识是“结构化父子切块 + 混合检索 + Reranker”，但先跑 Baseline，只有评测证明瓶颈在切分时才增加复杂度。
* 分块质量用语义完整性、结构完整性（不断句 / 断表 / 断代码）与 Recall@K、Context Recall 等指标共同验证。

> **Chunk 是为 Retrieval 服务的，不是为了把文本平均切开。**
