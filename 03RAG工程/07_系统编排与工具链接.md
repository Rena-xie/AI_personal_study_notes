## 1 为什么需要系统编排

### 1.1 单个组件拼不成应用

检索、重排、生成，每个组件单独拿出来都不难；难的是把它们按正确顺序串起来，并处理中间的分支、状态、失败与权限。系统编排要解决的就是这件事：决定每一步由谁执行、按什么条件跳转、失败后怎么办、状态存在哪里。

### 1.2 Pipeline / Workflow / Agent 的区别

* **Pipeline**：步骤与顺序全部写死在代码里，输入经过固定的 A → B → C 得到输出。确定性强、易调试，但无法根据中间结果改道。
* **Workflow**：同样由预定义代码路径编排，但引入条件分支——由代码而非模型决定走哪条路。
* **Agent**：由模型自己决定下一步做什么、调用哪个工具，程序不再规定路径。

Anthropic 在《Building Effective Agents》中把这类系统统称为 agentic systems，并给出官方定义：Workflow 是“LLM 与工具经由预定义代码路径编排”的系统，Agent 是“LLM 动态决定自身流程与工具使用”的系统。官方同时建议从最简单的方案起步，只有当任务确实需要灵活性与模型自主决策时才升级到 Agent——自主性换来的是延迟、成本与可预测性的代价。

## 2 RAG 的三条流水线

### 2.1 数据摄取流水线

把原始文件变成可检索的索引：解析 → 清洗 → 分块 → 向量化 → 入库。对应本库 [[01_数据解析策略]]、[[02_文本分块策略]] 与 [[03_向量化原理及选型]]。

### 2.2 检索流水线

把用户问题变成证据：查询工程 → 路由 → 混合检索 → 融合 → 重排 → 上下文构建，见 [[04_查询工程与混合检索重排]]。

### 2.3 生成流水线

把证据变成答案：上下文拼装 → Prompt 组织 → 模型生成 → 引用输出。生成侧的质量指标见 [[04_查询工程与混合检索重排]] 第 7 章与 [[05_自动化评测]]。

#### 2.3.1 上下文拼装与动态 Prompt 构建

在企业级检索增强生成闭环链路中，编排层负责把检索结果转换为模型能够理解与遵照的动态上下文，流程如下：

* **原始请求接收**：接收用户原始提问并触发前置处理。
* **检索召回**：通过混合检索与重排定位 Top-K 个精准切片。
* **上下文拼装**：把切片作为事实引文，与原始系统指令拼接为一整段包含角色定义、规范约束与参考数据的完整上下文。
* **模型生成约束**：把拼装好的 Prompt 交给大语言模型，约束其基于事实依据作答。

#### 2.3.2 Prompt 模板的结构化层级

在工业级应用中，Prompt 不是单一字符串的简单拼接，而是划分为四个权限与功能层级：

* **系统消息**：权威度与优先级最高，用于定义角色定位、任务规则、输出结构规范、工具 Schema 及安全护栏，模型将其作为全局基准。
* **用户消息**：包含用户当前提问以及经前置改写后的查询语句。
* **助手消息**：用于存放少样本示例或多轮历史对话。
* **工具消息**：承载外部工具执行后回填的真实观察结果。

### 2.4 条件路由：不同 Query 走不同路径

不是所有问题都该走检索：闲聊可以直接交给模型，结构化统计该走数据库，实时信息该走联网搜索。路由的三大分发维度、两种实现机制与对比表见 [[04_查询工程与混合检索重排]] 第 2 章。

### 2.5 安全与权限由编排层统一施加

元数据溯源、注入防护与权限过滤，都需要在调用模型前后由编排层统一施加。这三块的完整实现放在 [[06_LLMOps与可观测性运维]]：

* **元数据打标与可视化溯源**：切片阶段注入来源信息，生成阶段输出页码级引用角标。
* **安全护栏**：针对直接注入与间接文档注入的纵深防御。
* **权限隔离**：身份认证 → 角色解析 → 元数据过滤条件 → 底层强过滤。

## 3 编排框架选型与技术栈演进

### 3.1 智能体核心架构公式与控制流哲学
智能体的核心架构公式可归纳为：`Agent = Model + Harness`
* **模型**：作为大脑的核心算力与通用知识库，负责意图理解、逻辑推理、自然语言表达以及工具调用决策。
* **Harness**：围绕模型构建的确定性外围控制机制，包含 Prompt 工程、上下文管理、工具系统、工作记忆以及安全护栏。

#### 3.1.1 确定性代码与动态 LLM 决策的混合控制
在生产级 AI 系统中，纯 Prompt 驱动的 Agent 存在随机性与不可控风险。成熟工程实践普遍采用确定性代码逻辑与 LLM 动态决策相结合的模式：由确定性 Python 代码或状态机控制主干业务流程（如确定性的步骤 A ➔ 步骤 B），仅在需要意图理解、复杂路由或语义生成的局部节点引入 LLM。

### 3.2 主流编排框架对比

#### 3.2.1 代码优先框架
* **LlamaIndex**：数据连接与 RAG 领域的绝对霸主。拥有全行业最丰富的索引策略、数据图谱连接方式、元数据组织结构以及检索调优接口，最适合对摄取管道与检索路径有极致深度定制要求的团队。其 LlamaIndex Workflows 提供了基于事件驱动的节点编排能力。
* **LangChain / LangGraph**：AI 开发领域生态最大的框架。当系统由于业务复杂度上升，需要从单步被动检索演进到包含多轮推理、反思、自纠错的 Agentic RAG 阶段时，利用 LangGraph 编写基于状态图的代码级精细编排是行业主流。
  * **状态**：贯穿整个运行循环的共享数据结构。
  * **节点**：代表特定 LLM 推理、工具执行或数据处理步骤的 Python 函数。
  * **条件边**：根据当前状态中的动态字段决定跳转方向。
  * **持久化快照**：在关键节点持久化快照，支持断点恢复、故障重试与人工审批。

#### 3.2.2 低代码与可视化平台
* **Dify**：将知识库自动导入、混合检索、Rerank 配置、大模型调用以及可视化工作流拓扑一站式集成。非常适合企业极速跑通 MVP，并无缝发布为标准 WebApp 或商业化 API。
* **FastGPT**：国内本地私有化部署、高并发企业客服与知识库高频选型的低代码平台。

### 3.3 技术栈三阶段演进

技术栈通常按 V1.0（快速上线，Dify 或 LangChain + pgvector）→ V2.0（精度优化，高精度解析 + 混合检索 + Reranker + Ragas/Langfuse）→ V3.0（Agent 化，LangGraph / LlamaIndex Workflows + GraphRAG + DSPy）三阶段演进。完整对照表见 [[06_LLMOps与可观测性运维]]，本篇不重复。

## 4 工具调用与工具链接

### 4.1 Function Calling 底层运行机制
Function Calling 是大模型从“只能说话”走向“能够干活”的关键桥梁，使 LLM 能够安全调用外部 API、数据库或计算内核。

```
                1. 注册注入工具 JSON Schema
                    ┌─────────────────┐
                    │  LLM 推理内核    │ ◄───┐
                    └────────┬────────┘     │
        2. 主动停止文本       │              │ 4. 结果回填 (Observation)
        输出 JSON 指令        ▼              │
                    ┌─────────────────┐     │
                    │  Python/Node.js │ ────┘
                    │  后端执行沙箱   │
                    └─────────────────┘
                    3. 安全执行 API/数据库/代码
```

整个闭环流转分为 4 个标准化步骤：
1. **工具注册**：向大模型发起请求时，在参数中注入开发者定义的工具列表。每个工具都用标准的 JSON Schema 描述，规定函数名称、入参类型、字段说明、必填项以及适用场景。
2. **意图识别与参数提取**：LLM 阅读上下文与工具描述，一旦识别到需要外部工具才能完成请求，便主动停止生成普通文本，转而输出符合 JSON Schema 的结构化调用指令（如 `{"name": "query_db", "args": {"user_id": 1024}}`）。
3. **外部执行**：宿主后端（Python 或 Node.js）捕获该 JSON 指令，在本地安全沙箱或内网服务器中真实执行数据库查询、调用业务 API 或运行脚本。
4. **结果回填**：后端把工具返回的真实数据封装为观察结果，拼接为新的 Prompt 上下文重新喂回 LLM，由 LLM 进行二次整合推理，生成最终回答或触发下一步调用。

### 4.2 Python 原生函数到 Agent Tool 的 5 大映射
在工程实现中，原生 Python 函数可通过以下 5 个维度无缝映射为 Agent 可识别的工具 Schema：

| Python 原生元素 | Agent Tool 映射组件 | 工程功能与作用 |
| ------ | ------ | ------ |
| **Python 函数** | **Agent 工具** | 包含真实业务逻辑的可执行代码实体 |
| **函数名称** | **工具标识** | 模型识别与路由调用的唯一索引标识 |
| **类型标注** | **输入 Schema** | 强类型约束模型的参数提取格式 |
| **文档字符串** | **工具描述** | 模型判断“何时及为何使用该工具”的 Prompt 依据 |
| **函数返回值** | **观察结果** | 工具执行完毕后写回模型上下文的真实数据 |

### 4.3 任务规划范式

#### 4.3.1 经典任务规划范式
* **思维链**：引导模型在给出最终答案前显式写出中间推理步骤（“先分析，后结论”）。
* **ReAct 范式**：最经典的 Agent 交互模式，拆解为 `Thought`（分析当前状态决定动作）➔ `Action`（触发工具与参数）➔ `Observation`（接收执行结果写回上下文）三步闭环。
* **Plan-and-Solve**：面对长周期任务，Agent 先在宏观层面拆解出子任务清单，再针对每个子任务逐一调用工具解决并汇总交验。

#### 4.3.2 自动推理与工具使用 ART
ART 是针对 Function Calling 的高阶调度机制：当系统接收到复杂新任务时，首先在预设的任务示范库中匹配最相近的多步推理与工具使用 Few-Shot 示范装载至 System Prompt。在执行阶段，当生成的下一个 Step 需要调用工具时，编排程序立刻暂停 LLM 文本生成，执行外部接口获取 Observation 并拼接入轨迹，随后唤醒 LLM 继续生成。

#### 4.3.3 观察反馈与自我纠错
工具执行抛出超时、参数错误或网络异常时，运行时捕获报错信息，封装为观察结果写回上下文，引导大模型分析错误原因并自行修改参数重试，实现闭环自纠错。

### 4.4 RAG 与工具的结合

把检索封装成工具之后，RAG 就从一条固定管道变成 Agent 的一项能力。常见有四类工具：

* **知识库工具**：封装向量检索与重排，接受查询与过滤条件，返回带来源的切片。
* **数据库工具**：把自然语言转成 SQL，用于统计、聚合与结构化查询。
* **Web 搜索工具**：补齐本地知识库没有的实时信息与公开资料。
* **计算与代码工具**：处理需要精确运算或真实执行的请求。

这样路由器就能按问题类型分发，而不是所有问题都先走一遍向量检索，分发维度见 [[04_查询工程与混合检索重排]] 第 2 章。

### 4.5 开放协议与安全控制
* **模型上下文协议 MCP**：由 Anthropic 提出的开放标准，通过统一的 Client-Server 协议，使 Agent 能够以标准接口无缝接入本地文件系统、数据库、GitHub 或外部 SaaS 服务。
* **运行终止与边界控制**：为防止 Agent 死循环或无限消耗 Token，运行时必须硬性设置终止条件：目标达成即输出最终答案、限制最大迭代轮数（如最多 10 轮）、设置 Token 与费用预算上限，以及安全护栏拦截。

## 5 状态与执行控制

持久化、断点续传与人工审批的生产落地细节见 [[06_LLMOps与可观测性运维]] 第 5 章。

### 5.1 状态与记忆

状态是贯穿一次任务执行的共享数据结构：当前问题、已召回的证据、已调用的工具、中间结论都挂在上面。按生命周期分两层：

* **短期记忆**：一次会话或一条执行线程内的状态，靠快照持久化，用于断点续跑与恢复。
* **长期记忆**：跨会话保留的用户偏好、历史结论等，通常落在独立的存储里。

LangGraph 的持久化层就是按这个划分设计的：用 checkpointer 保存线程内的图状态，用 store 保存跨线程的长期记忆。

### 5.2 串行与并行

* **串行**：步骤之间有依赖时必须按序执行，前一步的输出是后一步的输入。
* **并行**：多个子查询、多路检索、多个工具调用之间没有依赖时并行执行，整体延迟取决于最慢的一路。

判断标准很简单：步骤之间有没有数据依赖。没有依赖就并行，否则串行。

### 5.3 重试、降级与终止条件

* **重试**：工具超时、限流、参数错误时按退避策略重试，并把错误信息回填给模型让它改参数。
* **降级**：主模型或主通道不可用时切到备用模型、备用数据源，保证有兜底输出。
* **终止条件**：目标达成即退出；同时硬性限制最大迭代轮数、Token 与费用预算，防止死循环。

## 6 系统接口设计

### 6.1 输入与输出契约

编排层的入口要定义清楚：请求里放什么（问题、会话 ID、用户身份、过滤条件），出口返回什么（答案、引用来源、耗时）。用强类型模型约束，避免非法字段进入流水线。

### 6.2 中间状态与错误处理

每一步都应有明确的状态与错误语义：哪一步失败、失败原因、是否可重试、已重试几次。错误不要吞掉，要作为观察结果回填给模型或向上抛出。

### 6.3 可观测性接口

每次请求都要留下可回放的轨迹：输入、路由决策、检索结果、工具调用参数与返回、Token 消耗与耗时。轨迹的采集方式与平台选型见 [[06_LLMOps与可观测性运维]]。

## 7 Agentic RAG 与完整架构

### 7.1 Agentic RAG 自适应检索
传统 RAG 属于单次、被动的“检索 ➔ 生成”管道，而 Agentic RAG 将其升级为拥有自主大脑与自纠错回路的自适应系统：

```
[用户 Raw Query]
       │
       ▼
【1. 智能意图路由 Router】 ───► 区分 闲聊 / SQL查询 / 知识库检索 / 联网搜索
       │
       ▼
【2. 查询重构与变换】     ───► Multi-Query / Step-Back / HyDE 消除词汇鸿沟
       │
       ▼
【3. 多路检索与重排】     ───► 混合检索 + Reranker 召回候选 Chunks
       │
       ▼
【4. 评估与自纠错 Evaluation】
       ├── 信息完整 ─────────► 【5. 最终合成回答 Generation】
       └── 残缺 / 存在矛盾 ──► 触发二次补充检索 / 外部 Web Search 补位
```

* **动态路由**：分析查询意图，自主分发至本地向量库、SQL 数据库、知识图谱或外部 Web 搜索。
* **查询重写**：运用多查询扩展、退一步抽象或 HyDE 生成假设性文档向量，克服词汇鸿沟。
* **自纠错与反思**：模型主动评估召回切片的相关性与充分性，若发现信息残缺或冲突，主动发起二次或三次补充检索，规避事实漏检。

### 7.2 一张完整的 RAG Agent 架构图

```
用户请求
   ↓
【接口层】契约校验 · 认证 · 限流 · 流式输出
   ↓
【编排层】路由 Router → 规划 Planner → 状态管理 State → 循环与终止控制
   ↓
【能力层】知识库工具 · 数据库工具 · Web 搜索工具 · 代码执行工具
   ↓
【模型层】主模型 / 备用模型（降级）/ 轻量分类模型（路由）
   ↓
【支撑层】可观测性 Trace·Metrics·Logs ｜ 安全护栏 ｜ 权限隔离
   ↓
最终答案 + 引用来源
```

自上而下的含义是：请求进来 → 决定怎么做 → 调用能力 → 生成答案；支撑层横切所有层级，任何一层出问题都要能在轨迹里看到。

## 8 高级与前沿范式

### 8.1 GraphRAG
* **代表方案**：Microsoft GraphRAG、LightRAG、Neo4j、FalkorDB。
* **解决痛点**：传统向量检索只能回答局部事实细节（如“某条款的报销上限是多少”），无法回答涉及全局、宏观特征的抽象归纳提问（如“这 100 份合同中存在哪些共同的合规风险”）。
* **四大核心构建链路**：
  1. **实体关系抽取**：通过 LLM 批量扫描全部文档，提取所有的“实体-关系-属性”三元组，在底层构建全局实体知识图谱。
  2. **层级社区划分**：利用社区发现算法（如 Leiden 算法）对知识图谱按粒度由细到粗划分出多层级社区。
  3. **自动生成社区摘要**：利用 LLM 对各个层级社区全自动撰写社区摘要。
  4. **宏观全局聚合**：用户提问全局性问题时，检索系统直接在图谱社区摘要之上进行聚合推理，提供宏观视角的归纳回答。

### 8.2 Self-RAG 与 Corrective RAG

#### 8.2.1 Corrective RAG
C-RAG 引入了“检索质检员”机制，流程为：检索 → 评估 → 行动。
* **正确**：切片高度匹配，经精炼压缩后送给 LLM 生成。
* **错误或无关**：切片完全不匹配，丢弃内部检索结果，自动触发查询重写并发起 Web 搜索补位。
* **模糊**：内部检索与外部 Web 检索结合，混合送给 LLM 推理。

#### 8.2.2 Self-RAG
Self-RAG 引入可训练的反思标记，让模型在生成过程中动态自主调控：
* `[Retrieve]`：判断当前句子是否需要触发外部知识检索。
* `[IsREL]`：评估检索到的切片是否与问题相关。
* `[IsSUP]`：评估生成的回答是否被检索切片充分支持（防范幻觉）。
* `[IsUSE]`：评估回答对用户问题的有用程度。

### 8.3 多模态 RAG
解决传统纯文本 RAG 通过 OCR 丢弃系统架构图、趋势折线图、产品照片及表格视觉空间关系的痛点：原生视觉编码把 PDF 页面直接作为图像送入模型，跨模态对齐让图文向量可以直接比较。原理与模型选型见 [[03_向量化原理及选型]]。

### 8.4 多智能体协作架构
面对复杂系统，单一 Agent 容易出现上下文爆炸与指令稀释。多智能体系统通过“解耦与上下文隔离”实现工程化分工：
* **Router Agent**：诊断用户意图，精准分发给专职 Agent。
* **Research Agent**：集成联网 API 与学术接口，获取最新情报。
* **Coding Agent**：读取代码库，生成带强类型标注的示例代码。
* **Critic Agent**：进行独立交叉校验，检查回答的忠实度、引用合规性及格式约束。
* **Writer Agent**：汇总各子 Agent 的精炼产物，消除冲突后生成最终报告。

## 9 小结

* 编排要解决的是：多组件怎么串、分支怎么走、失败怎么办、状态存在哪里。
* Pipeline 把路径写死，Workflow 由代码决定分支，Agent 由模型自主决策；应当从最简单的形态起步。
* RAG 本身可以拆成三条流水线——数据摄取、检索、生成，条件路由决定一个问题该走哪条。
* 工具调用让检索从固定步骤变成一项能力，代价是必须引入状态、重试、降级与终止控制。
* 这些控制都要能在接口契约与执行轨迹上被看见，否则系统一出问题就无从定位。

> **编排的价值不在于把组件连起来，而在于让系统在出错、变慢、越权时仍然可控。**
