## 1 大模型 API 调用与基础交互

### 1.1 API、HTTP 与 SDK 的三层架构关系
模型服务通常通过分层结构对外提供功能：

* API（约定交互规范）：定义通信契约，规定请求需包含的字段、模型标识、响应数据格式及错误码表示。
* HTTP（传输层协议）：应用通过网络发送 HTTP 请求至远程服务器，借助 HTTPS 协议中的 TLS 机制保障加密传输。
* SDK（开发者封装工具）：将构造网络请求、序列化/反序列化数据、解析响应及错误捕获等细节进行代码级封装，简化调用逻辑。

### 1.2 模型调用参数与消息角色分类
一次完整的模型 API 调用不仅包含消息内容，还需配置生成参数与控制项：

常见的消息角色及其工程用途：
* system（系统角色）：设置助手的全局行为准则与设定，具体支持形态依赖 API 规范。
* developer（开发者角色）：设置由应用开发者所指定的行为约束，不同 API 接口对其支持方式存在差异。
* user（用户角色）：接收用户的实际输入，或作为上下文提示词传入模型。
* assistant（助手角色）：记录模型先前生成的历史响应内容。
* tool（工具角色）：承载外部工具函数执行后的返回结果，具体格式由 API 契约决定。

核心调用参数及其工程作用：
* model：指定所调用的模型名称，直接决定推理能力、计费价格、响应延迟及功能特性。
* temperature：调节生成文本的随机性倾向，影响输出的多样化程度，但不保证事实准确性。
* max_tokens（或类似限制）：限制单次响应的最大生成 Token 数，用于控制输出长度与单次调用成本，具体语义因 API 而异。
* timeout：设置单次网络请求允许等待的最长时间上限，防止系统无限期挂起。
* stream：控制是否以流式传输接收响应，允许向前端实时分块渲染生成内容。

其中，模型生成参数控制内容的生成逻辑，而网络请求参数控制应用层的超时、重试与连接接收机制。

### 1.3 外部 API 异常情况与防御策略
模型 API 属于外部网络依赖，必须在代码层建立针对异常情况的处理机制：

* 网络超时：设置有限等待时长，并依据退避策略决定是否发起重试。
* HTTP 429 或限流：遵循服务商给出的限流要求，实施指数退避重试。
* HTTP 5xx 服务端错误：判定是否属于短暂性服务故障，进行有边界的重试。
* API Key 无效：明确捕获认证错误并阻断流程，禁止无意义的反复重试。
* 返回内容为空或不完整：解析 Stop Reason（结束原因），校验输出是否满足业务完整性。
* 响应格式异常：对 JSON 等解析失败情况进行安全捕获，切勿将错误文本误当作有效结果输出。

## 2 提示词工程与结构化输出

### 2.1 提示词设计的六要素框架
设计高质量 Prompt 建议包含以下六个结构化要素：

* 角色与定位（Role）：明确模型扮演的具体身份（例如 Python 技术导师）。
* 任务目标（Task）：清晰说明本次调用的具体任务，避免模糊要求。
* 输入与上下文（Context）：输入用户问题、待处理文档以及必要的背景资料。
* 约束与边界（Constraints）：设定事实依据要求、禁选行为、适用边界以及信息缺失时的拒答策略。
* 输出格式（Output Format）：指定响应结构（如 Markdown、指定 Schema 的 JSON）。
* 验收条件（Acceptance Criteria）：规定合法输出的校验标准（例如引用标识必须真实对应来源）。

### 2.2 结构化输出技术与多层校验机制
为了让模型输出稳定适配下游程序，需结合模型能力与应用侧校验：

关键概念与作用机制：
* JSON Mode：要求模型生成合法的 JSON 格式字符串，能力由 API 接口提供支持。
* JSON Schema / Structured Outputs：严格定义字段名、数据类型及结构约束，部分 API 能够强行约束生成过程。
* Pydantic：在 Python 应用侧定义数据 Schema，执行类型检查、值域约束与字段解析。
* Prompt 指令：在提示词文本中明确告之模型输出格式的要求。

多层验证防护流：
1. Prompt 指令层：告诉模型应该返回何种数据结构。
2. API 约束层（JSON Schema）：在 Token 生成阶段强行约束合法结构。
3. 应用侧 Pydantic 校验层：在代码运行阶段验证解析后的 Python 对象是否符合类型定义。
4. 业务规则与证据验证层：检查文档来源是否存在、引用是否支持结论、业务约束是否达成。

## 3 上下文管理与对话状态维护

### 3.1 对话历史管理的四大策略
在多轮对话场景中，需通过策略平衡上下文完整性与 Token 消耗：

* 策略 1：保留最近 N 轮对话（滑动窗口）：只截取最近的 N 轮交互，超出部分直接丢弃，实现简单且成本可控。
* 策略 2：历史摘要提取：将较早的对话历史调用大模型提炼为简短摘要，上下文仅保留摘要与近期对话。
* 策略 3：按需检索历史：将历史消息持久化至数据库，在发生新提问时通过语义检索动态召回相关的历史上下文。
* 策略 4：结构化状态更新：将对话提取为固定的业务字段（如用户槽位信息），以结构化状态伴随对话推进。

## 4 RAG 全链路工程化流程

### 4.1 从文档导入到可检索知识的六步流水线
构建检索增强生成（RAG）系统需遵循以下标准链路：

* 第 1 步：文档获取（Ingestion）：对接网页、PDF、Word、Markdown 及数据库等原始数据源。
* 第 2 步：文档解析（Parsing）：提取原始文件中的文本、标题、表格、页码与排版元数据。
* 第 3 步：清洗与规范化（Cleaning & Normalization）：剔除无用噪声，统一字符格式，进行质量校验。
* 第 4 步：文本分块（Chunking）：将长文档按照语义切分为适合向量化与检索的切片（Chunk）。
* 第 5 步：向量化与索引构建（Embedding & Indexing）：计算切片向量，构建倒排索引或向量索引，保存元数据。
* 第 6 步：可检索知识（Searchable Knowledge）：形成支持高效召回、来源追溯与质量验证的知识库。

### 4.2 正则表达式（Regex）文本清洗原则
正则表达式适合处理规则明确、模式固定的文本规范化任务：

典型应用场景：
* 匹配并批量剔除页眉、页脚等重复固定文本。
* 规范化多余连续空格与非标准换行符。
* 提取或校验 URL、版本号、错误码等固定模式。

正则表达式的使用原则：
* Regex 缺乏语义理解能力，不能单纯依靠模式判断文本知识的重要性。
* 规则必须具备明确目标，避免盲目清洗导致有效内容丢失。
* 保持局部修改原则，避免全局误删。
* 必须配套单元测试样例，验证清洗前后信息的完整性。

## 5 文档解析、清洗与数据质量保障

### 5.1 解析、清洗与数据质量的三界限
必须清晰区分数据处理阶段的不同职责，避免混淆问题归因：

* 文档解析（Parsing）：将 PDF、HTML 等异构格式解析为标准文本与结构化数据。核心关注点在于内容提取的完整性。
* 文本清洗（Cleaning）：消除格式噪声，修补排版问题，规范文本表达。核心关注点在于内容干净且未误删关键数据。
* 数据质量检查（Data Quality Validation）：根据规则与统计指标，验证数据是否满足进入索引库的标准。核心关注点在于数据可用的证据充分性。

### 5.2 数据质量评估的五个维度
高质量数据需从以下维度进行审查：

* 完整性（Completeness）：正文是否为空，关键章节、页码或必要字段是否存在缺失。
* 正确性（Correctness）：提取文本是否与原文档一致，代码、数值、错误码是否受损。
* 可读性与结构（Readability & Structure）：段落与标题层级是否合理，列表、表格及代码块结构是否可读。
* 唯一性（Uniqueness）：是否存在非必要的重复页面、重复段落或冗余 Chunk。
* 可追溯性（Traceability）：是否完整保留了文档 ID、来源 URL、页码及章节层级等元数据。

### 5.3 数据处理异常处置策略
根据异常类型采取差异化的容错手段：

* 可恢复失败：针对临时网络抖动，执行有限次数的指数退避重试。
* 需变更处理模式的失败：针对扫描版 PDF 无法提取文本的情况，自动降级并路由至 OCR 识别组件。
* 极度无效输入：针对空文件或不受支持的格式，进行明确阻断并抛出异常。
* 无法自动判定的质量问题：记录异常上下文并沉淀至待人工审查队列。

## 6 检索、融合、重排序与上下文构建

### 6.1 RAG 核心组件职责划分
一个完整的 RAG 检索链路包含以下协作模块：

* Retriever（检索器）：负责从向量数据库或全文索引（如 FTS5）中召回候选 Chunk。验收重点为相关证据的召回率。
* RRF Fusion（融合器）：合并倒排检索与向量检索的多路排名。验收重点为 RRF 算法计算与去重准确性。
* Reranker（重排序器）：使用交叉编码器对候选 Chunk 进行精细化语义相关性打分。验收重点为高相关证据是否排在最前。
* Context Builder（上下文构建器）：扩展父级上下文、执行 Token 预算控制及证据组织。验收重点为结构完整且无冗余超限。
* Citation Validator（引用校验器）：校验引用 ID、来源映射与主张支持度。验收重点为引用的真实性与可追溯性。
* Answer Generator（答案生成器）：结合上下文证据驱动模型生成终极回答。验收重点为回答的准确性与事实依据。

### 6.2 文本分块（Chunking）评测与注意事项
分块质量不仅影响检索效果，也直接决定上下文构建的优劣。

检索评估指标（如 Recall@K、Precision@K、MRR、NDCG）衡量的是检索模块的综合表现，不能直接等同于分块质量的证明。评测分块时需同步审查：
* 核心概念与关键定义是否被切断。
* 代码块与表格数据是否保持完整。
* 切片之间是否引入大量重复内容。
* 切片粒度是否兼顾了精确检索与信息完整性。

### 6.3 上下文构建与 Token 预算管理
上下文构建阶段需对重排序后的 Chunk 进行二次加工：

上下文构建四大核心动作：
* 去重（Deduplication）：针对多路检索返回的相同或高度重合 Chunk，仅保留一份文本并合并元数据。
* 补充必要上下文（Context Expansion）：当子 Chunk 缺乏主语或前置背景时，依据 parent_chunk_id 关联并引入父级段落，但需控制扩展幅度。
* 控制上下文预算（Context Budgeting）：Token Budget（Token 预算）指预先分配给各模块的 Token 容纳上限。需为系统指令、历史对话、检索证据及生成输出设定严格配额。
* 组织证据顺序（Evidence Ordering）：按相关性分级或按逻辑推演顺序排列证据，保持元数据标注，避免破坏原文逻辑。

### 6.4 引用校验的三层架构与实现流
引用校验用于确保模型的回答具有据可查：

引用校验的三层检查：
* 引用存在性：通过程序校验答案中的引用 ID 或 URL 是否在检索返回的证据库中。
* 引用相关性：结合规则或轻量模型，判断引用段落是否与被引用的语句主题相关。
* 引用支持性：深度校验引用的证据内容是否在逻辑上真正支持该关键主张。

实用引用校验流程：
1. 模型生成带引用标记（如 [1]）的候选答案。
2. 程序解析引用标记，校验 ID 是否合法存在于本次检索集。
3. 提取对应 Chunk 正文与元数据信息。
4. 验证关键主张与证据段落的一致性。
5. 对缺乏证据支持的主张进行二次修正、标注不确定性或触发拒答。

系统模块的推荐实现与验证顺序为：检索器 -> Reranker -> 上下文构建器 -> 引用校验链路。

## 7 RAG 评估体系：检索、答案与引用指标

### 7.1 RAG 质量的三层评估维度
评估 RAG 系统需拆解为三个独立层次：

* 第一层：检索质量（Retrieval Quality）：评估系统是否成功召回回答问题所需的正确证据（指标：Recall@K, Precision@K, MRR, NDCG）。
* 第二层：答案质量（Answer Quality）：评估模型是否基于上下文生成了正确、切题的文本（维度：正确性、完整性、相关性、忠实性/依据充分性）。
* 第三层：引用质量（Citation Quality）：评估答案引用的准确性与支持度（维度：可追溯性、引用准确性、主张支持率、引用覆盖率）。

### 7.2 评测数据集构建规范
评测需建立在固定且高质量的基准数据集（Benchmarking Dataset）之上：

数据集字段设计：
* question：测试提问文本。
* relevant_chunk_ids：人工标定的标准相关 Chunk ID 集合。
* reference_answer：参考答案或核心要点。
* required_evidence：回答该问题所必须依赖的关键事实证据。
* source_ids：相关证据对应的原始文档 ID。
* expected_behavior：预期系统行为（如正常回答、拒答等）。

数据集维护注意事项：
* 保持提问固定，以便跨版本公平对比。
* 标注证据需经过人工严格核验，不可直接相信模型自建数据。
* 覆盖标准问题、专业术语、多跳复杂问题、无答案问题及冲突文档场景。
* 对数据集、知识库、Embedding 模型及 Prompt 进行同步版本化管理。
* 严禁将评测集泄漏至训练语料或提示词中。

### 7.3 四大核心检索指标解析
* Recall@K（前 K 召回率）：衡量排名前 K 的结果中找回了多少比例的已知相关证据。分母为全部已知相关证据总量。
* Precision@K（前 K 精确率）：衡量排名前 K 的结果中真正相关的比例。分母为当前提取的 K 个结果数。
* MRR（平均倒数排名）：关注每个问题第一个相关结果出现的排名位置倒数，衡量首个有效证据的靠前程度。
* NDCG@K（归一化折损累计增益）：综合考虑结果的相关性等级与排序位置，适合评估 Reranker 对整体候选列表的重排效果。

检索指标适用场景汇总：
* Recall@K：核心评估找回相关证据的能力，适用于调整分块策略、检索算法与候选集规模。
* Precision@K：核心评估前 K 结果的噪声控制情况，适用于确定送入大模型的上下文规模。
* MRR：核心评估首个有效证据的排名靠前程度，适用于衡量用户快速获取关键信息的体验。
* NDCG@K：核心评估列表整体排序的合理性，适用于对比 RRF 融合与 Reranker 模型的效果。

### 7.4 答案质量与引用质量的评估维度
答案质量四大维度：
* Correctness（正确性）：检查答案中的事实与结论是否客观准确。
* Completeness（完整性）：检查答案是否覆盖了问题要求的所有核心要点。
* Relevance（相关性）：检查输出内容是否紧扣用户提问，无答非所问。
* Faithfulness / Groundedness（忠实性/依据充分性）：检查答案中的所有主张是否均能从提供的上下文证据中推导得出。

引用质量四大指标：
* Citation Validity（引用有效性）：引用 ID 或来源 URL 是否真实存在并指向正确文档。
* Citation Relevance（引用相关性）：被引用的切片文本与对应语句是否主题相关。
* Claim Support Rate（主张支持率）：答案中附带引用的主张占所有需依据主张的比例。
* Citation Coverage（引用覆盖率）：应附带引用的主张中实际成功附带有效引用的比例。

标准 RAG 评测执行流程：固定测试集与环境 -> 评测检索指标 -> 评测生成答案 -> 评测引用质量 -> 失败案例归因分析 -> 版本对照与回归测试。

## 8 RAG 安全防护与可观测性体系

### 8.1 RAG 五大安全风险与控制措施
RAG 系统面临的特有安全挑战及应对手段：

* 提示词注入（Prompt Injection）：恶意指令隐藏于用户输入或检索到的第三方文档中。控制措施：将检索文本视为不可信数据，限制模型的指令跟随边界，严禁将文档拼接为可执行代码。
* 越权检索与数据泄露：多租户环境下缺乏权限隔离导致越权。控制措施：由服务端依据认证身份在检索层强行施加授权过滤条件，绝不信任客户端传入的 user_id。
* 恶意文档与数据投毒：导入库的文档包含虚假事实或恶诱导指令。控制措施：建立数据源准入校验与内容安全审计。
* 不安全的数据获取（SSRF）：获取外部 URL 时发起内网攻击或遭遇超大文件。控制措施：严格校验协议、目标 IP 范围、重定向路径，设置超时与响应体大小上限。
* 日志与追踪泄露：日志或 Trace 记录了敏感数据。控制措施：实施数据最小化采集、字段脱敏、日志访问控制及定期保留清理策略。

### 8.2 可观测性三大支柱在 RAG 中的实践
可观测性通过 Logs、Metrics 和 Traces 监控内部运行状态：

* Logs（日志）：记录具体事件的发生（如：检索模块返回 0 个结果），主要用于单点事件诊断。
* Metrics（指标）：持续聚合数值以描述系统整体状况（如：检索失败率上升至 15%），主要用于发现趋势异常。
* Traces（追踪）：记录请求在各组件间的流转链路与耗时（如：文档获取 50ms -> 检索 80ms -> LLM 调用超时），主要用于瓶颈与故障定位。

RAG 监控指标分类：
* 系统可靠性：请求成功率/失败率、超时率、重试率、降级与拒答次数。
* 性能指标：端到端延迟、各阶段分级延迟（P50/P95/P99）、并发请求量。
* 检索与答案质量：检索空结果比例、召回率/准确率指标、答案忠实度、引用支持率。
* 成本指标：输入/输出 Token 数、单次请求模型成本、成功回答平均成本。

### 8.3 RAG 故障排查六步法与演进路线
结构化排障流程：
1. 确认请求状态：检查请求是否被正常接收，输入校验是否通过，是否触发超时、限流或权限拒绝。
2. 检查检索候选：确认候选集是否为空或缺失相关 Chunk。若缺失，排查解析、切片、索引或检索参数。
3. 检查排序与上下文：排查相关 Chunk 是否被 RRF 或 Reranker 过滤，上下文是否因 Token 预算超限而被截断。
4. 检查模型调用：检查 API 请求是否超时、报错，输入是否超长，模型是否返回有效输出。
5. 检查答案与引用：检查模型是否存在误读、幻觉或主张与引用错配。
6. 归因修复与回归复测：定位根因并修复，使用原始失败样例执行回归测试。

安全与可观测性三级演进路线：
* 第一层（基础控制，优先级高）：配置外部 URL 防防 SSRF；设定网络与模型调用超时；日志不记录 API Key 与完整敏感文本；区分失败类型；校验引用映射。
* 第二层（故障定位，尽早实施）：使用统一 request_id 贯穿全链路；记录分阶段耗时与错误分类；记录模型版本、Token 数与检索参数；建立失败案例库。
* 第三层（高级扩展，按需推进）：引入分布式链路追踪平台；针对多租户实施细粒度隔离与审计；为 Agent 工具调用增加权限校验与停止机制。
