架构设计的核心，是提前决定职责边界与协作关系，从而降低后续修改的成本和风险。
### 1.2 模块划分的三大原则
划分模块时需要遵循以下三条基本原则：
* **单一职责**：一个模块只负责一个明确的功能领域。
* **高内聚、低耦合**：
  * **高内聚**：一个模块内部的代码围绕同一类职责展开。
  * **低耦合**：模块之间尽量减少不必要的依赖，降低一处修改对其他部分的影响。
* **明确模块接口**：模块之间通过清晰定义的规范进行交互。

### 2.1 Python + FastAPI 四层架构
对于基于 Python 与 FastAPI 构建的 AI 应用，通常采用以下四层结构。架构的核心要求是各层职责清晰、依赖方向合理：

### 2.1.1 API 层
* **定位**：系统的入口层。
* **职责**：接收 HTTP 请求、校验请求参数、调用业务逻辑、组织 HTTP 响应。
* **适合内容**：FastAPI 路由、请求和响应模型、HTTP 状态码与响应格式、与接口协议直接相关的参数校验。
### 2.1.2 Service 层
* **定位**：业务服务层，业务流程的组织者。
* **职责**：组织业务流程，协调多个模块完成一项业务任务。
* **适合内容**：协调多个模块、组织业务步骤、控制流程何时继续或终止、将业务处理结果交给 API 层。
### 2.1.3 Domain 层
* **定位**：领域层，核心业务规则的载体。
* **职责**：表达核心业务规则、领域对象和不应被技术细节左右的业务约束。
* **使用条件**：并不是所有项目都必须包含该目录，它适合放置相对独立于技术实现的核心业务规则。
### 2.1.4 Infrastructure 层
* **定位**：基础设施层，具体技术实现的封装。
* **职责**：封装数据库访问、外部 API、文件读取、网页抓取和向量库操作等底层技术细节。
* **适合内容**：使用 httpx 访问网页、使用 HTML 解析库提取正文、调用大模型 API、使用 SQLite 执行数据库读写、使用 Chroma 执行向量检索。

在实际简化架构中，Service 层可以直接使用基础设施提供的接口。Domain 层是否单独存在，取决于业务复杂度。

除了上述核心四层外，实际开发中还会遇到其他常见的分层概念：

| **名称** | **中文解释** | **主要职责** |
| ------ | ------ | ------ |
| Presentation 层 | 表现层 | 面向用户或客户端的交互；在 Web 后端中，有时与 API 层职责重叠 |
| Application 层 | 应用层 | 编排用例、协调业务流程；有些架构将它与 Service 层分开 |
| Repository 层 | 仓储层 | 封装业务数据的读取和保存接口 |
| Persistence / Data Access 层 | 持久化 / 数据访问层 | 执行数据库查询、更新、事务等具体操作 |
| Integration / Adapter 层 | 集成 / 适配层 | 将外部 API、第三方系统或不同接口转换成内部可用的形式 |
这些名称不一定都代表独立的一层，常用于具体架构模式下的职责划分。

## 4 模块依赖与依赖倒置原则

### 4.1 依赖关系与依赖方向

  * **依赖抽象**：只要求对方提供约定好的能力。
  * **依赖具体实现**：直接绑定某个具体类、库或服务的细节。
* **依赖方向**：指一个模块为了编译、理解或运行其代码，需要了解另一个模块的定义或具体实现时，依赖关系指向哪里。依赖方向决定了一个模块的变化会向哪些模块传播。

降低耦合的一种方式是让业务层依赖一个稳定的接口，而不是直接依赖具体实现。

### 4.2 限制依赖方向的三大原因
1. **避免技术细节侵入业务逻辑**。
2. **避免模块形成循环依赖**。
3. **让测试更容易隔离**。

### 4.3 依赖倒置原则
高层不必依赖低层的具体实现：
* 高层模块不应该直接依赖低层模块的具体实现。
* 高层和低层都应该依赖抽象。
* 抽象不应该依赖具体实现，具体实现应该符合抽象的约定。

## 5 模块接口与边界设计

### 5.1 模块接口与封装
* **模块接口**：指一个模块向其他模块提供的、供它们使用的能力和约定。
* **封装**：模块对外提供必要的能力，同时隐藏不需要调用方了解的内部细节。

### 5.2 接口设计的四大考量维度
设计接口时，至少考虑四个方面：
1. **输入**：调用方需要提供什么？
2. **输出**：返回结果究竟代表什么？
3. **错误**：失败时会发生什么？
4. **副作用**：调用会改变什么？

### 5.3 模块边界与三大常见设计误区
* **模块边界**：哪些职责和实现属于这个模块，哪些职责属于其他模块，以及模块之间通过什么方式协作。
* **接口设计中最常见的三个问题**：
  1. **暴露太多内部细节**。
  2. **接口承担太多职责**。
  3. **为了通用而过度抽象**。
