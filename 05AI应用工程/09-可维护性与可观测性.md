## 1 可维护性与可观测性的核心定义

### 1.1 可维护性与可观测性的区别与联系
在软件工程与 AI 应用开发中，可维护性与可观测性分别从静态开发与动态运行两个视角度量系统的质量。

| **概念维度** | **关注焦点** | **核心定义** |
| ------ | ------ | ------ |
| 可维护性 | 静态代码与架构 | 当需求变化、出现缺陷或需要增加功能时，开发者能否以合理的成本和风险理解、修改、验证代码。 |
| 可观测性 | 动态运行与状态推断 | 能否根据程序产生的运行信息（日志、指标、追踪等），推断系统内部发生了什么。 |

## 2 工程文档体系与单一事实来源

### 2.1 常见的六类项目文档
高质量的文档体系是保障项目可维护性的基础。根据服务对象与解决问题的不同，常见的项目文档分为六类：

| **文档类型** | **服务对象与解答问题** | **主要记录内容** |
| ------ | ------ | ------ |
| README.md | 面向使用者、新开发者与贡献者，解答“项目是什么？怎么运行和使用？” | 项目目标、主要功能、技术栈、快速启动方法、基本使用方式、项目状态。 |
| 架构文档 | 面向开发者与架构师，解答“系统由哪些部分组成？为什么这样设计？” | 模块职责、依赖方向、核心数据流、关键设计决策。 |
| 接口契约 | 面向服务调用方，解答“调用方可以传什么？会得到什么？失败时会怎样？” | 输入、输出、错误语义、副作用和兼容性要求。HTTP API 可使用 OpenAPI 描述。 |
| 开发规范 | 面向内部开发者，解答“开发时必须遵守什么规则？” | 代码格式、命名约定、测试要求、代码质量工具配置、开发流程。 |
| AGENTS.md | 面向 Coding Agent（如 Codex），解答“AI 在仓库工作时需遵守什么？” | 项目结构、开发约定、验证命令、数据库迁移要求及敏感配置处理等限制。 |
| 决策记录（ADR） | 面向团队与后续维护者，解答“为什么这样设计，而不是采用另一种方案？” | 重要方案的背景、候选方案、取舍分析、最终决定及后果。 |

### 2.2 单一事实来源（SSOT）原则
单一事实来源（Single Source of Truth，SSOT）的核心思想是：同一项信息在系统中应有且仅有一个明确的权威来源。其他文档或模块如果需要使用该信息，应采取引用、概述或链接的方式，避免维护互相独立的同名副本，从而消除因信息不同步导致的维护冲突。

### 2.3 AGENTS.md 的核心编写内容
为确保 AI Coding Agent 在项目仓库中能够精准遵循项目约束，AGENTS.md 应明确包含以下五类关键信息：
*  项目背景：简述项目目标与主要技术栈。
*  代码结构：列出关键模块的职责定位与依赖边界。
*  开发约定：说明 Python 版本、代码格式化规则、命名要求等。
*  验证方式：提供运行单元测试、Lint 检查、格式检查的实际终端命令。
*  重要约束：规定修改数据库结构时的迁移流程、敏感配置与密钥的处理规范等。

### 2.4 文档联动更新时机与审查模板
文档不是项目开发结束后补写的静态附件，而必须作为代码变更的一部分同步迭代：
*  修改接口时：同步更新接口契约、调用方代码、相关测试用例及 API 文档。
*  修改数据库结构时：同步更新迁移文件、数据迁移逻辑、相关测试及架构说明。
*  修改模块边界或技术方案时：同步检查架构文档和架构决策记录（ADR）的准确性。
*  修改开发命令或工具配置时：同步更新 README、AGENTS.md 及 CI 配置中的命令。

在审查代码变更对文档的影响时，可使用以下 Prompt 模板指导 Agent 检查：

```text
请检查本次实现是否改变了项目文档所描述的行为、接口、架构或开发命令。

- 只更新受本次变更影响且确实过期的文档。
- 不要复制已有内容或创建没有必要的新文档。
- 确保文档中的命令、接口和技术信息与当前项目一致。
- 如果发现文档与代码存在冲突，说明冲突内容及建议处理方式。
- 在完成报告中列出更新的文档及更新原因。
```

## 3 日志设计与应用统一配置

### 3.1 日志的基本定义与统一配置策略
日志是程序在运行过程中按时间顺序产生的事件记录。在项目中仅仅调用 logging.getLogger(__name__) 无法自动建立全局统一的日志管理策略。

日志应在应用入口处（如 FastAPI 应用启动阶段）进行集中配置，统一明确以下核心要素：
*  最低日志级别（如 INFO、DEBUG、ERROR）。
*  日志输出位置（控制台标准输出或特定文件系统）。
*  日志格式（时间戳、日志级别、模块名称及具体的消息文本）。
*  日志结构化格式（如生产环境评估采用 JSON 格式）。
*  日志文件轮转（Log Rotation）与保留策略（当写入文件系统时）。

### 3.2 个人项目的日志落地建议
对于初期的个人项目，建议采用标准库 logging 将日志直接输出到控制台（Console），优先保障关键字段（时间、级别、模块、事件上下文）的清晰易读。当项目演进至需要跨服务检索、集中分析或长期监控时，再评估引入结构化日志和日志集中收集平台。

## 4 可观测性的三大支柱

### 4.1 日志、指标与链路追踪的概念映射
构建完整的可观测性系统依托于三大支柱，各自承担不同的诊断视角：

| **支柱名称** | **数据形态** | **核心作用与应用场景** |
| ------ | ------ | ------ |
| 日志（Logs） | 离散的事件记录 | 记录特定时刻发生的具体事件及其详细上下文，用于特定异常的精准定位。 |
| 指标（Metrics） | 可聚合的数值数据 | 持续统计与聚合一段时间内的数值（如成功率、延迟、QPS），观察系统整体运行状况与趋势。 |
| 链路追踪（Traces） | 跨组件的调用链条 | 记录单次请求在分布式或多模块系统中的完整传递路径，展示各个环节的耗时分布。 |

## 5 故障排查与修复验证流程

### 5.1 假设驱动排查的四步循环
排查系统故障时，盲目修改代码或无目的尝试会带来极大风险。专业的排查流程遵循以下四步：
1. 先确认事实，不要急着修改代码：收集错误现象与相关上下文证据。
2. 利用证据缩小问题范围：牢记“错误出现的位置，不一定是根因所在的位置”。异常堆栈展示的是函数调用路径，最后一行代码仅代表触发异常的位置，未必是问题根源。
3. 假设驱动排查循环：
   *  根据现有证据提出一个可验证的假设。
   *  选择能够区分不同原因的检查手段。
   *  执行检查并记录实际结果。
   *  根据结果保留、修正或排除假设。
   *  当根因得到充分证据支持后，再设计修复方案。

### 5.2 修复后的四项验证标准
故障现象消失并不意味着修复完全正确。修复完成后，必须通过以下四项验证：
*  复现测试（Reproduction Test）：验证原先失败的场景当前是否能够稳定通过。
*  边界测试（Boundary Test）：检查相邻输入、异常边界输入是否依然能被正确处理。
*  回归测试（Regression Test）：确认本次修复未破坏系统中原有的其他正常功能。
*  状态验证（State Verification）：核实数据库记录、任务状态及外部副作用是否完全符合预期。

### 5.3 故障调查 Prompt 模板
当需要 Agent 协助排查故障时，可使用以下指令约束排查过程：

```text
请调查当前故障，先不要修改代码。

1. 复现或确认故障现象，记录实际结果。
2. 检查相关日志、异常堆栈、调用链和代码变更。
3. 提出可能原因，并用代码或运行证据逐一验证。
4. 明确指出已确认的根因；若证据不足，说明还缺少什么，不要把猜测当成结论。
5. 报告故障影响范围、建议修复方向及需要补充的测试。

不要进行无关重构，不要通过删除测试、弱化断言或隐藏异常来让问题消失。
```

## 6 运行状态、健康检查与告警

### 6.1 三类健康检查机制
健康检查（Health Check）是系统暴露的探针机制，用于判断服务是否处于正常的运行状态。在 Web 应用中通常通过专门的 HTTP 端点实现，分为三类：

| **健康检查类型** | **检查目标与回答的核心问题** |
| ------ | ------ |
| 存活检查（Liveness Probe） | 回答“应用进程是否还活着，是否仍然能够正常运行？”若失败通常触发容器重启。 |
| 就绪检查（Readiness Probe） | 回答“应用现在是否已经准备好接收业务流量？”若失败则暂时切断流量分发。 |
| 依赖健康检查（Dependency Check） | 回答“数据库、外部 API、缓存等下游依赖服务是否正常？”评估依赖项的可用性。 |

### 6.2 告警的作用与触发逻辑
健康检查解决的是“当前检查是否通过”的问题；而告警（Alerting）解决的是“系统是否出现了需要人工或自动化流程立即采取行动的问题”。告警阈值应基于明确的健康检查指标与运行数据设定，避免无效告警打扰。

## 7 日志、监控与隐私安全防护

### 7.1 可观测性数据安全风险
日志、指标与链路追踪数据不仅会在控制台输出，还可能写入磁盘文件、上传云端平台、转发至监控系统或长期保存在备份中。这些数据一旦离开应用边界，就会面临越权访问与数据泄露风险。

### 7.2 隐私安全五项基本原则
在可观测性建设中，必须严格遵守以下五项安全原则：

| **原则名称** | **核心要求与实现规范** |
| ------ | ------ |
| 数据最小化 | 只采集和保留故障排查与系统监控所必需的数据，拒绝过度采集。 |
| 脱敏与秘密管理 | 严格区分“删除敏感字段”（不写入 token）与“替换敏感字段”（记录 token=[REDACTED]）。避免依赖事后脱敏，必须在日志构造时拦截敏感数据；API Key 等凭证严禁硬编码或写入日志，必须通过环境变量或秘密管理机制加载，并禁止提交 `.env` 文件。 |
| 访问控制 | 对日志、监控及追踪平台的存储数据配置严格的身份鉴权与访问权限管控。 |
| 保留期限 | 制定明确的数据保留策略，到期自动清理或归档，避免敏感历史数据无限期滞留。 |
| 指标与追踪隐私保护 | 限制指标与链路追踪中的敏感数据暴露，进行标签与属性安全管控。 |

### 7.3 指标、追踪与异常堆栈的安全管控
针对三类特定可观测性数据的安全要求如下：
*  Metrics 指标：指标标签（Labels）必须使用有限且稳定固定的取值集合，严禁将动态用户输入或敏感字符串作为标签，防止高基数（High Cardinality）问题与数据泄露。
*  Traces 链路追踪：只记录诊断所需的属性；自动剥离 URL 中的敏感查询参数；严禁默认记录完整的请求体（Body）与响应体；严格控制追踪数据的查看权限。
*  异常堆栈（Stack Traces）：异常消息可能包含内部文件路径、SQL 查询串、URL 密钥或第三方接口返回的敏感内容。严禁将原始异常堆栈直接返回给前端用户或无差别公开，应对用户响应简洁安全的错误提示，将诊断细节留存在受控的服务端日志中。

## 8 AI Coding Agent 的代码审查与问题修复

### 8.1 可维护性与可观测性审查维度
对 AI 生成的代码进行审查时，需从可维护性与可观测性两个视角开展全面评估：

| **审查视角** | **细分检查维度** | **重点审查内容** |
| ------ | ------ | ------ |
| 可维护性审查 | 职责边界 | 模块职责是否单一，依赖方向是否合理，是否存在无意义的抽象。 |
| 可维护性审查 | 可读性与影响范围 | 代码命名是否准确，复杂度是否合理，修改是否会带来非预期的连锁反应。 |
| 可维护性审查 | 文档与项目知识 | 代码变更是否同步更新了相关的架构文档、接口契约及 Agent 指令。 |
| 可观测性审查 | 日志（Logs） | 是否记录关键事件、错误类型、请求标识、耗时及状态；是否存在冗余或模糊日志。 |
| 可观测性审查 | 指标（Metrics） | 成功率、错误率、延迟等统计口径是否准确；标签是否存在高基数风险。 |
| 可观测性审查 | 链路追踪（Traces） | 跨模块调用时能否有效关联请求上下文；是否按需引入追踪。 |
| 可观测性审查 | 健康检查与告警 | 健康检查端点是否符合实际目的；告警是否会因短暂波动误报。 |
| 可观测性审查 | 隐私与安全 | 日志、指标、追踪中是否包含凭证、用户敏感输入或未经脱敏的 URL。 |

### 8.2 验证证据的三要素
评估 AI 生成的代码质量不能仅看静态代码，必须要求提供三要素证据：
1. 代码证据：确认逻辑实现本身符合预期约束。
2. 测试证据：确认单元测试与集成测试覆盖了关键行为与异常路径。
3. 运行证据：确认实际运行过程中输出了预期的结果与合规的日志。

### 8.3 AI 审查 Prompt 模板
可使用以下指令让 Agent 执行可维护性与可观测性审查：

```text
# 任务：审查可维护性与可观测性

请审查当前项目的可维护性、可观测性和相关安全风险。先不要修改代码。

重点检查：
1. 模块职责、依赖方向、重复逻辑和变更影响范围。
2. 日志的事件、级别、上下文、重复记录和异常处理边界。
3. 指标、链路追踪、健康检查与告警是否满足项目实际需要，是否存在过度设计。
4. 日志、指标和追踪数据是否可能泄露凭证、用户输入、文档内容或敏感 URL。
5. 相关测试、配置和文档是否完整且与实现一致。

要求：
- 结合实际代码、调用链、配置和测试给出证据，不要只列通用建议。
- 区分已确认的问题、潜在风险和优化建议。
- 按严重程度和修复优先级排序，说明影响、依据及建议修复方向。
- 不要为了增加监控能力而默认引入新依赖或复杂基础设施。
- 不要将缺少某项监控工具直接认定为缺陷；先判断项目是否真的需要。
- 最后给出建议优先处理的最小任务列表及各任务的验证方式。
```

### 8.4 AI 排错与修复的五步工作流
当 Agent 参与代码排错与修复时，应严格遵循五步规范工作流：
1. 第一步：先控制风险，再确认事实：防止错误扩散，优先复现并记录异常证据。
2. 第二步：划分问题类型：区分是业务逻辑缺陷、外部依赖故障、配置错误还是性能问题。
3. 第三步：确定模块职责，避免重复处理：明确应由哪一分层修复问题，防止在多个层级进行冗余处理。
4. 第四步：确定最小充分修复：只针对根因进行针对性修复，避免附带无关的大范围重构。
5. 第五步：用证据判断是否完成：通过复现测试、边界测试、回归测试与状态验证确认修复成功。
