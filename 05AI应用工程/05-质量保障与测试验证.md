
## 1 软件测试的核心层级与分类

### 1.1 单元测试（Unit Test）
* 概念定义：验证一个相对独立的代码单元是否按预期工作。
* 核心关注点：局部逻辑是否正确。
* 经典案例：测试 extract_main_text() 函数是否能从给定 HTML 中提取正文，或者在没有正文时按约定返回结果。
* 特征维度：测试范围通常较小；外部依赖通常隔离；执行速度通常最快；故障定位通常较容易；常见风险在于测试断言太弱。

### 1.2 集成测试（Integration Test）
* 概念定义：验证多个组件或系统边界之间能否正确协作。
* 核心关注点：组件之间的接口、数据和协作是否正确。
* 经典案例：测试 Service 层是否能调用文档获取模块、解析返回内容，并正确将学习记录写入真实的测试数据库。
* 特征维度：测试范围为一组相关组件；外部依赖按目标选择真实或模拟依赖；执行速度居中；故障定位难度中等；常见风险在于接口或数据传递错误。

### 1.3 端到端测试（End-to-End Test，E2E）
* 概念定义：从接近真实用户的入口出发，验证一个完整业务流程是否达到预期结果。
* 核心关注点：完整业务流程是否真正可用。
* 经典案例：通过 HTTP API 提交官方文档 URL，检查系统最终返回的回答、来源和学习记录状态。
* 特征维度：测试范围从入口到最终结果；外部依赖尽量覆盖关键真实链路；执行速度通常较慢；故障定位通常较困难；常见风险在于环境复杂、成本高、结果不稳定。

### 1.4 三种测试层级的综合对比

| **对比维度** | **单元测试** | **集成测试** | **端到端测试** |
| ------ | ------ | ------ | ------ |
| 主要目标 | 验证独立代码单元的行为 | 验证模块之间的协作 | 验证完整业务流程 |
| 测试范围 | 通常较小 | 一组相关组件 | 从入口到最终结果 |
| 外部依赖 | 通常隔离 | 按目标选择真实或模拟依赖 | 尽量覆盖关键真实链路 |
| 执行速度 | 通常最快 | 居中 | 通常较慢 |
| 故障定位 | 通常较容易 | 中等 | 通常较困难 |
| 常见风险 | 测试断言太弱 | 接口或数据传递错误 | 环境复杂、成本高、结果不稳定 |


## 2 单元测试的深入实践：模式与隔离

### 2.1 AAA 模式与参数化测试
单元测试通常围绕一个相对独立的代码单元展开，具体包含以下三个核心步骤（简称 AAA 模式）：
1. 准备（Arrange）：准备输入和必要的前置条件。
2. 执行（Act）：调用被测代码。
3. 断言（Assert）：检查实际结果是否符合预期。

当多组输入使用同一套判断逻辑时，可以使用 `pytest.mark.parametrize` 避免重复编写结构相似的测试函数。
### 2.2 测试隔离与 Mock（模拟对象）
* 测试隔离（Test Isolation）：尽量控制测试环境和依赖，让当前测试能够专注验证自己负责的行为。
* Mock（模拟对象）：测试中使用的一种替代对象，用来模拟某个依赖的行为，让测试能够控制它的输入、输出或异常。
## 3 集成测试的四大重点检查维度

### 3.1 接口契约一致性
重点检查一个模块输出的数据结构、类型和字段是否符合下游模块的要求。
例如：解析模块输出的 content 是否能被 Service 层正确读取。

### 3.2 调用顺序与协作关系
重点检查模块是否按正确顺序调用，以及必要的参数是否正确传递。
例如：先提取正文，再将正文交给 LLM，而不是把原始 HTML 当作正文发送。

### 3.3 数据传递与持久化
重点检查一个模块处理后的数据能否被另一个模块正确使用并持久化保存。
例如：学习记录写入数据库后，重新查询仍然能得到正确的标题和状态。

### 3.4 跨模块错误处理
重点检查底层模块失败后，上层是否能获得符合约定的错误，而不是误报成功或留下错误状态。
例如：网页获取失败时，系统不应该把学习记录标记为成功。


## 4 测试数据与测试环境管理

### 4.1 核心概念定义
* 测试数据（Test Data）：测试过程中使用的输入、记录和预期结果。
* 测试环境（Test Environment）：运行测试所依赖的配置、数据库、文件、网络和其他资源。

### 4.2 测试数据的四种常见类型
1. 正常数据（Valid Data）：符合预期格式、可以正常处理的数据。例如包含标题和正文的标准 HTML。
2. 边界数据（Boundary Data）：位于规则边缘的数据。例如空字符串、只有一个字符的正文、达到长度限制的文本。
3. 非法数据（Invalid Data）：不符合接口要求的数据。例如 URL 为空，或者传入的参数类型不符合约定。
4. 特殊业务数据（Domain-specific Data）：符合业务实际特点的数据。例如重复导入同一文档、中文技术文档、超长文章和正文中包含代码块的网页。

### 4.3 防止测试污染的三种做法

| **方法** | **做法** | **适用场景** |
| ------ | ------ | ------ |
| 独立测试数据库 | 测试使用专用数据库，不碰真实用户数据 | 数据库集成测试 |
| 每次测试前初始化 | 创建所需数据，或清理旧数据 | 需要可预测初始状态的测试 |
| 事务回滚 | 测试结束后回滚数据库事务 | 数据库支持且测试架构允许的场景 |


## 5 代码覆盖率的衡量与分析

### 5.1 代码覆盖率的定义
代码覆盖率衡量的是：运行测试时，有多少被统计的代码被执行过。

### 5.2 语句覆盖率与分支覆盖率
* 语句覆盖率：可以帮助发现从未被测试执行到的代码，但它不能证明执行过的代码得到了正确验证。
* 分支覆盖率（Branch Coverage）：衡量测试执行了多少个可统计的分支。其核心价值在于能够提示测试是不是只走了条件判断的一边。


## 6 回归测试策略与测试范围选择

### 6.1 测试范围的三个层次
1. 第一级：定向测试（Targeted Tests）
   * 含义：运行直接对应本次改动的测试。
   * 适用情况：修改一个纯函数，影响范围明确，且风险较低。
   * 示例：修改标题空白字符的规范化规则，只运行相关的参数化测试和边界测试。
2. 第二级：相关回归测试（Related Regression Tests）
   * 含义：运行直接测试和受影响模块的测试。
   * 适用情况：修改公共接口、数据结构、数据库操作或多个模块共用的逻辑。
   * 示例：修改正文解析结果的字段，需要测试解析模块、Service 层及相关数据库写入逻辑。
3. 第三级：全量测试（Full Test Suite）
   * 含义：运行项目中全部适用的自动化测试。
   * 适用情况：架构调整、公共基础模块修改、依赖升级、发布前验证，或改动影响范围不明确。
   * 示例：修改整个学习助手的错误处理机制，可能影响 API、数据库状态和用户响应。

执行策略：这三个层次不是固定的严格等级。实际项目中可以先运行定向测试，再运行相关回归测试，最后根据风险和交付要求决定是否运行全量测试。

### 6.2 测试范围选择决策矩阵

| **判断因素** | **需要思考的问题** | **对测试范围的影响** |
| ------ | ------ | ------ |
| 改动范围 | 修改了一个函数，还是多个模块？ | 涉及模块越多，通常需要测试越广 |
| 依赖关系 | 是否修改公共接口、共享数据结构？ | 需要覆盖调用方和相关集成 |
| 业务影响 | 是否影响核心功能或数据一致性？ | 重要业务需要更强验证 |
| 失败后果 | 是否涉及安全、权限、数据丢失？ | 高风险修改需要更严格的回归验证 |
| 不确定性 | 是否不清楚代码被哪些模块使用？ | 应扩大测试范围并调查依赖关系 |


## 7 持续集成（CI）的核心思想

### 7.1 CI 的自动化质量检查
持续集成（CI）的核心思路是：把关键的质量检查自动化，并在代码变更时执行，让问题尽早暴露。
