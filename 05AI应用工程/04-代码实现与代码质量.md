# 代码实现与代码质量全景指南

## 1 模块设计与职责划分

### 1.1 函数拆分的标准与考量
在设计或重构函数时，判断一个函数是否需要拆分，可以通过以下三个核心问题进行考量：
1. 这个步骤是否有独立、清晰的含义？
2. 它是否可能独立变化、复用或需要单独验证？
3. 拆分之后，是否让调用方更容易理解？

### 1.2 类的适用场景与本质
类不只是把几个函数放进同一个文件的工具。当满足以下条件时，使用类更为合适：
* 多个操作需要共享一组有意义的状态或配置。
* 某个对象具有明确的生命周期和行为。

### 1.3 AI生成代码的结构审查
针对代码生成工具产生的函数与类，审查时应优先从四个维度进行评估：
1. 职责是否明确：函数名能否准确表达其主要行为？是否同时处理了互不相关的业务？
2. 修改原因是否混杂：当网络请求、业务规则和数据库存储分别发生变化时，是否都必须修改同一个函数？
3. 抽象是否合理：新增的函数或类是否减少了重复、隔离了职责或改善了可读性？还是只增加了无谓的代码跳转？
4. 行为是否保持正确：调整结构后，原有的输入输出、错误行为和副作用是否符合要求？是否有相应的验证证据？

## 2 命名规范、类型系统与代码可读性

### 2.1 代码可读性审查清单
在代码审查阶段，可以使用包含 8 项检查要点的清单辅助评估（该清单用于辅助审查，非自动通过标准）：
1. 函数名和类名是否准确表达实际职责？
2. 变量名是否清楚，是否存在含义模糊或误导性命名？
3. 重要函数是否标注合理的参数类型和返回类型？
4. 类型提示是否与真实返回值、异常和调用方式一致？
5. 可选值、空字符串和 None 是否被正确区分？
6. 是否存在过深的嵌套、过多布尔参数或难以理解的流程？
7. 是否创建了没有实际收益的类、数据模型或抽象层？
8. 是否需要通过静态检查、类型检查或测试进一步验证？

## 3 代码重用与抽象层级设计

### 3.1 DRY原则的真正含义
DRY 原则的核心思想是“不要重复自己”。它的核心不是禁止出现任何相似代码，而是尽量避免同一项业务知识、规则或决策被重复维护。

### 3.2 抽象程度的三级决策模型
根据业务场景选择合适的抽象深度，可遵循以下三个层级进行划分：
* 第一级（直接写代码）：适用于逻辑简单、只出现一次、职责明确的场景。没有必要为了未来可能出现的需求而提前抽象。
* 第二级（提取公共函数或模块）：适用于同一规则确实被多处使用、具有明确职责，且集中维护能有效降低成本的场景。
* 第三级（设计接口、策略或扩展框架）：适用于确实存在多种实现、替换需求或稳定扩展点的场景。需要综合评估接口定义、注册机制和维护成本。

## 4 代码复杂度控制与可维护性

### 4.1 复杂度的来源与评估指标
代码复杂度主要来自开发人员需要同时理解和追踪的信息量，具体体现在五个方面：
1. 代码中存在多少条不同的执行路径？
2. 一个变量在不同位置分别代表什么？
3. 一个操作会影响多少其他模块？
4. 修改一处代码，需要检查多少相关行为？
5. 失败时，系统的状态和副作用是否容易预测？

圈复杂度是衡量程序控制流复杂程度的指标，它主要关注代码中有多少条独立执行路径，而非代码的行数。
关于圈复杂度的使用注意：圈复杂度越高通常意味着需要考虑的路径越多，但它不是代码质量的完整评分。两段圈复杂度相同的代码，仍可能在可读性、耦合程度和错误风险上存在明显差异。

### 4.2 四种常见复杂度问题与调用链优化
常见引发高复杂度的四种典型结构问题：
1. 过深的条件嵌套。
2. 一个函数有太多分支。
3. 状态过多，且彼此相互影响。
4. 调用链过长，理解成本高。

针对过长调用链的审查要点：
如果每一层都有明确职责，长调用链可能有其存在价值。但如果多层只是简单转发参数，排查问题时就需要频繁跳转。审查时应重点检查：
* 每一层是否真正处理了自己的职责？
* 是否隐藏了重要的错误行为或副作用？
* 是否可以在不破坏边界的前提下简化调用链？
简化调用链的目标是降低理解成本，而不是追求最少的文件数量。

### 4.3 可维护性的定义
可维护性指代码在需要修复漏洞、调整逻辑、扩展功能或阅读理解时，是否容易、安全地完成修改。

## 5 安全重构工作流

### 5.1 重构的定义与核心目标
重构指在不改变软件外部可观察行为的前提下，调整内部代码结构，使其更容易理解、测试和维护。

### 5.2 六步安全重构流程
在标准开发工作流中，安全重构包括以下六个步骤：
1. 确认重构目标：明确当前要解决的具体问题（例如：文档获取函数同时负责 HTTP 请求和正文提取，职责不够清晰），切忌写“优化代码”或“让代码更优雅”等泛泛而谈的目标。
2. 了解现有行为：检查被修改函数的调用方、错误处理约定、已有测试，以及是否会写数据库或调用外部接口。弄清哪些行为必须保持不变。
3. 先验证现状：查看相关测试是否通过。若已有测试失败，需先弄清原因，不能直接把重构前的失败当成重构造成的，也不能忽略它们。
4. 进行最小范围的结构调整：一次只解决一个明确问题。例如先拆出正文提取函数，不要同时重写 HTTP 请求、错误处理和数据库逻辑。
5. 验证行为是否保持一致：运行相关测试，并根据影响范围执行必要的回归测试。检查正常返回、异常行为和副作用是否符合原有约定。
6. 审查 Diff 并决定是否接受：查看修改前后的差异，确认改动确实改善了结构，且没有夹带未经批准的功能变化、错误处理变化或无关修改。

### 5.3 重构验证的边界与审查要点
测试全部通过也不能绝对证明行为完全一致，因为测试用例可能没有覆盖某些场景。因此，重构审查还需要结合模块调用关系、代码差异和关键业务约定进行综合审查。

## 6 静态检查工具与自动化管道

### 6.1 四大检查工具类型与职责
代码质量保障工具链主要由四类工具协同组成：
1. 代码检查器：检查代码中的常见错误、潜在问题、规范违规等。示例：Ruff（检查未使用的导入、部分错误写法、导入排序违规等）。
2. 代码格式化工具：自动统一代码的排版（缩进、空格和换行）。示例：Ruff Formatter、Black。
3. 类型检查器：根据类型提示检查部分类型不匹配的问题。示例：mypy、Pyright。Ruff 本身不等同于完整的类型检查器。
4. 自动化测试工具：执行代码，验证指定输入是否产生预期结果。示例：pytest（验证文档获取成功、超时失败、数据库状态正确等行为）。

### 6.2 Ruff工具的使用与常见命令
Ruff 是 Python 开发中常用的高性能工具，兼具 Lint 检查与格式化功能。常见用途包括：
* 代码检查：发现部分未使用导入、未使用变量、潜在错误写法、风格违规等。
* 导入排序：通过特定的规则（如 I001）检查并规范导入顺序。
* 代码格式化：通过内置格式化器统一 Python 代码格式。

常用命令与说明如下：

| **命令** | **作用** |
| ------ | ------ |
| ruff check . | 检查代码，不主动修改文件 |
| ruff check . --fix | 自动修复支持安全修复的部分问题 |
| ruff format --check . | 检查格式是否符合格式化规则 |
| ruff format . | 自动格式化代码 |

## 7 AI生成代码审查与Agent协同规范

### 7.1 AI代码审查的六个核心维度
针对 AI 生成的代码，必须从以下六个维度进行全方位审查：
1. 需求正确性：实现的到底是不是要求的实际功能？有没有遗漏验收标准，或者擅自增加功能？
2. 行为正确性与可靠性：正常输入、异常输入、超时、失败和边界条件下，系统是否表现正确？
3. 架构与职责边界：模块职责是否清晰？依赖方向是否合理？有没有为了实现一个小功能引入不必要的抽象？
4. 代码质量与可维护性：命名是否准确、职责是否混杂、复杂度是否合理、重复规则是否需要统一维护？
5. 验证证据：相关测试是否真的执行？断言是否有效？是否存在没有验证的关键场景？
6. 变更范围与副作用：代码差异中有没有无关修改？是否意外改变数据库状态、接口契约、依赖或配置？

审查的核心原则：每项重要修改都应当能追溯到明确的需求或必要的技术原因。

### 7.2 审查三步法与易忽略问题
进行 AI 代码审查的推荐步骤：
* 第一步：先看代码差异（Diff），而不是先读整个项目。
* 第二步：沿着实际调用链检查代码。
* 第三步：重点检查五类容易被 AI 忽略的问题：
  1. 需求实现不完整。
  2. 错误处理改变了原有语义。
  3. 过度设计。
  4. 测试通过，但测试没有验证关键行为。
  5. 不必要的副作用。

### 7.3 检查手段的能力证据与局限性
不同的质量检查工具和方法能够提供的证据及其局限性如下：

| **检查手段** | **能提供的证据** | **不能单独证明** |
| ------ | ------ | ------ |
| 代码检查工具 | 启用规则范围内的代码问题已检查 | 业务逻辑正确 |
| 代码格式化工具 | 代码格式符合格式化规则 | 代码容易维护 |
| 类型检查 | 部分类型不匹配已检查 | 数据符合业务语义 |
| 自动化测试 | 指定场景的断言通过 | 所有场景都正确 |
| 差异审查 | 变更范围和具体修改可见 | 所有隐蔽缺陷均已发现 |
| 实际运行或手动验收 | 特定真实场景的行为得到验证 | 未测试的其他场景正确 |

### 7.4 风险分级审查策略
依据代码变更的影响风险，采取分级的审查策略：
* 低风险（文案、注释、简单格式调整）：检查代码差异、格式与相关轻量检查，确认没有夹带其他修改。
* 中风险（业务逻辑、数据处理、模块重构）：检查调用链、输入输出、异常路径，运行相关测试和必要的回归测试。
* 高风险（权限、安全、数据库删除、URL 抓取边界）：检查安全约束是否实际落地，验证关键失败路径和副作用，执行针对性的安全或集成测试；必要时进行独立审查。

### 7.5 Agent代码审查指令模板
当要求 Agent 执行项目配置的质量检查时，可使用以下标准提示词模板：

```text
请审查本次任务的代码变更。

1. 对照任务目标和验收标准，检查实现是否完整。
    
2. 检查 Diff 中的无关修改，以及接口、错误处理和副作用是否发生非预期变化。
    
3. 检查职责划分、依赖关系和复杂度是否合理。
    
4. 运行与本次修改相关的检查和测试，并报告实际执行结果。
    
5. 列出发现的问题、尚未验证的风险，以及是否建议交付。

不要为了让检查通过而修改测试预期或弱化验收标准。发现问题时，先报告具体位置、原因和影响。
```
