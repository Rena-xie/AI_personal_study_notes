### 1.1 需求与验收思维：先定义问题，再编写代码

**（1） 核心要素拆解**
面对具体的开发需求，需进一步将其拆解为以下五个关键要素：
* **目标**：明确本次开发要解决的具体问题。
* **输入与输出**：定义模块接收的数据格式与产生的预期结果。
* **边界与异常**：规定不支持的边缘场景及失败时的处理方式。
* **验收标准**：制定客观、可衡量的达标依据。
* **本次不做什么**：明确划定任务边界，防止范围无序膨胀。

**（2） 功能需求与非功能需求**
* **功能需求**：系统需要完成的具体业务功能，如添加知识源、检索文档、生成回答等。
* **非功能需求**：系统需要达到的质量与性能指标，如响应时间、稳定性、安全性和资源消耗。

### 1.2 架构与模块化思维：把复杂问题拆成可管理的部分

**（1） 核心架构概念**
* **高内聚**：模块内部的功能围绕相对明确的单一职责组织。
* **低耦合**：模块之间减少不必要的依赖，不依赖其他模块的内部实现细节。
* **职责分离**：不同性质的问题由合适的模块独立负责，模块间通过明确的接口契约交互。

**（2） 复杂度与 MVP 原则**
架构复杂度本身就是成本。在核心方案合理的前提下，应优先完成一个可以运行的最小可行性实现（MVP），避免过度设计。

### 1.3 软件工程质量维度与验证体系

**（1） 软件工程质量的四个核心维度**
软件交付质量由四个互不替代的维度构成：

| **质量维度** | **核心关注点** | **典型应用场景** | **验证方式** |
| ------ | ------ | ------ | ------ |
| 正确性 | 功能与输出是否符合预期需求 | 业务逻辑计算、文档提取完整性、回答依据核对 | 单元测试、集成测试、业务结果对比 |
| 可靠性 | 面对异常与变化能否稳定工作 | API 限流处理、超时控制、数据库断连恢复 | 异常测试、超时重试测试、状态一致性检查 |
| 可维护性 | 后续修改、排查与扩展的成本 | 模块独立性、解耦外部依赖、清晰命名 | 代码审查、依赖结构检查、重复代码检测 |
| 可交付性 | 能否按要求在目标环境中安装部署 | 环境变量配置、干净环境启动、初始化步骤 | 独立环境部署测试、交付文档与配置文件核查 |

**（2） 质量验证**

| **验证层次** | **验证对象**  | **典型示例**         |
| -------- | --------- | ---------------- |
| 单元测试     | 独立函数或模块   | 文本分块逻辑是否符合预期     |
| 集成测试     | 多个组件之间的协作 | 分块结果能否正确写入数据库    |
| 端到端测试    | 完整业务流程    | 提交网址后能否成功入库并回答问题 |
| 质量评测     | 系统输出的实际质量 | 检索内容是否相关、回答是否有依据 |
### 1.4 防御式编程，在正常路径之外，必须主动设计失败路径与边界条件

### 1.5 可维护与可观测思维：容易修改，容易排错

**（1） 可维护性**
降低长期修改、扩展与阅读成本。常见实践：
* 清晰的模块划分与准确命名。
* 避免重复代码（DRY 原则）。
* 配置文件与业务代码强分离。
* 使用类型标注与必要的文档说明。
* 为关键业务逻辑编写自动化测试。
* 使用 Git 规范管理版本与变更历史。

**（2） 可观测性**
通过系统运行时产生的日志、状态与指标，能够精准推断内部运行状况并迅速定位故障根因。

## 2 工程化开发思考维度对照表

在实现功能之前，工程化思维要求从以下 10 个维度全方位思考系统设计：

| **维度** | **需要思考的问题** | **具体工程设计** |
| ------ | ------ | ------ |
| 需求 | 什么才算功能完成？ | 明确输入、输出和可验证的验收标准 |
| 架构 | 功能之间如何协作？ | 划分为抓取、解析、分块、向量化、检索等独立模块 |
| 数据 | 数据如何存储和关联？ | 设计文档、知识源、文本块等数据实体与模型关系 |
| 异常 | 外部服务失败怎么办？ | 设置超时机制、异常捕获和有限次数的重试策略 |
| 质量 | 如何判断代码正确？ | 编写单元测试、集成测试和端到端测试 |
| 可观测性 | 出错后如何定位问题？ | 记录结构化日志、任务处理状态和关键运行上下文 |
| 可维护性 | 后续如何修改功能？ | 控制模块职责，减少不必要的模块间耦合 |
| 部署 | 如何让其他环境运行？ | 规范管理依赖库、环境变量和启动配置文件 |
| 安全 | 如何防止不合理输入？ | 校验网址格式、限制请求范围、保护 API 密钥安全 |
| 演进 | 如何支持未来扩展？ | 通过清晰的接口设计增加新功能，避免提前过度设计 |

## 3 协同开发与任务管理规范

### 3.1 适合委派给编码工具的任务标准

**（1） 四项合格任务评估标准**
适合独立委派给编码工具的任务应具备以下特征：

| **评估维度** | **合格任务标准** | **不合格任务标准** |
| ------ | ------ | ------ |
| 目标明确 | 清晰描述具体的单一功能实现 | 表达为“优化系统体验” |
| 范围可控 | 限制在特定的少数字符串或模块改动 | 同时改动前端、后端、数据库与部署配置 |
| 结果可验证 | 具备明确的断言或自动化测试方法 | 缺少客观的检查路径 |
| 交付相对独立 | 改动完成后可立即独立进行验证 | 必须依赖多个后续未建模块才能运行 |

**（2） 开发者三种控制能力**：控制单次改动范围、控制模块依赖顺序、控制异常风险。

### 3.2 协同开发工作流程与顺序

**（1） 基础六步工程化工作闭环**
基础开发闭环由六个核心环节构成：
① 明确目标与验收标准 -> ② 确定设计与模块边界 -> ③ 实现完整的最小功能 -> ④ 验证正常与异常情况 -> ⑤ 审查实现与交付质量 -> ⑥ 完成闭环并进入下一任务。

```
给codex的提示词示例：
请先分析当前代码仓库，针对以下需求制定分阶段实施计划，暂时不要修改代码。
要求：
1. 阅读与该需求相关的现有代码、测试和项目文档，不要仅根据需求描述猜测当前架构。
2. 将需求拆分为多个可控的开发任务。每个任务应有明确目标、有限的改动范围和可验证的完成条件。
3. 优先考虑能够形成有意义业务闭环、且便于独立验证的任务。
4. 对任务之间的依赖关系进行排序，说明哪些任务必须先完成。
5. 为每个任务列出：
- 任务目标
- 预计修改的模块或文件（如果当前信息足以判断）
- 验收标准
- 需要运行的测试或其他验证方式
- 主要风险和可能影响的已有功能
6. 避免不必要的重构、过度设计和与当前目标无关的功能扩展。
7. 如果需求存在影响架构或验收结果的关键歧义，请先指出，不要擅自做重大假设。
最后，请给出推荐的实施顺序，并说明为什么这样拆分。等我确认计划后，再开始第一个任务。
```


```
请在完成本次开发任务后，进行交付验证，并按以下结构报告：
1. **实现结果**
- 实际实现了哪些功能？
- 修改了哪些文件？每项关键改动的目的是什么？
2. **验收标准**
- 逐条列出本次任务的验收标准。
- 标明每项标准是通过、失败还是尚未验证。
- 对通过项说明对应的验证方式。
3. **测试证据**
- 列出实际执行的测试命令。
- 报告测试结果及失败详情。
- 区分自动化测试、手动验证和静态检查。
- 不要将未执行的测试描述为已通过。
4. **回归风险**
- 分析本次修改可能影响的已有功能。
- 运行与改动相关的回归测试。
- 如果有未验证的风险，明确列出。
5. **代码审查**
- 检查无关改动、异常处理、数据一致性和安全风险。
- 说明发现的问题及处理结果。
6. **遗留事项**
- 列出尚未完成的需求、已知限制和需要人工验证的事项。
不要为了让报告看起来完整而虚构测试结果。只有实际执行并获得证据的检查，才能标记为通过。
```

## 4 交付验证与审查标准

### 4.1 交付验证三层证据链

**（1） 代码证据**：检查修改位置是否准确，是否存在逻辑漏洞、无关改动或高危操作，确认关键业务条件覆盖无误。

**（2） 测试证据**：验证单元测试、集成测试与端到端测试是否真正执行，确保主干路径与异常路径均被覆盖。

**（3） 行为证据**：在真实运行环境中确认用户操作结果、数据状态及系统反馈符合预期。

### 4.2 交付审查提示词与检查清单

**（1） 交付审查汇报结构**
在委派编码工具进行交付验证时，应要求其按以下结构汇报：
* **实现结果**：列出实际完成的功能与修改文件的具体目的。
* **验收标准**：逐条标注标准状态（通过/失败/未验证）及对应验证手段。
* **测试证据**：提供执行的测试命令、日志输出与检查分类。
* **回归风险**：分析对已有功能的影响，附带回归测试结果。
* **代码审查**：汇报异常处理、数据一致性与安全风险的检查结果。
* **遗留事项**：明确未完成事项、已知限制与需人工核验的环节。

**（2） 七项交付核查清单**
交付核查需对照以下七项清单：
* [ ] **需求与范围**：实现结果与目标一致，未擅自扩充范围。
* [ ] **代码差异**：无无关代码改动，接口变更与副作用明确。
* [ ] **自动化测试**：自动化测试已真实运行并获取通过日志。
* [ ] **异常场景**：核心失败路径经过验证，无静默吞掉异常行为。
* [ ] **回归验证**：关联的现有功能运行正常。
* [ ] **实际行为**：关键业务流程在运行环境中验证成功。
* [ ] **遗留问题**：所有风险、限制与未验事项已清晰记录。

## 5 工程师能力梯队与工程原则总结

### 5.1 能力优先级矩阵

根据工程化实践的重要性，能力要求划分为三个梯队：

| **优先级** | **能力模块**  | **需要达到的工程程度**                    |
| ------- | --------- | -------------------------------- |
| P0      | 需求拆解与验收   | 能把模糊需求拆成明确、可执行、可验证的具体任务          |
| P0      | 模块化与接口设计  | 能清晰解释模块的职责、输入、输出及依赖关系            |
| P0      | 异常处理      | 能识别常见失败场景，并设计合理的容错与恢复策略          |
| P0      | 测试与调试     | 能编写基本测试用例，理解测试结果并精准定位问题根因        |
| P0      | Git 与版本管理 | 能审查代码差异（Diff）、理解提交记录并安全管理变更      |
| P1      | 数据建模与持久化  | 能理解实体关系、数据约束和数据状态转变              |
| P1      | 日志与可观测性   | 能根据结构化日志和错误信息高效定位系统问题            |
| P1      | 配置与依赖管理   | 能严格区分配置、密钥和业务代码，并管理依赖版本          |
| P1      | 部署与运行环境   | 能根据文档启动、配置并在干净环境中排查部署项目          |
| P2      | 性能与成本优化   | 能识别真正的系统性能瓶颈和 AI API 成本开销问题      |
| P2      | 高级架构设计    | 根据实际扩展需要，合理学习与应用缓存、异步任务、消息队列和微服务 |

### 5.2 九大工程原则与本质总结

**（1） 经典工程六大原则**
* **1. 先定义问题，再写代码。**
* **2. 先设计边界，再增加复杂度。**
* **3. 能运行不代表正确，必须通过验证证明。**
* **4. 正常路径只是系统的一部分，必须设计失败路径。**
* **5. 软件不仅要能运行，还要能够被理解、修改、排错和维护。**
* **6. 不追求最先进的技术，只选择对当前问题最合适的方案。**

**（2） AI Coding Agent 时代三大原则**
* **7. AI 的输出不是证据，验证结果才是证据。**
* **8. 把任务、约束和验收标准说清楚，再让 Agent 执行。**
* **9. 人负责目标、架构、判断和最终验收，Agent 负责高效率地执行大量工程工作。**

**（3） 软件工程的核心本质**
开发项目中的工程化思维，本质上是不只考虑“如何把功能写出来”，还要考虑“如何让系统可靠地实现目标、方便地验证、容易地维护，并且能够持续演进”。
