## Agent 的执行循环（Agent Loop）

Agent 最典型的机制是循环执行，而不是只调用一次模型。

观察——决策——校验——执行——更新状态——检查停止条件

模型提出请求，后端应当执行以下过程：

1. 解析模型返回的工具调用。
    
2. 检查工具名称是否在允许列表中。
    
3. 校验参数格式、长度和业务约束。
    
4. 检查当前用户是否有权执行该操作。
    
5. 执行工具，并处理超时、异常和资源限制。
    
6. 将真实执行结果写入任务状态和日志。
    
7. 按模型 API 协议返回工具结果。
    
8. 让模型根据结果继续处理，或生成最终回答。


在测试层面，可以区分：

- 单元测试（Unit Test）：验证 Schema、权限规则和单个工具。
    
- 集成测试（Integration Test）：验证工具、数据库、模型接口之间的协作。
    
- 端到端测试（E2E Test）：验证从用户输入到最终交付的完整路径。
    
- 回归测试（Regression Test）：确认修改后，原有正确行为没有退化。


Agent 的任务状态不应该随意变化。

例如，定义以下状态：

- `pending`：等待执行。
    
- `running`：正在执行。
    
- `succeeded`：成功完成。
    
- `failed`：执行失败。
    
- `cancelled`：任务被取消。

Checkpoint（检查点）是保存某个执行时刻的状态和必要数据，使任务在中断后能够从合适的位置恢复。



## 第4课：Agent 工具工程与权限边界

本课重点是：如何设计一套既能让 Agent 完成任务，又不会让它越权、误操作或失控的工具系统。安全边界必须由可信的程序代码实施，而不能只依赖模型自觉遵守。


更可靠的工具契约至少应明确以下六项：

| 契约要素 | 需要明确的问题              |
| ---- | -------------------- |
| 输入参数 | 参数名称、类型、必填项、长度限制     |
| 输出结果 | 成功、失败分别返回什么          |
| 前置条件 | 什么情况下允许调用？           |
| 权限范围 | 可以操作哪些用户、记录或资源？      |
| 副作用  | 是否新增、修改或删除数据？        |
| 执行限制 | 超时、重试、调用次数和资源消耗如何限制？ |
## 四道核心安全防线

第一道：工具白名单（Allowlist）

只允许调用程序明确注册的工具。模型即使生成了 `execute_shell`，如果该工具不在允许列表中，程序也必须拒绝。

第二道：参数校验与业务授权

检查参数类型、取值范围、业务规则以及调用者权限。不能因为模型提供了一个合法的 `note_id`，就默认它有权修改对应笔记。

第三道：人工确认（Human-in-the-loop）

对高影响操作设置确认门槛，例如永久删除重要数据、向外部发送消息或执行不可逆操作。确认必须绑定具体操作和参数，不能只问一句笼统的“是否继续”。

第四道：执行隔离与资源限制（Sandboxing）

对需要执行代码或处理不可信输入的工具，使用适当的隔离机制，并限制文件系统、网络访问、运行时间、内存和 CPU。普通 Python 函数封装不等于沙箱。



## 最小权限原则：不要给 Agent 它不需要的能力

最小权限原则（Principle of Least Privilege）是指：系统只授予完成当前任务所必需的权限。


## 第5课：Agent 规划、任务分解与 Replanning（重新规划）

本课要解决的问题是：当用户提出一个复杂目标时，Agent 如何制定执行计划、逐步完成任务，并在遇到意外时调整计划，而不是机械地执行最初的步骤？
一个计划至少需要回答四个问题：

- 做什么？ 需要完成哪些子任务？
    
- 先做什么？ 哪些步骤存在先后依赖？
    
- 怎样算完成？ 每一步的验收条件是什么？
    
- 失败怎么办？ 哪些情况可以重试，哪些情况需要调整计划或停止？

Task Decomposition（任务分解）是将复杂目标拆成较小、能够独立执行或验证的子任务。
好的子任务通常具备三个特征：

1. 边界明确： 知道它需要处理什么，不需要处理什么。
    
2. 产物明确： 能指出执行结束后应该得到什么。
    
3. 验收明确： 能通过检查判断它是否完成。
