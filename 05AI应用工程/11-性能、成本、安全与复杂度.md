## 1 性能测量与基准评估

### 1.1 性能基础概念
在评估 AI 应用性能时，需要准确区分以下四个核心指标：

* **延迟**：完成一次请求需要多长时间。例如获取文档并生成答案花费了 5 秒。
* **吞吐量**：单位时间内系统处理的请求数量。例如系统每秒能够处理 20 个请求。
* **并发**：同一时间内处于执行或等待状态的任务数量。例如同时有 10 个请求正在等待大模型响应。
* **资源消耗**：处理请求时消耗的硬件及网络资源。例如进程运行时占用 1GB 内存。

### 1.2 瓶颈定位与测量指标
当 AI 应用运行缓慢时，应当通过数据测量定位瓶颈，常见的测量指标如下：

* **总延迟**：用户等待整个请求完成的全部时间，例如 8 秒。
* **分阶段耗时**：每个具体处理环节所花费的时间，例如获取网页消耗 1.2 秒。
* **P50 延迟**：代表百分之五十的请求在此时间范围内完成，例如 5 秒。
* **P95 延迟**：代表百分之九十五的请求在此时间范围内完成，例如 12 秒。
* **错误率**：请求处理过程中出现失败的比例，例如 2%。
* **吞吐量**：单位时间内处理的请求总数，例如每秒处理 10 次。
* **资源使用**：系统运行时 CPU、内存和网络等资源的具体消耗，例如消耗内存 500 MB。

### 1.3 基准测试设计与多维评估
设计有效的基准测试需遵循三个基本步骤：

1. **固定测试输入**：确保每次测试使用的输入数据完全一致。
2. **保持环境一致**：尽可能在相同或可控的运行环境中进行测试。
3. **多次运行观察分布**：通过多次测量观察数据分布情况，避免偶然误差。

AI 应用的性能基准测试应当同时评估以下四个维度：

* **性能维度**：评估系统的延迟、吞吐量以及资源消耗情况。
* **正确性维度**：评估生成的答案是否准确、引用的来源是否真实有效。
* **成本维度**：统计消耗的词元用量以及产生的接口服务费用。
* **可靠性维度**：考察请求的成功率、超时率以及错误发生率。

### 1.4 性能测量工具与方法分类
在不同开发阶段，应根据实际需求选用合适的测量工具：

* **时间测量函数**：主要用于测量局部代码的执行耗时，初学者必须掌握。
* **应用日志与计时埋点**：用于记录真实请求在各个分阶段的详细耗时，推荐在工程中使用。
* **自动化测试框架**：主要用于验证功能逻辑和代码正确性，必须掌握。
* **性能基准测试工具**：用于重复测量特定 Python 代码片段的性能表现，存在专门性能分析需求时使用。
* **负载测试工具**：用于模拟并发用户访问，测量高负载条件下的系统性能，存在并发扩展需求时学习使用。

## 2 成本核算与优化路径

### 2.1 AI 应用的成本构成
单次 AI 请求会产生多项综合成本，不能仅关注单个接口的计费价格：

* **大模型调用成本**：包含输入的词元、输出的词元以及模型本身的计费规则。
* **向量化成本**：将文档转换为向量时，调用收费向量 API 产生的费用，或本地运行向量模型消耗的计算资源。
* **外部服务成本**：调用网页搜索、搜索接口或第三方数据服务时，按请求次数或套餐支付的费用。
* **基础设施成本**：运行环境、服务器、数据库、存储空间、网络流量以及日志系统消耗的硬件与服务资源。

### 2.2 成本优化的四个核心方向
降低 AI 应用运行成本主要有以下四个方向，在工程实践中无需同时实施，应先测量成本构成，再选择收益明确、风险可控的方案：

1. **减少不必要的模型调用**：能够通过普通程序确定的逻辑，无需交给大模型处理。例如 URL 格式的合法性校验可以直接使用 Python 代码完成。
2. **减少无效的词元传输**：避免将无关内容、重复的历史对话或过长提示词发送给模型，仅提供完成当前任务所必需的上下文。
3. **缓存可复用的处理结果**：在条件允许时复用历史结果，避免重复发起 HTTP 请求、重复生成答案或重复计算向量。
4. **选择适配任务的模型**：对于简单任务选用低成本模型，复杂任务选用高能力模型。在替换模型前必须通过质量评测确认效果可接受。

## 3 缓存机制与风险控制

### 3.1 缓存对象与应用场景
在 AI 应用中，常见的可缓存对象及其特性如下：

* **网页获取结果缓存**：保存 URL 对应的网页原文或提取后的正文内容。
  * **收益**：减少重复的网络请求和网页解析工作。
  * **风险**：当源网页内容更新后，缓存的数据可能过期失效。
  * **适用场景**：经常被重复访问的公开技术文档。
* **向量数据缓存**：保存文本段落计算后得到的向量结果。
  * **收益**：同一段文本无需反复调用向量化模型。
  * **风险**：当模型类型、模型版本或向量化配置改变时，旧的向量可能无法兼容。
  * **适用场景**：文档的重复处理与重复入库过程。
* **模型响应缓存**：保存特定请求所对应的模型输出答案。
  * **收益**：当完全相同的请求再次出现时，可以直接返回已有答案。
  * **风险**：当用户提问、权限设定、模型配置或底层文档发生变化时，旧答案可能不再适用。
  * **适用场景**：输入高度稳定、答案可重复利用且允许一定陈旧风险的任务。

### 3.2 缓存策略的三大核心问题
设计缓存策略时必须明确解决以下三个关键问题：

1. **缓存键设计**：确定通过何种规则和字段组合，判断两个请求能够复用同一缓存结果。
2. **生存时间配置**：确定缓存数据应该保留多久，超过预设时间后自动失效。
3. **缓存失效机制**：当底层源数据发生变化时，确保缓存能够及时更新或失效。常见解决方案包括：
   * 设置合理的预设生存时间。
   * 通过 HTTP 验证器检查源头内容是否被修改。
   * 根据正文内容的哈希值判断数据是否变化。
   * 在文档更新后重新执行解析与向量化，并使旧答案缓存主动失效。
   * 为不同的模型版本、提示词版本和数据版本指定不同的缓存标识。

### 3.3 缓存引入的额外风险
引入缓存虽然能降低成本并提升性能，但同时也可能带来以下安全与业务风险：

* **数据隔离风险**：缺乏严格检查时，可能导致用户甲的私人数据或个性化答案被错误地返回给用户乙。
* **安全边界失效**：缓存机制不能绕过权限检查、URL 安全校验及内容合法性验证。
* **数据陈旧风险**：过期的旧文档或旧答案可能给用户提供错误的引导。
* **并发重复计算**：当多个并发请求同时发现缓存未命中时，可能同时发起昂贵的重复调用。此类问题可通过请求合并机制进行缓解。
* **缓存污染风险**：异常响应、失败结果或不可信的内容，未经校验绝不能作为有效结果长期存入缓存。

## 4 安全边界与防线构建

### 4.1 安全边界的定义
安全边界是系统中专门用于区分允许执行的操作与禁止执行的操作的控制边界。

### 4.2 安全防护的四道核心防线

#### 第一道防线：输入验证
输入验证指在处理数据前，判断其是否符合系统允许的格式、范围与业务规则。验证分为三个递进层次：

* **格式验证**：回答输入是否符合语法规范。例如判断输入的 URL 是否能被正确解析。
* **业务验证**：回答输入是否符合功能业务规则。例如检查系统是否仅允许 HTTPS 协议。
* **安全验证**：回答执行操作是否会引发越权或危险行为。例如检查请求是否试图访问内部网络地址。

在针对服务器端请求伪造（SSRF）进行防护时，必须建立多层防御体系：

1. 解析 URL，严格限制允许使用的协议、主机名和端口。
2. 解析 DNS，检查目标 IP 地址是否属于禁止访问的内网或保留地址范围。
3. 处理网络重定向时，对每一个新跳转的目标地址重新执行完整的安全检查。
4. 防范 DNS 重绑定攻击，处理实际建立连接的目标与安全检查结果不一致的问题。
5. 配置网络出口规则，在基础设施层面进一步限制后端服务的访问范围，避免单独依赖应用层判断。
6. 严格限制超时时间、响应体大小、下载总时长和重试次数，防止系统资源被恶意耗尽。
7. 实现时需综合考虑 IPv4、IPv6、代理配置以及 DNS 解析与连接过程的一致性，不能简单依赖正则表达式排除特定字符串。

#### 第二道防线：提示词注入防护
防范提示词注入需要建立可靠的代码控制体系：

* 不向模型提供不必要的密钥、内部配置或敏感业务数据。
* 严格限定大模型能够调用的工具类型以及参数范围。
* 在工具实际执行前，必须由应用层代码进行严格的权限与安全校验。
* 对带有副作用的操作设置额外的授权机制。
* 绝不将网页获取的内容直接拼接为可执行代码或 SQL 查询语句。
* 对大模型的输出结果进行结构校验与必要的安全检查。

#### 第三道防线：权限最小化
严格遵循最小权限原则，确保每个系统组件仅获得完成当前具体任务所必需的最低权限。

#### 第四道防线：资源与费用限制
安全防护不仅要防止数据泄露，还需防止系统被恶意滥用或资源耗尽。必须配置以下控制项：

* **请求超时**：避免单次网络或计算操作陷入无限等待。
* **响应体大小上限**：防止下载体积过大的恶意内容占满内存。
* **重定向次数上限**：防止网络请求进入无休止的跳转循环。
* **重试次数上限**：避免因频繁重试导致资源与费用被快速消耗。
* **输入长度限制**：防止异常的超大文本输入引发系统故障。
* **词元与输出长度限制**：有效控制大模型的调用费用与生成规模。
* **速率限制**：限制单位时间内的请求频率，防止系统被高频刷调用。
* **费用告警与监控**：实时监控费用与用量，尽早发现并处理异常消耗。

### 4.3 安全要求验收与验证方法
系统的安全要求及其对应的验收标准与验证方法如下：

* **限制 URL 要求**：不允许的协议、主机和端口必须被拒绝，通过单元测试验证。
* **防范 SSRF 要求**：指向禁止 IP 地址的请求必须被拦截，通过安全测试验证。
* **检查重定向要求**：跳转到禁止目标时请求必须被拒绝，通过集成测试验证。
* **控制资源要求**：超时或超大响应不会无限占用资源，通过边界测试验证。
* **防范提示词注入要求**：网页中的恶意指令不能绕过工具权限，通过对抗测试验证。
* **保护密钥要求**：密钥绝不进入普通日志或用户响应，通过代码审查与测试验证。
* **限制滥用要求**：超过规定请求速率时按策略拒绝或限流，通过集成测试验证。

## 5 数据安全与隐私保护

### 5.1 概念区分
* **数据安全**：侧重于防止数据被未授权访问、修改、泄露或损坏。
* **隐私保护**：侧重于控制个人信息如何被收集、使用、共享、保留和彻底删除。

### 5.2 数据安全与隐私保障五步法

#### 第一步：识别应用中的全路径数据
开发者需要全面追踪数据在整个系统中的流转过程，而不能仅仅关注数据库中静态保存的内容。

#### 第二步：数据分类与保护要求
根据数据的敏感程度及其泄露影响，进行分类管理：

* **公开数据**：如官方公开的技术文档，重点关注数据来源的可信度、完整性及使用条件。
* **普通业务数据**：如文档标题和处理状态，重点控制修改权限，避免不必要的对外公开。
* **用户私人数据**：如私人笔记、对话历史和个人学习记录，严格限制访问、共享和留存范围。
* **认证与密钥**：如 API 密钥、访问令牌和数据库密码，绝不公开、不写入普通日志，并严格限制调用权限。
* **高敏感个人信息**：如身份证件信息和财务账户信息，必须极其严格地限制收集、访问、传输和留存。

#### 第三步：控制发送给外部模型的具体数据
严格遵循数据最小化原则，仅收集、处理和传输完成当前任务所必需的数据字段。

#### 第四步：日志安全与数据脱敏
日志是排查故障的重要手段，但也是常见的数据泄露途径。必须采取脱敏与屏蔽措施：

* **脱敏**：指删除或替换不应暴露的敏感数据。
* **原则**：构造日志字段时即排除敏感数据，在输出边界增加脱敏手段，检查异常信息与第三方日志，防止凭证进入日志。

#### 第五步：加密、权限控制与数据生命周期
* **加密机制**：使用 HTTPS/TLS 进行传输加密保护通信过程；使用静态加密降低存储介质丢失时的直接泄露风险。
* **访问控制**：确保用户和服务仅能访问受控数据，后端必须严格校验归属权，不能盲目相信客户端传参。
* **数据生命周期管理**：明确数据在收集、使用、存储、归档及删除各阶段的规则。注意删除数据库记录并不代表备份、缓存、日志及第三方副本已被彻底清理。

### 5.3 数据保护要求拆解与验证
具体数据保护要求的验收标准及验证方式如下：

* **保护 API 密钥要求**：密钥不进入版本库、普通日志和用户响应，通过代码审查和测试验证。
* **控制日志内容要求**：不记录完整的私人正文及认证凭据，通过日志测试验证。
* **限制数据访问要求**：用户无法读取其他用户的私人记录，通过权限集成测试验证。
* **减少数据传输要求**：发往大模型的内容仅包含任务必需字段，通过检查请求构造和测试验证。
* **控制数据保留要求**：超过保留期限的数据按既定策略处理，通过生命周期测试验证。
* **执行数据删除要求**：删除操作必须覆盖约定的数据存储与缓存，通过集成测试验证。
* **保护传输安全要求**：外部 API 使用符合规范的安全传输配置，通过配置检查和集成测试验证。

## 6 复杂度控制与过度设计防范

### 6.1 复杂度的定义
工程中的复杂度不等于代码行数或功能数量，它代表系统需要多少额外的知识、规则和操作才能被正确开发、运行、排查与维护。

### 6.2 复杂度控制的三大原则
* **YAGNI 原则**：暂不需要的功能先不实现。不要仅因为未来可能用到就提前编写代码。
* **KISS 原则**：保持方案简单。在满足需求、正确性、安全性和可靠性的前提下，优先选择更容易理解和维护的实现。
* **三者法则**：重复出现三次再评估抽象。逻辑第一次出现时正常编写，第二次出现时观察差异，第三次出现时再评估是否抽象为公共模块。

### 6.3 判定过度设计的五个审查问题
判断一个技术方案是否过度设计，需要回答以下五个问题：

1. **需求依据**：该方案解决了哪个明确的需求或已经观察到的问题？
2. **实际收益**：它能在正确性、延迟、并发、成本或可维护性上带来什么具体改善？
3. **引入成本**：它会增加多少代码量、依赖项、配置项、测试用例和运维负担？
4. **替代方案**：是否存在更简单且同样能够满足验收标准的实现方式？
5. **演进与可逆性**：如果未来需求发生变更，能否以合理的代价进行升级或替换？

### 6.4 过度设计审查 Agent 指令模板
用于指导 AI Agent 对技术方案进行过度设计审查的提示词模板如下：

```markdown
请审查当前方案是否存在过度设计。

重点检查：
1. 每个模块、依赖和抽象层解决了什么实际需求？
2. 是否存在没有明确需求依据的组件？
3. 是否有更简单且满足当前验收标准的替代方案？
4. 删除或合并某个组件后，会影响哪些功能、安全性、可靠性和可测试性？
5. 哪些能力应该现在实现，哪些应等需求出现后再实现？

请给出具体证据和建议，并区分：
- 必须保留
- 建议简化
- 暂缓引入

不要为了简化而削弱安全性、正确性或必要的测试。此次先进行审查，不修改代码。
```

## 7 技术方案权衡与综合验收

### 7.1 高代价与低可逆性决策
在系统开发中，以下决策具有较高的修改代价和较低的可逆性，必须在实施前进行充分分析：

* 公开 API 的契约设计。
* 数据库结构与数据迁移策略。
* 用户身份认证、权限分配与数据隔离设计。
* 已有数据的删除与长期保留政策。
* 将单体系统拆分为多个独立微服务。

针对不同可逆性的决策，合理做法是对易调整的决定快速试验验证，对代价高、影响范围大的决定加强前期设计与分析。

### 7.2 技术方案评估 Agent 指令模板
用于评估关键技术选择与权衡取舍的提示词模板如下：

```markdown
请评估当前任务的技术方案。

对于每个关键技术选择，请说明：
1. 当前需求和验收标准是什么？
2. 该方案带来的主要收益是什么？
3. 新增的开发、测试、部署和维护成本是什么？
4. 主要风险及其影响是什么？
5. 是否存在更简单、同样满足验收标准的替代方案？
6. 如果现在不引入，未来出现什么具体信号时才值得引入？

最后给出推荐方案及理由，区分必须解决的问题、可选优化和暂缓事项。

不要仅因为某项技术流行或便于未来扩展就推荐引入。不要为了简化而牺牲必要的安全性、正确性和可靠性。
```

### 7.3 性能、安全与成本综合验收 Agent 指令模板
用于对项目进行最终综合验收审查的提示词模板如下：

```markdown
请对当前任务进行综合验收审查，不要直接修改代码。

检查以下维度：
1. 正确性：需求和验收标准是否全部满足？
2. 性能：是否有测量证据，是否存在明显瓶颈？
3. 成本：是否能统计单次成功任务的模型调用和费用？
4. 安全与隐私：是否存在未验证的安全边界、密钥泄露或不必要的数据记录？
5. 复杂度：是否存在缺乏明确需求依据的依赖、抽象或基础设施？

对每项发现，请列出：
- 具体问题及证据
- 影响与风险
- 必须修复、建议改进或暂缓处理
- 推荐的最小解决方案
- 对应的验证方法

明确区分已验证、未验证和不适用的项目。不要把没有测试覆盖的行为描述为已经验证，也不要仅凭静态检查通过就认定运行正确。
```
