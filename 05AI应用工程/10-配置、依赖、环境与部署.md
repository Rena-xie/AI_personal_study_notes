## 1 配置管理工程原则与核心依赖

### 1.1 配置管理四大工程原则
在应用开发中，配置管理是保证软件在不同环境（开发、测试、生产）中安全、稳定运行的基础。配置管理的四条核心工程原则如下：

*  变量与代码解耦：环境相关的值（如数据库连接串、服务地址、第三方 API 秘钥）切勿散落在业务代码中。
*  错误早期暴露：必要配置在缺失或不合法时，系统启动时应尽早、明确地抛出异常并停止运行，避免带病运行。
*  默认值与合法性校验：有合理默认值的配置可以提供默认值，但必须对其类型和取值范围进行合法性验证。
*  敏感信息防护：密钥、令牌等敏感数据绝不能提交到 Git 代码仓库，也不能打印或写入运行日志。

### 1.2 项目核心依赖与用途划分
Python 项目常用的核心依赖库及其主要用途划分如下：

| **依赖名称** | **核心用途** |
| ------ | ------ |
| fastapi | 构建高性能 HTTP API Web 框架 |
| uvicorn | 启动并运行 ASGI 应用服务器 |
| httpx | 发送异步 HTTP 请求与获取网页或技术文档 |
| pydantic | 负责数据验证、类型转换与配置管理 |
| pytest | 运行自动化测试与断言验证 |
| ruff | 执行代码静态检查、风格排查与自动格式化 |

## 2 环境隔离与 Python 运行机制

### 2.1 依赖声明与环境隔离三件套
管理 Python 项目的依赖关系与虚拟环境时，通常依靠以下三个核心组件协同工作：

*  pyproject.toml：项目依赖与配置声明文件。用于描述项目所需的第三方依赖、支持的 Python 版本以及开发工具的配置参数。
*  uv.lock：依赖版本锁定文件。记录依赖解析后的具体版本及分发文件哈希信息，确保不同开发者与部署环境中依赖安装完全可复现。
*  .venv：本地 Python 虚拟环境目录。保存项目独立安装的 Python 依赖包，实现与其他项目的运行环境隔离。

### 2.2 Python 运行环境四要素
一个完整的 Python 应用运行环境包含以下四个核心组成部分：

*  操作系统：如 Windows、Linux、macOS 等，直接影响文件路径分隔符、系统权限以及部分依赖库的编译。
*  Python 解释器：负责解析并执行 Python 代码的核心运行时环境（如 Python 3.11 或 3.12）。
*  虚拟环境：为当前项目提供独立的依赖包存储空间，并绑定指定的 Python 解释器。
*  项目依赖与配置：包括项目引用的第三方包、环境变量以及数据库连接等配置信息。

### 2.3 ASGI 规范与网络服务器职责映射
ASGI 是 Python Web 应用与服务器之间的接口规范。在 Web 服务处理流程中，相关组件的职责映射如下：

*  FastAPI：负责定义 HTTP 路由接口、请求校验与业务处理逻辑。
*  Uvicorn：负责运行 ASGI 应用，接收网络连接并处理底层的协议传输。
*  HTTP：客户端与服务器之间交换请求和响应信息的标准化网络协议。

## 3 应用部署流程与 Docker 容器化技术

### 3.1 本地运行到生产部署的八步流程
从本地代码编写到最终生产环境部署的标准流程分为以下 8 个步骤：

1. 依赖同步：在本地环境使用 `uv sync` 命令同步并锁定项目依赖。
2. 配置环境变量：针对当前环境配置必需的环境变量与参数。
3. 质量检查：运行自动化测试集与 Ruff 静态代码检查。
4. 应用启动：使用正确的启动命令（如 Uvicorn 命令）启动 Web 应用。
5. 基础验证：通过 HTTP 请求验证系统的健康检查接口与核心 API。
6. 目标环境配置：在部署目标环境中配置依赖、密钥、数据库连接及启动命令。
7. 部署后验证：完成部署后，执行健康检查与真实的业务流程验证。
8. 日志核查：排查运行日志，确认失败场景可准确定位且未泄露敏感信息。

### 3.2 Docker 容器化核心概念与工程判断
Docker 的核心价值在于将应用本身及其依赖的所有运行环境打包为一个可分发、可重复运行的标准化单元。

*  镜像：应用运行环境的静态模板，包含应用代码、运行时、依赖包与启动配置。
*  容器：根据镜像创建并运行的动态实例。同一个镜像可以启动多个相互隔离的容器。
*  Dockerfile：定义镜像构建步骤与指令的配置文件。

### 3.3 构建忽略文件与容器适用场景
为了确保镜像构建的安全与高效，需要妥善处理构建忽略机制：

*  .dockerignore 文件的作用：用于排除构建上下文中的无关或敏感文件（如 `.env` 密钥文件、`.git` 版本库、大型缓存目录及 `.venv` 虚拟环境）。防止敏感配置外泄、缩短构建时间并减小镜像体积。需注意 `.dockerignore` 与 `.gitignore` 职责不同，不能相互替代。
*  适合使用 Docker 的 5 种场景：
   1. 需要向其他开发者或部署环境交付高度一致的运行环境。
   2. 部署目标平台明确要求提交容器镜像。
   3. 项目包含多个服务（如 API、数据库、缓存），需要统一进行多容器编排。
   4. 希望在 CI/CD 流程中自动验证容器镜像的构建、启动及健康检查。
   5. 项目依赖特定的底层系统库，需要严格控制运行环境的差异。

## 4 部署验收与工程化交付规范

### 4.1 部署验收维度清单
项目在部署交付时，需对照以下 5 个维度进行全面验收：

| **验收维度** | **检查项目与要求** |
| ------ | ------ |
| 配置管理 | 必需环境变量缺失时明确报错退出；密钥禁止写入 Git、镜像或日志；配置类型与取值范围完成严格校验 |
| 环境与依赖 | Python 版本符合项目规范；环境可依据 `uv.lock` 完备重建；静态检查与自动化测试全部通过 |
| 启动与接口 | 启动命令与应用实际入口一致；服务进程能够稳定运行；HTTP 健康检查返回预期结果 |
| 运行与数据 | 数据库与外部依赖服务正常连接；重启后持久化数据符合逻辑预期；核心业务接口验证通过 |
| 交付说明 | README 包含完整的安装、配置、启动与测试说明；失败时抛出易懂的错误；交付结果附带验证证据 |

### 4.2 工程化交付审查体系
工程化交付审查包含五大核心模块，每个模块的具体检查项如下：

*  A. 依赖与环境：Python 版本与依赖声明清晰明确；锁文件与配置完全一致；新环境可依据说明快速重建；已核对静态检查与自动化测试结果。
*  B. 配置与安全：必需配置均经过合法性验证；密钥未提交至代码仓库或写入镜像；日志无敏感信息泄露；开发与生产环境配置差异得到妥善隔离。
*  C. 启动与运行：启动命令与应用入口完全匹配；服务进程能够持续正常运行；HTTP 健康检查通过；核心业务流程经过实际运行验证。
*  D. 数据与可靠性：数据库及外部依赖服务可用性已确认；持久化数据保留机制符合预期；系统超时与异常已被捕获处理；失败场景未误报为成功。
*  E. 交付材料：README 包含安装、配置、启动和测试指南；验证命令与执行结果可追溯；如实记录已知限制与遗留事项；第三方开发者可按文档复现流程。

### 4.3 工程化交付审查 Agent 指令模板
在指挥 AI Agent 执行交付审查时，可使用以下结构化审查指令：

```markdown
# 任务：工程化交付审查

请审查当前项目的工程化交付状态，先检查，不要立即修改代码。

重点检查：
1. Python 版本、依赖声明、锁文件和环境重建流程。
2. 环境变量、必需配置和密钥保护。
3. 应用启动入口、启动命令和健康检查。
4. 自动化测试、静态检查和核心业务验证。
5. 数据持久化、异常处理和运行日志。
6. README 中的安装、配置、启动和验证说明。

请区分：
- 已实现且有验证证据
- 已实现但尚未验证
- 尚未实现
- 存在风险或信息不足

输出每项发现对应的文件、相关代码位置或验证证据，并按安全风险、正确性和交付阻塞程度排序。

不要仅凭代码存在就认定功能正常；没有实际执行的检查必须明确标注。不要为了让项目看起来更完整而引入不必要的依赖或基础设施。

本任务只做审查和报告，不修改文件。完成后等待下一步指令。
```
