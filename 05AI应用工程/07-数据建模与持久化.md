## 1 数据建模与持久化基础概念

### 1.1 数据建模与持久化定义
* 数据建模：确定应用需要保存哪些数据、数据之间存在什么关系，以及哪些业务规则必须成立。
* 数据持久化：将数据可靠地保存到程序运行之外的存储介质中，使数据在进程或应用结束后仍然存在，并能在需要时重新读取。

### 1.2 主键与外键
* 主键：用于唯一识别一条数据库记录的字段或字段组合。主键必须满足两个核心要求：
  * 唯一：不同记录不能拥有相同的主键值。
  * 非空：主键字段不能缺失。
* 外键：用于建立可靠的表间关联，确保不同数据实体之间的引用关系真实有效。

## 2 字段约束与数据库规范化

### 2.1 四种核心字段约束
约束是数据库用于限制数据输入、维护数据完整性的规则。不同约束解决的问题不同，不能互相替代：
* NOT NULL：不允许字段值缺失。
* UNIQUE：不允许字段值在表中重复。
* CHECK：限制字段允许输入的值或范围。
* DEFAULT：在未显式提供值时自动使用预设的默认值。
### 2.2 数据库规范化三范式
数据库规范化的核心思路是识别不同的业务实体，将各自的数据放到合适的表中，再通过键建立关系，从而避免数据冗余和更新异常。

* 第一范式：每个字段应当表示一个明确的数据项，禁止将多个独立值塞进同一个字段中。
* 第二范式：在满足第一范式的基础上，消除非主键字段对复合主键的部分函数依赖，确保非主键字段完全依赖于整个主键。
* 第三范式：在满足第二范式的基础上，消除非主键字段对主键的传递依赖，即非主键字段不应通过另一个非主键字段间接依赖主键。

### 2.3 数据库模型审查清单
在评估现有模型时，应针对数据冗余与异常风险进行审查，遵循不为了拆表而拆表的原则：

* 涉及表与字段：明确审查对象。
* 重复保存的业务事实：定位冗余数据。
* 潜在异常风险：识别插入、更新或删除时可能引发的数据不一致。
* 规范化与快照评估：判断是否需要规范化拆分，或者保留为具有明确业务语义的快照/缓存。
* 改进方案与代价：评估最小改进方案及其重构成本。

## 3 事务特性与并发容错机制

### 3.1 事务 ACID 核心特性
数据库事务用于将多条数据库操作组合为一个整体，其核心特性包括：

| **特性** | **核心含义** |
| ------ | ------ |
| 原子性 | 一组数据库操作要么全部成功，要么全部失败回滚 |
| 一致性 | 事务执行前后，数据库始终满足预设的所有完整性约束 |
| 隔离性 | 并发执行的事务之间按照规定的隔离级别相互作用、互不干扰 |
| 持久性 | 事务一旦提交成功，其产生的数据变更在规定的故障模型下能够持久保存 |

### 3.2 容错机制的能力边界
不同容错与一致性机制具有明确的职责边界，单一机制无法解决所有问题：

| **机制** | **主要解决的问题** | **不能单独解决的问题** |
| ------ | ------ | ------ |
| 事务 | 保证多条数据库操作的原子性提交或回滚 | 不能自动撤销已发生的外部 API 调用 |
| 数据库约束 | 在数据库层阻止违反数据完整性规则的写入 | 不能完整实现复杂的上层业务流程逻辑 |
| 幂等性 | 防止同一业务操作重复执行时产生重复副作用 | 不能自动保证多条 SQL 语句的原子提交 |

## 4 SQL 查询与多类型索引机制

### 4.1 查询效率与索引
随着数据量增加，索引能够大幅提升数据检索效率。SQLite 常见索引采用 B-tree（平衡树）结构，能够高效支持相等匹配、范围查询以及某些排序操作。

### 4.2 三种主流索引类型对比
在不同检索场景下，需要选用适宜的索引技术：
* B-tree 索引：主要用于精确匹配、范围查询和结果集排序。
* FTS5 全文索引：基于 SQLite 的 Full-Text Search 5 扩展，专门用于文本词项检索与全文匹配。
* 向量索引：基于向量相似度计算，专门用于高维语义召回（如 RAG 场景中的语义检索）。

## 5 Python 数据库技术栈与组件分工

### 5.1 架构分层与组件职责
Python 应用在与数据库交互时，通常采用多层协同的技术栈架构：

* FastAPI / 业务代码层：负责业务逻辑编排，决定何时查询或保存业务数据。
* Pydantic 模型层：负责 API 请求与响应的数据结构校验与描述，确保输入符合格式并转换为 Python 对象。
* SQLAlchemy (ORM / Core) 层：负责组织数据库操作、构建 SQL 表达式、管理 Session 与事务。
* 数据库驱动（Driver）层：负责实现 Python 程序与具体数据库的底层网络/文件通信（如 Python 标准库自带的 sqlite3）。
* 数据库（SQLite）层：负责实际的数据持久化存储、SQL 语句执行以及数据库约束与事务的物理落实。

组件职责总结：Pydantic 管理数据结构与输入校验，SQLAlchemy 管理数据库操作，数据库驱动负责通信，数据库负责实际存储与执行约束。

### 5.2 端到端请求流转全流程
1. 用户发起 HTTP 请求。
2. FastAPI 框架调用 Pydantic 模型校验请求数据的合法性。
3. 路由函数将数据传递给 Service（服务层）。
4. Service 层调用 Repository（数据访问层）或直接调用 SQLAlchemy。
5. SQLAlchemy 生成 SQL 语句并通过数据库驱动发送至数据库。
6. 数据库执行 SQL 并返回结果给 SQLAlchemy。
7. FastAPI 结合响应模型将结果序列化并返回给客户端。

### 5.3 SQLAlchemy 核心对象与并发规则
使用 SQLAlchemy 时，需要准确区分三个核心概念：
* Engine（引擎）：管理数据库连接池与通信基础设施，在应用生命周期内长期复用。
* Connection（连接）：代表与数据库建立的单条物理/逻辑连接通道。
* Session（会话）：管理 ORM 对象状态、执行数据库操作与事务的工作单元。Session 应按请求或明确的工作单元创建与销毁。

并发安全规则：严格禁止多个线程或并发任务共享同一个 SQLAlchemy Session。在异步场景中，AsyncSession 同样不能由多个并发任务共同操作。

## 6 数据库迁移与安全演进流程

### 6.1 数据库迁移核心概念
数据库迁移是指通过一系列有序、可追溯的变更，将数据库 Schema（数据库结构）从旧版本升级到新版本，并同步完成必要的数据转换。
* Schema：表、字段、类型、索引、约束及外键等数据库结构的集合。
* Migration Script：描述结构变更及数据转换具体步骤的迁移脚本。
* Migration Version：标识数据库当前所处的结构版本节点。

### 6.2 安全执行数据库迁移 5 步流程
1. 备份数据库：确保备份真实可用。对于处于 WAL 模式下的 SQLite，必须使用专门的 WAL 备份命令，严禁直接复制主数据库文件。
2. 编写迁移脚本：明确旧结构与目标结构的差异，以及历史数据的转换规则。
3. 审查迁移内容：排查是否误删字段、丢失数据、破坏约束或产生非法数据状态。
4. 副本测试：在包含代表性历史数据的数据库副本上执行迁移脚本，验证正常与异常路径。
5. 应用与验证：在生产/目标数据库应用迁移，全面验证表结构、记录数、约束及业务流程正常运转。

### 6.3 迁移审查重点检查项
* 迁移脚本是否已纳入版本控制系统。
* 是否在真实的旧版数据副本上通过验证。
* 历史记录迁移后是否完整且满足新约束规则。
* 迁移中途失败时是否会产生不可识别的中间状态。
* 避免将重建测试数据库误认为是真实的数据库迁移操作。

## 7 数据完整性分类

### 7.1 数据完整性的四种类型
数据库完整性是保证数据质量与业务正确性的基石，分为以下四种类型：

* 实体完整性：保证每一条记录都能被唯一识别。主要依靠主键约束，要求主键唯一且非空。
* 参照完整性：保证外键引用的目标对象真实存在，避免出现孤立引用。
* 域完整性：保证字段值符合规定的数据类型、取值范围或允许的取值集合（如重试次数不能小于零）。
* 业务完整性：保证数据满足上层业务逻辑规则（如标记为成功的任务必须具备有效的处理结果与来源字段）。
