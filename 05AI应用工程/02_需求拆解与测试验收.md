## 1 需求分析与功能规格转化

### 1.1 需求、规格与任务的递进关系
在软件工程与 AI 协同开发中，需求、规格与任务构成了从想法到代码落地的递进体系：
* 需求定义：明确系统需要解决的核心问题。
* 功能规格：定义系统必须表现出的外部行为。
* 开发任务：定义如何分阶段实现这些行为。

与agent的协作：
* 低风险细节：对于容易调整、影响局部的细节，允许 AI 智能体依据项目现有约定自行决定，并在报告中进行说明。
* 高风险细节：涉及数据库事务、关联记录删除、用户权限校验等直接影响数据一致性或系统安全的问题，严禁完全交给 AI 智能体随意决定，必须提前人工确认。

将模糊的原始想法转化为精准的功能规格，需遵循以下五个递进步骤：
1. 明确用户与问题：梳理谁在什么情况下，需要解决什么问题。
2. 定义功能范围：明确本次开发做什么，以及明确不做什么。
3. 描述系统行为：详细描述用户执行操作后，系统应产生的具体响应。
4. 明确边界与异常：界定在何种条件下不能执行操作，以及发生失败时系统的表现。
5. 制定验收标准：给出客观可观察的断言证据，用以判断规格是否实现。

### 1.4 需求分析与规格制定提示词
可使用以下结构化提示词模板：

```text
我想为当前项目增加以下功能：

【原始需求】
用户可以删除历史对话。

请先分析需求和当前代码仓库，暂时不要修改代码。

1. 检查现有对话模型、数据库关系、删除接口、前端历史列表和相关测试。
2. 找出会影响实现结果的关键歧义、现有技术约束和潜在风险。
3. 区分必须由我确认的业务决策，与可以依据现有项目约定自行决定的实现细节。
4. 提出一份初步功能规格，说明正常行为、异常行为、数据影响和验收标准。
5. 不要仅为了实现这个功能而提出不必要的架构重构。

请先输出分析结果和待确认事项，等待我确认后再制定实施计划。
```

## 2 需求管理、范围控制与版本规划

### 2.1 需求管理三大要素与 MVP 特征
需求管理包含三个核心维度：
* 需求优先级：评估不同需求的业务价值与紧迫程度，决定开发顺序。
* 范围控制：明确当前版本做什么与不做什么，防止目标无休止扩张。
* 迭代规划：将确定要做的需求合理切分成不同阶段，每个阶段交付可验证的成果。

最小可行产品（MVP）的核心要求是用尽可能小的产品范围验证核心价值，其标准特征包括：
* 核心主干流程能够完整执行。
* 必要的异常路径得到妥善处理。
* 拥有明确可校验的验收标准。
* 不为暂时用不到的功能提前引入复杂的架构设计。

### 2.2 应对范围蔓延的四大规则
在开发过程中应对需求扩张，应严格遵循以下规则：
1. 每个版本先冻结范围：开始开发前，明确本阶段目标、必须完成的项及明确排除的项。
2. 灵感与新想法先记录待办：开发期间产生的新需求统一进入待办列表，除非该项暴露了严重安全漏洞、核心缺陷或初始规格漏项。
3. 新增需求评估收益与成本：阐明新需求解决的问题、受影响的模块，以及增加的测试、维护和部署成本。
4. 插入需求必须动态平衡：新增高优先级需求时，必须相应减少同等工作量的其他任务，严禁无条件压榨交付时间。

### 2.3 版本规划与变更影响分析提示词
评估版本计划或针对中期需求变更进行影响分析时，可使用以下提示词模板：

```text
版本计划制定提示词模板：

请检查当前项目和现有需求规格，为下一阶段制定开发计划。

要求：
1. 将需求分为 Must、Should、Could、Won't（本版本不做）。
2. 说明每项需求的价值、依赖关系和主要风险。
3. 将 Must 拆分为范围可控、可独立验证的开发任务，并标明任务依赖。
4. 明确本阶段的交付目标、验收标准和不包含的内容。
5. 优先复用现有实现，避免不必要的架构改造和提前抽象。

本次只输出分析和计划，不修改代码。遇到影响业务行为、安全或数据一致性的关键歧义时，先列出问题，不要擅自决定。
```

```text
变更影响分析提示词模板：

请分析这项需求变更对当前项目的影响，暂时不要修改代码。

请说明：
1. 它属于缺陷修复、需求澄清、安全/可靠性改进、功能扩展还是需求替换。
2. 不处理它会造成什么后果。
3. 它会影响哪些现有功能、模块、数据、测试或配置。
4. 是否有更小、更低风险的实现方案。
5. 如果接受，需要更新哪些规格、验收标准和测试。

明确区分已确认的事实与推测。若涉及业务行为、安全或数据一致性的关键歧义，请提出需要确认的问题。最后给出建议：接受、缩小范围、暂缓或拒绝。
```

## 3 从需求推导测试设计

### 3.1 有效测试的三大条件
高质量的自动化测试必须同时具备以下三个条件：
* 对准需求：测试检查的逻辑必须直接对应明确的需求规格或验收标准，不写脱离业务逻辑的无效测试。
* 检查正确结果：测试不能仅满足于“没有崩溃”或“有返回值”，必须严格校验返回值、数据库数据状态以及页面实际行为是否完全符合预期。
* 有能力发现缺陷：测试代码必须具备针对性，当程序出现典型错误或异常时，测试能够高概率报错触发失败。

### 3.2 从需求到断言的推导链路与概念辨析
合理的测试推导路径为：需求规格 → 验收标准 → 测试用例 → 测试断言。三者的核心区别如下：
* 验收标准：定义在何种业务条件下、达成何种结果才算通过验收。
* 测试用例：明确具体的输入数据、操作步骤及预期结果描述。
* 测试断言：在代码层面具体校验条件的语句（例如：assert status == "failed"）。

| **测试用例** | **操作步骤** | **关键预期结果** |
| ------ | ------ | ------ |
| TC-01：获取成功 | 模拟接口成功返回网页内容 | 数据库记录的状态更新为 success |
| TC-02：获取失败 | 模拟网络请求超时 | 数据库记录的状态更新为 failed，绝不能记为 success |
| TC-03：刷新页面 | 获取完成后重新加载页面记录 | 前端页面展示的状态与数据库保存的状态保持一致 |

推导编写时需注意：
1. 消除模糊主观词汇，将其转化为客观可观察的结果（如“失败时妥善处理”应明确为“返回 404 时数据库记为 failed 且不产生错误成功记录”）。
2. 一个测试用例可以同时校验多个关联断言；复杂的验收标准也可拆分为多个测试用例覆盖。

### 3.3 测试设计的三个核心维度与复杂系统验证
进行测试用例设计时，应从以下三个维度展开：
* 正常路径：验证标准输入与顺畅流程下的主干业务逻辑。
* 异常路径：验证网络超时、数据缺失、接口故障或非法输入下的容错处理机制。
* 边界条件：验证极端数值、空值、超长文本或临界状态下的稳定性。

针对复杂系统（如 RAG 或 Agent）的测试需额外注意：
* RAG 系统：单次回答正确不代表质量稳定，需使用固定测试数据集与预设评价标准进行多轮测试。
* Agent 系统：除最终输出外，需重点检查工具调用逻辑、失败恢复机制以及是否存在越权行为。

### 3.4 引导智能体拆解需求与测试推导提示词
引导 AI 智能体设计并执行测试的标准六步工作流：
1. 梳理业务需求，提取对应的验收标准。
2. 识别正常路径、关键异常路径与核心边界条件。
3. 为每个测试明确输入、操作步骤与预期结果。
4. 审查测试是否真正校验了业务逻辑与数据持久化状态。
5. 执行测试，分析失败原因并修复缺陷。
6. 排除过弱断言（如仅检查非空）、未触发目标场景或与实现逻辑过度耦合的无效测试。

```text
引导智能体测试验证提示词模板：

检查当前功能的测试是否真正验证了需求。

根据需求和验收标准，检查现有测试的输入、执行路径、断言及覆盖场景，重点识别只检查非空、没有验证持久化状态、未真正触发异常等无效测试。

先报告发现的问题及依据，再补充必要的测试。运行相关测试，并说明每个关键验收标准的验证结果、未覆盖场景和剩余风险。不要为了让测试通过而修改正确的业务预期。
```

## 4 改动风险评估与验证分级

### 4.1 评估改动风险的四个核心维度与基本原则
评估一项代码改动的风险，需从以下四个维度综合判断：

| **风险维度** | **评估考量关键点** |
| ------ | ------ |
| 影响范围 | 改动仅作用于局部函数，还是会波及多个模块与核心用户功能？ |
| 失败后果 | 出错后仅影响视觉美观，还是会导致数据丢失、信息泄露或服务不可用？ |
| 可恢复性 | 发生故障后能否快速修复上线，还是会造成不可逆的数据破坏？ |
| 不确定性 | 是否涉及复杂的业务逻辑、外部第三方 API、高并发或未知系统行为？ |

评估核心原则：
* 代码改动行数不等于风险大小。修改一行权限校验代码可能关乎全局数据安全，而修改几十行文档注释几乎没有运行风险。
* 评估风险应聚焦于改动失败可能引发的后果严重程度，而非修改代码的数量。

### 4.2 风险分级（L1~L3）与差异化验证策略
根据风险评估结果，采取分级验证策略：
* 低风险（L1）：适用于文档说明、代码注释修改及不影响逻辑的微调。验证方式为检查 Git Diff，确认无无关改动，必要时执行静态检查。
* 中风险（L2）：适用于业务逻辑变更、数据处理调整、内部接口改动。验证方式为运行相关单元测试，校验正常与关键异常路径，检查数据状态一致性并执行必要集成测试。
* 高风险（L3）：适用于权限认证、数据删除、外部 URL 内容抓取、安全校验、数据库 Schema 迁移等。验证方式为覆盖攻击场景与边界条件，验证失败数据一致性与副作用，执行深度集成与回归测试，必要时进行人工操作验证或 independent 安全审查。

### 4.3 风险升级规则与智能体评估规范
评估与协作注意事项：
1. 低风险不等于免检，仅代表验证方式更轻量。
2. 高风险不等于盲目堆砌测试，应优先覆盖发生概率最高、后果最严重的失败模式。
3. 升级规则：若改动涉及公共接口定义、核心依赖版本或通用数据结构，即使修改行数极少，也必须主动提高风险验证等级。

```text
安排智能体评估与修复任务提示词模板：

修复文档获取后的状态保存问题。

先检查相关代码、现有测试和需求，评估本次改动的风险等级，并说明判断依据。

实现修复后，根据风险和验收标准执行必要的测试，重点验证获取成功、获取失败、数据库状态持久化及刷新后的状态一致性。

报告实际执行的测试及结果、未验证的验收项和剩余风险。不要将未执行或未覆盖的验证报告为通过。
```

智能体协作规范：要求智能体先评估风险再修改代码；验证手段必须对准需求而非仅追求测试套件 pass；汇报中严格区分实际执行证据与推测；开发者必须保留最终审查权（智能体易低估数据一致性与跨模块副作用）。

## 5 测试覆盖率、回归测试与范围决策

### 5.1 测试覆盖率指标与初学者优先级
测试覆盖率用于统计测试执行时代码被运行的比例。行覆盖率计算公式为：
行覆盖率 = (执行过的代码行数 / 可统计的代码总行数) * 100%

主要指标包含：
* 行覆盖率：可执行代码行被运行的比例。
* 分支覆盖率：条件判断语句（如 if/else）中 True/False 分支被执行的比例。
* 函数覆盖率：代码库中函数被调用的比例。

覆盖率的局限：代码被执行过不等于行为被正确校验，高覆盖率不等于高测试质量。初学阶段合理的测试优先级为：
1. 确保核心业务主路径有测试。
2. 确保关键异常与极端边界有测试。
3. 确保测试断言校验了真实的业务结果。
4. 利用覆盖率工具寻找未测试的代码区域查漏补缺。

### 5.2 回归测试核心逻辑与功能测试的区别
回归测试是在代码修改后重新运行既有测试，验证本次改动没有破坏原有正常功能。
其核心逻辑流为：修改代码 → 验证本次修改的正确性 → 重新运行受影响的旧测试 → 确认新旧功能均符合预期。

两者的核心区别在于：
* 功能测试：检查新开发或修改的某项功能是否符合需求规格。
* 回归测试：代码变更后，检查既有功能是否依然维持正确行为。同一测试用例可同时承担这两种职责。

### 5.3 测试范围的三种类型与六步决策工作流
测试范围由改动影响范围、风险等级与验证成本共同决定，分为三种类型：
* 定向测试：仅针对本次修改的代码或函数执行精确定向校验。
* 相关回归测试：针对与改动存在直接或间接依赖关系的上下文模块执行回归校验。
* 全量测试：运行项目完整的自动化测试套件。

六步标准决策工作流：
1. 检查 Git Diff，识别实际代码改动。
2. 分析直接依赖、下游影响与潜在风险。
3. 运行与改动直接相关的定向测试。
4. 根据依赖关系与风险评估运行相关回归测试。
5. 必要时运行全量测试；若未运行全量测试，需在汇报中说明未执行原因。
6. 对照验收标准，汇总测试证据与剩余风险。

### 5.4 常见改动场景决策表与独立/公共函数案例

| **改动场景** | **建议的验证方式** |
| ------ | ------ |
| 修改文档或代码注释 | 检查 Git Diff，执行轻量校验 |
| 修改独立的纯函数 | 运行该函数的单元测试（正常、边界、异常输入） |
| 修改数据库状态逻辑 | 运行单元测试、集成测试及相关回归测试 |
| 修改公共接口或共享模块 | 扩大测试范围，运行关联模块回归测试 |
| 修改认证、权限、安全校验或数据迁移 | 执行全面边界、安全专项验证与深度回归测试 |
| 准备发布版本 | 运行全量测试套件及部署验证 |

实战对比案例：
* 修改独立的格式化函数（如文档标题显示格式）：先确认 Git Diff 局限于该函数，运行对应单元测试。若依赖简单、测试正常，无需立即触发全量测试。
* 修改公共文本规范化函数（被文本分块、向量索引和检索模块共同调用）：必须扩大测试范围，进一步验证所有依赖它的下游模块。

智能体完成任务后必须汇报 6 项内容：修改的业务行为、已校验的验收标准、新增/修改的测试、回归测试结果、覆盖率暴露的盲区、未覆盖场景。

## 6 需求追溯与闭环交付管理

### 6.1 闭环管理定义与需求追溯机制
闭环管理的定义：闭环不是指“代码编写完成”，而是指“需求得到充分验证、结果经过客观判断、不达标项有明确处理与修复”。

实现闭环的关键是建立需求追溯机制：
* 为需求、验收标准与测试用例分配稳定的唯一标识（如 REQ-01、AC-01、TC-01）。
* 当需求变更时，可沿着追溯链条迅速定位受影响的验收标准、测试用例与代码模块。
* 小型任务可记录在报告中，复杂任务可维护需求追踪表：

| **需求 ID** | **验收标准 ID** | **测试用例 ID** | **验证目标** |
| ------ | ------ | ------ | ------ |
| REQ-01 | AC-01 | TC-01 | 正常获取正文 |
| REQ-01 | AC-02 | TC-02 | 超时时返回失败 |
| REQ-01 | AC-03 | TC-03 | 失败记录不能标记为成功 |
| REQ-01 | AC-04 | TC-04 | 刷新后获取记录仍然存在 |

### 6.2 验收证据的三层级与六步闭环流程
验收证据分为三个层级：
* 代码层：代码是否实现了逻辑、处理了异常、保障了数据状态。
* 测试层：自动化测试是否覆盖了正常、异常与关键边界条件，回归测试是否通过。
* 实际行为层：用户真实操作下，系统是否产生预期结果，数据重启或刷新后是否保持一致。

标准六步闭环流程：
1. 确认需求规格。
2. 提取验收标准。
3. 设计测试用例。
4. 实施最小功能增量。
5. 执行验证并记录客观证据。
6. 审查并做出交付判断。

### 6.3 交付结项五项检查与三条硬性闭环规则
每个任务结项时必须执行五项检查：
1. 本次任务对应哪些需求和验收标准？
2. 哪些测试校验了这些标准？
3. 测试是否实际执行，具体结果如何？
4. 哪些标准尚未验证，具体原因是什么？
5. 是否存在遗留问题或未经批准的范围变更？

同时严格遵守三条硬性闭环规则：
1. 同步变更规则：需求发生变更，对应验收标准与测试用例必须同步调整。
2. 测试不等于验收规则：测试通过不等于所有需求已通过业务验收。
3. 禁止默认通过规则：未验证的必需项严禁默认标记为通过，必须持续跟进验证或标明未完成。

### 6.4 验收报告与追溯维护提示词

```text
任务验收报告提示词模板：

请依据本任务的验收标准验证实现结果。

1. 逐条列出验收标准及其状态：通过、未通过或未验证。
2. 说明每项标准对应的测试方法和实际结果。
3. 列出实际执行的测试命令及结果；明确区分已执行和未执行的测试。
4. 如果存在未通过或未验证项，说明原因，不要将其报告为已完成。
5. 检查相关回归风险，并列出尚未解决的问题。

如果发现实现不符合验收标准，请先修复，再重新运行相关测试。不要仅根据代码看起来正确就判定通过。
```

```text
追溯链路维护提示词模板：

请根据当前任务的需求规格，建立并维护完整的验收追踪链路。

1. 为需求、验收标准和测试用例分配稳定的 ID。
2. 确保每项关键验收标准都有对应的验证方式。
3. 实现功能时，为相关代码和测试建立可核查的对应关系。
4. 执行适当的测试，并逐条记录验收标准的状态：通过、未通过或未验证。
5. 明确列出未覆盖的标准、未执行的测试、失败原因和剩余风险。
6. 如果发现需求存在歧义或需要扩大任务范围，先说明问题，不要擅自改变已确认的业务要求。

最终报告必须区分实际执行结果与推测，不得仅凭代码已修改或测试文件已编写就判定任务完成。
```
