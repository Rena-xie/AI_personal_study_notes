## 1 异常控制与架构分层

### 1.1 异常处理核心概念区分

在构建可靠的系统时，首先需要清晰区分三个经常混淆的概念：

* 错误情况：实际发生了某个问题，例如网络请求超时或文件不存在。
* 抛出异常：程序通过语言层面的异常机制向调用链上层报告发生的错误。
* 处理异常：程序捕获异常，并按照约定采取行动，例如返回失败结果、记录日志或执行清理。

### 1.2 架构分层的异常处理职责

不同架构层级在面对错误时有着明确分工，避免将底层细节直接暴露出系统边界：

| 层级 | 主要职责 | 示例 |
| ------ | ------ | ------ |
| 基础设施层 | 识别底层故障，必要时转换成项目定义的异常 | 将 HTTP 客户端超时转换为 DocumentFetchTimeout |
| 业务服务层 | 根据业务规则决定下一步行为和状态 | 获取失败后不调用 LLM，不标记任务为成功 |
| API 层 | 把内部结果转换为对外契约 | 将已知获取失败映射为适当的 HTTP 错误响应 |

### 1.3 流程问题的四大分类与应对策略

整个业务流程中出现的故障通常可以归结为以下四类：

1. 输入错误
* 定义：问题来自请求数据不符合要求，例如 URL 格式错误、必填字段缺失或字符串长度超出限制。
* 处理思路：尽早校验，直接返回明确的输入错误信息，避免触发不必要的网络请求或后端计算。

2. 业务规则错误
* 定义：请求本身格式合法，但不符合具体的业务逻辑规则，例如重复提交不允许重复创建的任务，或尝试操作不存在的学习记录。
* 处理思路：根据业务规则明确拒绝请求、返回对应的业务错误，或执行既定的替代动作。

3. 外部依赖故障
* 定义：系统所依赖的外部服务、网络或资源发生故障，例如网页连接超时、LLM API 限流、数据库暂时不可用。
* 处理思路：根据故障类型决定是否重试、是否降级、如何返回失败，以及如何保证内部数据状态的最终正确。

4. 程序缺陷
* 定义：代码本身存在逻辑错误或违反设计契约，例如访问不存在的字典键、错误地把获取失败标记为成功、传递了不正确的参数。
* 处理思路：定位根因、修复代码并增加有效测试。不能将程序缺陷简单包装成普通业务失败后就不再处理。

## 2 边界条件与防御式编程

### 2.1 边界条件的定义

边界条件是指程序在输入、状态、资源或运行环境接近允许范围边缘时需要正确处理的情况。典型的边界场景包括空数据输入、超长字符串、达到并发上限或临界时间点。

### 2.2 防御式编程的设计原则

防御式编程的核心理念是：不要盲目假设输入数据、外部依赖和运行状态永远符合预期，而是在关键逻辑节点主动建立合理的约束与检查机制，防止异常状态扩散。

## 3 超时与资源控制策略

### 3.1 超时控制的四个维度

系统中的超时机制通常分布在多个环节，不同环节的控制重点各不相同：

| 超时类型 | 控制什么 | 示例 |
| ------ | ------ | ------ |
| 连接超时 | 建立网络连接需要等待多久 | 无法连接目标服务器 |
| 读取超时 | 等待响应数据时，多久没有收到数据就停止等待 | 服务器建立连接后迟迟不返回数据 |
| 总时限 | 整个操作最多允许持续多久 | 获取网页及其后续处理必须在总预算内完成 |
| Task Timeout | 一个完整任务最多运行多久 | 获取文档、解析和模型调用的整个工作流 |

### 3.2 资源控制的三大维度

超时控制关注“最多等多久”，资源控制关注“最多消耗多少”。合理的资源上限可以防止单个异常请求无限占用系统资源：

1. 时间限制
控制 HTTP 连接、数据读取、整个任务的耗时上限，以及 LLM 调用的截止时间。

2. 数据大小限制
对 HTTP 响应体、上传文件大小、提取的正文文本长度进行明确限制，避免超大内容挤爆系统内存。

3. 计算与模型预算
限制并发任务数量、LLM 单次输入的 Token 数量、输出的 Token 数量，以及单次调用的整体费用预算。

## 4 容错机制：重试、幂等、降级与隔离

### 4.1 重试机制与退避策略

* 重试：当一次操作失败后，根据预先定义的规则，再次执行该操作。
* 退避：失败后不立即重试，而是等待一段时间，再进行下一次尝试。通常使用指数退避或随机抖动退避，以防止短时间内对下游服务造成二次冲击。

### 4.2 幂等性与重复执行控制

幂等性是指对于同一个业务操作，在相同条件下执行一次或多次，最终产生的业务效果是相同的。确保幂等性可以避免重复执行时产生重复数据、额外费用或错误的业务状态。

实现幂等性的三种常用方法：

* 方法 1：使用唯一约束（通过数据库唯一索引或主键约束防止重复插入）
* 方法 2：先检查，再执行（在执行关键写操作前检查记录是否已存在或已处理）
* 方法 3：使用幂等键（为每一次业务请求分配唯一的 Token 或请求标识，服务端据此判断是否已处理过该请求）

### 4.3 降级、熔断与故障隔离

当某个外部服务持续故障时，需要通过以下手段防止故障扩散：

* 降级：当部分能力不可用时，改用较简单的方式继续提供服务（例如 LLM 不可用时直接返回模版正文）。
* 熔断：当依赖服务持续故障且失败率达到阈值时，暂时停止向该服务发送请求，直接返回失败，给下游服务恢复的时间。
* 故障隔离：限制故障的传播范围，避免一个组件的问题拖垮整个应用。常见的隔离方式包括：组件隔离、并发隔离与限流、资源池隔离。

## 5 数据一致性与失败恢复

### 5.1 数据一致性的多维表现

数据一致性指的是系统保存的状态、实际完成的操作和对外报告的结果彼此一致，不互相矛盾。它涵盖以下四个核心维度：

* 状态是否真实：记录的成功与失败状态是否完全符合实际执行结果。
* 内容是否匹配：生成的回答、文档来源和学习记录是否属于同一次任务。
* 状态转换是否合法：失败的任务是否被错误地标记为成功，状态迁移是否顺畅。
* 对外反馈是否准确：用户是否能够准确知晓哪些步骤成功完成、哪些步骤处理失败。

### 5.2 数据库事务的局限性

事务可以把一组数据库操作作为一个整体提交或回滚。如果事务中的某些数据库操作失败，数据库可以回滚这一组尚未提交的更改。

但必须特别注意：数据库事务不能自动回滚已经发生的外部网络操作或第三方 API 调用。因此，绝不能把整个 HTTP 网络请求和 LLM 调用包在一个长时间运行的数据库事务中。

### 5.3 失败恢复的四大关键机制与术语区分

为了让系统从故障中平滑恢复，需要具备以下四项关键机制：

1. 保留已有成果（保留中途已成功获取或处理的中间数据，减少重复消耗）
2. 区分重试与恢复
   * 重试：再次执行失败的操作（例如 LLM 请求遇到暂时性网络波动后直接重试）。
   * 恢复：让业务从故障后的实际状态继续推进（例如复用已保存的文档重新生成讲解，再补写学习记录）。
3. 使用幂等性防止重复副作用
4. 让失败状态与真实结果一致

失败恢复相关的三个技术术语区分：

* 回滚：撤销事务中尚未提交的数据库更改。
* 补偿：通过发起后续的纠正操作（如退款、反向抹平）来修正已经发生的业务影响。
* 恢复：根据当前的真实状态决定继续执行、重试、补偿还是终止任务。

## 6 可靠性测试与故障注入

### 6.1 可靠性测试与故障注入概念对比

* 异常测试：专注于验证特定异常场景下的系统行为。
* 故障注入：指主动制造或模拟故障，观察系统是否能够按照预期正确应对。
* 可靠性测试：包含故障注入在内的更广泛范畴，用于验证系统在异常条件、依赖故障、资源压力或重复操作等情况下是否仍符合预期行为约定，包括恢复能力与长时间运行表现。

### 6.2 常见故障类型与注入方式

根据故障发生的位置，可以在测试中使用对应的模拟注入方式：

| 故障类型 | 注入方式 | 主要验证目标 |
| ------ | ------ | ------ |
| 网络超时 | Mock 抛出超时异常 | 是否按契约返回错误、更新状态 |
| HTTP 500 / 429 | Mock 返回指定响应或抛出对应异常 | 是否正确分类和处理错误 |
| 无效网页内容 | 返回空正文、纯空白或不符合预期的 HTML | 是否拒绝无效内容 |
| LLM 调用失败 | 模拟超时、限流或服务不可用 | 是否有限重试、正确降级 |
| 数据库写入失败 | 让数据库操作抛出异常 | 是否避免误报成功、正确处理事务 |
| 重复请求 | 连续提交相同任务标识 | 是否产生重复记录或重复副作用 |
| 进程中断 | 在受控环境中中断任务 | 是否能识别未完成任务并恢复 |

注意：不需要真实破坏物理底层系统。在开发过程中，使用 pytest 和 monkeypatch 模拟依赖故障即可覆盖绝大部分业务逻辑。

### 6.3 可靠性测试设计检查清单

在进行测试设计时，应当逐项核对以下 8 项标准：

* [ ] 网络超时：请求按规定时限结束，错误处理符合约定
* [ ] HTTP 错误：不同状态码按服务契约处理
* [ ] 无效正文：不将空白或无效内容误判为成功
* [ ] LLM 故障：重试次数有上限，最终状态准确
* [ ] 数据库故障：不误报持久化成功，检查部分写入
* [ ] 重复提交：同一任务不产生重复业务记录
* [ ] 故障恢复：依赖恢复后，任务能按设计重新执行
* [ ] 安全性：错误响应不暴露密钥、堆栈或敏感内部信息

### 6.4 常规故障注入与混沌工程对比

| 对比 | 常规故障注入 | 混沌工程 |
| ------ | ------ | ------ |
| 主要目标 | 验证特定故障处理逻辑 | 检验系统整体在真实或复杂故障下的韧性 |
| 实施范围 | 通常是测试代码、组件或测试环境 | 可以涉及多服务、网络、基础设施 |
| 故障方式 | 可控地模拟异常、超时、失败 | 可能注入延迟、断连、实例终止等故障 |
| 适用阶段 | 开发阶段即可使用 | 通常在具备监控、隔离和恢复能力后开展 |

## 7 可靠性建设的演进路径与审查维度

### 7.1 可靠性逐步完善的六步路径

构建可靠系统不需要一步到位，建议按照以下六步渐进演进：

1. 第一步：明确错误语义和任务状态。先保证系统能够清晰区分完整成功、部分成功和失败。
2. 第二步：完善超时与资源限制。防止任务无限等待、下载过大响应或消耗过多 Token。
3. 第三步：加入有边界的重试。明确可重试错误类型、重试次数、退避策略和总截止时间。
4. 第四步：防止重复副作用。通过唯一任务标识、数据库约束和业务逻辑检查处理重复提交。
5. 第五步：验证失败恢复。检查系统中断后哪些中间成果能够保留、哪些步骤可以安全重做。
6. 第六步：建立故障测试。用 Mock、集成测试和必要的故障注入逐项验证系统应对故障的行为。

### 7.2 系统可靠性审查的六个核心问题

在进行代码审查与架构评估时，可以围绕以下六个维度进行全面核查：

1. 输入与边界是否安全？是否检查了无效输入、空数据、资源上限以及 URL 抓取的安全边界？
2. 操作是否有时间和资源上限？是否设置了必要的连接超时、总时限、重试上限、并发与费用约束？
3. 重复执行是否安全？在重试、重复点击或响应丢失后重发时，是否会造成重复记录或额外副作用？
4. 故障是否被隔离？某一个外部依赖失败时，是否会耗尽共享资源或拖垮其他功能？是否需要降级？
5. 状态和数据是否一致？失败后是否准确记录了已完成步骤、最终状态和可恢复信息？
6. 是否有足够的验证证据？正常、异常、边界、重复执行与恢复场景是否经过测试？断言是否能发现真正的缺陷？
