* **核心链路**：LLM（大语言模型）生成结构化 Tool Call（工具调用）请求 → Runtime（运行时）校验与授权 → 执行工具 → 将 Observation（观察结果）返回模型。

## 1 Tool Calling（工具调用）的概念与接口

### 1.1 从 Function Calling（函数调用）到 Tool Calling

**Function Calling（函数调用）** 是较早的典型叫法，强调模型生成结构化参数，以调用本地代码函数。

**Tool Calling（工具调用）** 是更广义、更贴近生产环境的概念：工具既可以映射到函数，也可以封装其他外部能力。

* 编程语言原生函数。
* REST API 与 Web 服务。
* 数据库查询与写入。
* 搜索引擎接口。
* MCP Server。
* 操作系统命令、Shell 脚本与 GUI 自动化。

### 1.2 工具定义与 Schema（模式）契约

Tool Schema（工具模式）是模型生成调用参数时遵循的接口契约。一个可执行 Tool 的完整定义还包含模型不可直接执行的绑定和结果约定。

* **Name（名称）**：
  * *作用*：工具的稳定唯一标识。
  * *要求*：语义明确，避免名称相似的工具让模型误选。
* **Description（描述）**：
  * *作用*：说明功能、适用场景和调用边界。
  * *要求*：同时说明“何时调用”与“何时不应调用”。
* **Input Schema（输入模式）**：
  * *作用*：用 JSON Schema 定义调用参数。
  * *要求*：声明参数名、类型、必填项、枚举值和其他取值范围。
* **Execution Binding（执行绑定）**：
  * *作用*：把工具名绑定到实际函数、API 或适配器。
  * *要求*：检查版本与部署一致性，避免调用到错误实现。
* **Output Contract（输出契约）**：
  * *作用*：约定成功、失败和部分成功的结果格式。
  * *要求*：区分业务数据、错误信息和 Metadata（元数据）。

### 1.3 一次工具调用的执行链路

```text
应用向 LLM 提供允许使用的工具定义
                ↓
LLM 生成 Tool Call（工具名、参数、调用 ID）
                ↓
Runtime 解析并校验名称、参数、权限和风险
                ↓
查找绑定的执行函数或工具适配器
                ↓
执行并捕获结果、异常与执行状态
                ↓
将结果与调用 ID 关联，更新 State
                ↓
把清洗后的 Observation 交回 LLM
                ↓
LLM 继续调用工具或生成最终回答
```

工具返回成功只表示该原子操作完成，不代表用户任务已经完成。模型仍需根据 Observation 判断是否继续、重试、改道或终止。

### 1.4 Runtime 的分层校验

* **Schema（模式）校验**：检查必填字段、参数类型、枚举值、格式和取值范围。
* **业务规则校验**：确认资源属于当前任务，操作满足业务前置条件。
* **路径与目标校验**：规范化路径或资源标识，阻止目录穿越、越权对象和符号链接。
* **身份与权限校验**：校验用户、租户、工具权限和下游凭据，不能只依赖 Prompt 自我约束。
* **执行环境控制**：通过最小权限、超时、网络限制和沙箱约束实际能力。

## 2 MCP（Model Context Protocol，模型上下文协议）

### 2.1 定义与职责边界

MCP（模型上下文协议）用于标准化 AI 应用与外部工具、数据源及上下文能力之间的连接。

可将其类比为 USB-C：统一接口降低了连接成本，但设备仍需满足供电、通信和能力约束。MCP 也不只是“连接器”，还定义了初始化、能力发现、请求与响应等交互方式。

![[Tool与MCP.png]]

一次远程工具调用的职责可以拆为：

* **LLM**：判断是否需要工具，并生成结构化调用请求。
* **MCP Host（宿主应用）**：承载应用逻辑、模型上下文和整体权限策略，决定向模型暴露哪些工具。
* **Runtime（运行时）**：组织 Agent Loop，并执行参数、权限、预算和审批控制。
* **MCP Client（客户端）**：在 Host 内管理与 MCP Server 的协议连接和消息调度。
* **MCP Server（服务端）**：处理协议请求并调用底层工具实现；独立封装数据源或操作能力，向 Client 暴露受控接口。
* **底层实现**：真正访问数据库、调用 API、读写文件或操作其他系统。

不同框架可能重新划分这些模块，但“模型决策、Runtime 控制、Server 执行”的核心边界不应混淆。

### 2.2 从连接到执行

* 第 1 步，配置 Server：填写启动命令或远程地址，并配置环境变量和认证信息。
* 第 2 步，建立连接：Client 与 Server 初始化，协商协议版本和支持的能力。
* 第 3 步，发现能力：Client 获取工具、Resources 或 Prompts；工具信息包含名称、描述和参数 Schema。
* 第 4 步，筛选并暴露工具：Host 按任务和权限选择允许使用的工具，再转换为模型可理解的接口格式。
* 第 5 步，模型决策：LLM 生成调用请求，或直接生成最终回答。
* 第 6 步，控制并发送请求：Host 检查权限、参数和风险，Client 通过 MCP 发送 `tools/call`。
* 第 7 步，Server 执行：Server 调用底层能力，按协议返回结果或错误。
* 第 8 步，回传 Observation：Runtime 更新状态并再次调用模型，由模型决定继续调用还是结束。

### 2.3 将现有 API 封装为 MCP Tool（工具）

假设已有接口 `POST /search`，可按以下方式接入：

* 在 MCP Server 中定义一个工具 `search_knowledge_base`，声明用途、必填参数 `query` 和参数 Schema。
* 实现工具函数：收到调用后，把 `query` 转为对 `/search` 的 HTTP 请求，并规范化返回结果和错误。
* 在 Agent Host 中配置 Server 的启动命令或连接地址，建立连接并发现工具。
* Host 将适用工具暴露给模型；模型提出调用后，由 Runtime 控制执行，Server 调用底层接口并回传 Observation。

## 3 运行控制与工程保障

### 3.1 循环终止与资源控制

仅依靠 Prompt 要求模型“不要循环”并不可靠，Runtime 需要配置确定性规则：

* **最大步数或轮次**：限制单次任务的模型调用和工具调用次数。
* **超时与 Token / 成本预算**：任一预算耗尽时停止、降级或返回受控错误。
* **重复调用检测**：识别相同工具和相同参数的连续调用，阻止无效循环。
* **可控降级**：多次失败后停止自动重试，向用户说明失败原因并提供已获得的局部结果。
* **明确终止条件**：正常完成、达到上限、预算耗尽、安全校验失败、用户取消或不可恢复异常都应结束当前循环。

### 3.2 高风险操作的人机审批

删除数据、修改生产配置、发送外部邮件、发起支付等高风险操作，不应完全由模型自主决定：

* **挂起（Suspend）**：Runtime 判断操作命中高风险规则后，保存当前 State（状态）并暂停执行。
* **展示影响**：前端至少展示工具名称、参数、目标对象、预期副作用和风险等级。
* **批准（Approve）**：恢复状态机，再由 Runtime 执行真实操作。
* **拒绝（Reject）**：把“用户拒绝”写入 Observation，引导模型重新规划或直接结束。
* **修正参数**：人工修改参数并批准，修改后的值仍需重新校验。

### 3.3 评估与可观测性

可使用 LangSmith、Arize Phoenix 等平台，也可自建追踪系统；平台不是前提，关键是保留可回溯的调用轨迹。

* **Routing Accuracy（路由准确率）**：是否在正确场景选择正确工具，而不是无关工具或直接回答。
* **Schema Compliance（模式合规率）**：生成参数满足类型、必填项和取值约束的比例。
* **Invalid and Repeated Call Rate（无效与重复调用率）**：同类失败是否反复出现，是否存在死循环。
* **Task Success Rate（任务成功率）**：最终结果是否满足用户目标和验收条件。
* **Context Faithfulness（上下文忠实度）**：最终结论是否依据工具 Observation，而非编造数据。
* **Latency and Cost（延迟与成本）**：调用耗时、Token（词元）消耗、外部 API 费用和重试开销。

追踪记录建议包含调用 ID、工具名称与版本、脱敏后的参数、结果状态、耗时、重试、审批和错误信息。工具调用的评测与线上观测可分别衔接 [[_自动化评测]] 和 [[_LLMOps与可观测性运维]]。
