## 1 外部工具集成场景

### 1.1 典型外部能力

在实际 AI 应用开发中，智能体通常需要接入以下六类典型的外部能力：

1. **企业 RAG 知识库**：检索私有文档、规章制度、技术规范或历史工单。
2. **网络搜索**：获取互联网上的实时新闻、网页动态与最新公开资料。
3. **数据库系统**：查询客户信息、订单记录、库存数据或统计报表。
4. **业务 API 接口**：创建业务工单、发送通知邮件、发起支付或调用内部微服务。
5. **文件系统**：读取项目源代码、解析本地配置文件、写入生成报告或处理数据表格。
6. **MCP 服务**：通过标准化协议接入已暴露能力规范的远程或本地服务。

## 2 外部工具集成的分层架构

### 2.1 工具接入四层架构

为了保证智能体运行的稳定性与安全性，外部工具集成机制在架构上必须进行明确的分层设计，划分出决策、控制、工具与结果处理四层职责。

| 架构层次     | 担当角色            | 核心职责                                      | 核心回答的问题                 |
| -------- | --------------- | ----------------------------------------- | ----------------------- |
| **决策层**  | 大语言模型      | 根据当前任务目标与上下文，提出工具调用请求及参数                  | 下一步应该做什么？应该调用哪个工具？      |
| **控制层**  | 运行时    | 组织流程执行，实施参数结构校验、权限检查、人工审批与终止控制            | 当前这项工具调用请求是否允许被执行？      |
| **工具层**  | 工具适配器 | 连接实际外部系统，发起网络通信、数据库查询或文件读写                | 如何向外部系统发送指令并获取真实返回值？    |
| **结果处理层** | 结果治理模块          | 校验工具返回值、记录操作日志、更新状态，并将有效数据拼装为上下文 | 工具执行是否成功？哪些返回数据需要提交给模型？ |

### 2.2 能力类型与上下文划分

| 外部能力类型 | 推荐封装的工具接口 | 适合进入上下文的数据内容 |
| ------ | ------ | ------ |
| **RAG 知识库** | 知识库检索工具、文档全文拉取工具 | 经过相关性筛选与重排后的高价值文档片段及来源标识 |
| **网络搜索** | 网页搜索工具、网页正文提取工具 | 与当前任务直接相关的搜索结果摘要、核心网页片段 |
| **数据库** | 客户信息查询接口、订单受控查询接口 | 数据库查询返回结果中满足当前任务所需的必要字段 |
| **业务 API** | 工单创建接口、订单状态变更接口 | API 响应的操作状态、业务流水号、操作结果反馈 |
| **文件系统** | 受限目录文件读取工具、文件写入工具 | 决策所需的目标文件段落、格式化解析数据、写入结果 |
| **MCP 服务** | 通过 MCP 客户端调用的远程工具或资源 | 通过 MCP 协议获取并经过筛选后的标准化资源与数据 |

## 3 高质量工具接口设计

### 3.1 八项设计要素

一个具备生产级可靠性的工具接口，不能只是简单函数，而应包含以下八个维度：

1. **名称**：具备明确语义的标识符，清晰表达工具的核心用途。
2. **描述**：详细说明工具的适用场景、功能边界与调用建议，供模型判断是否选用。
3. **输入模式**：使用 JSON Schema 明确定义参数名称、数据类型、必填项与取值约束。
4. **执行逻辑**：严谨的底层代码，负责与真实外部服务通信。
5. **权限边界**：硬性代码逻辑，限制当前用户能够操作的数据范围。
6. **超时与重试**：明确超时阈值，并区分可重试错误（如网络瞬断）与不可重试错误（如参数越权）。
7. **返回结果**：采用统一的结构化数据模型表示成功响应或异常错误。
8. **可观测性**：记录调用耗时、输入参数、执行结果与错误日志，用于追溯和审计。

### 3.2 统一工具结果数据模型

为了让运行时以一致方式处理不同外部工具的返回值，建议建立统一的工具结果数据模型：

* **执行成功状态**：布尔字段 `success`，标识工具执行是否成功。
* **业务数据内容**：字段 `data`，保存成功执行返回的核心业务数据。
* **错误代码**：字段 `error_code`，执行失败时返回标准系统错误码。
* **错误信息**：字段 `error_message`，提供人类和模型可读的故障原因。
* **重试标识**：字段 `retryable`，指示运行时是否可以自动重试。
* **扩展元数据字段**：包含全局请求 ID、执行耗时、数据来源标识、分页信息及安全审计标签。

## 4 权限与安全边界

### 4.1 最小权限原则

外部工具集成的核心安全风险是权限过大：模型可能读取超出任务范围的敏感数据，也可能执行删除、支付或配置修改等副作用操作。必须严格贯彻最小权限原则：

1. **凭据与角色隔离**：只读查询任务仅分配只读数据库账号或受限 API 访问令牌，不得为了开发省事而直接使用高权限管理员凭据。
2. **接口颗粒度收紧**：将宽泛的数据库 SQL 执行接口，收窄为具备特定业务逻辑的受限 API（如仅允许根据订单 ID 查询单个订单）。
3. **敏感信息拦截**：严格禁止向模型输入传递数据库连接密码、第三方密钥或未经鉴权的访问令牌。
4. **人工审批**：对删除数据、转账支付、修改生产配置等高风险副作用操作，建立阻断等待与人工确认节点。
5. **程序强制校验**：权限隔离与访问控制必须由底层业务服务与运行时在代码层强制执行，不能只在提示词中要求模型“自我约束”。

### 4.2 六类外部工具的安全防御

| 工具类型 | 必须重点防御的安全风险 | 生产级核心安全手段 |
| ------ | ------ | ------ |
| **RAG 知识库** | 文档访问越权、跨用户数据泄露、检索内容中的恶意提示词注入 | 数据库硬性租户隔离、检索切片权限过滤、将检索内容声明为不可信数据区 |
| **网络搜索** | 不可信第三方网页内容、虚假诱导信息、恶意外部链接 | 域名白名单过滤、提取纯文本清洗标签、拦截网页中的系统级指令 |
| **数据库系统** | 越权查询、未授权修改、SQL 注入攻击 | 使用参数化查询、分配只读数据库账号、强制租户 ID 绑定 |
| **业务 API** | 伪造用户身份、越权调用、重复调用产生副作用 | 校验 API 访问令牌、引入幂等性锁、对敏感写操作引入人工审批 |
| **文件系统** | 路径越权、目录穿越、敏感配置文件泄漏 | 路径规范化校验、限制可读写基准目录、禁止访问系统关键文件 |
| **MCP 服务** | 不可信 MCP 服务端、暴露能力超出预期、下游越权 | 建立 MCP 服务端来源白名单、严格审查暴露的工具模式、限制下游通信凭据 |

## 5 工具结果的上下文转化与治理

### 5.1 工具结果进入上下文的六步流程

工具返回的原始数据往往包含接口冗余信息、技术元数据或敏感字段。不能直接注入模型上下文，必须经过以下六步治理：

```mermaid
flowchart LR
    A[工具成功返回原始数据] --> B[1. 校验结果与执行状态]
    B --> C[2. 解包并提取必要字段]
    C --> D[3. 脱敏并剔除敏感字段]
    D --> E[4. 清除冗余元数据与重复信息]
    E --> F[5. 补充来源与追溯标签]
    F --> G[6. 按词元预算选入上下文]
```

### 5.2 字段筛选与敏感数据脱敏

以查询客户信息的数据库工具为例，底层接口返回的原始数据可能包含：客户 ID、姓名、历史订单数、内部敏感备注以及支付鉴权令牌。

在将数据转化为上下文时，治理模块应当：

* **精简保留**：仅提取当前决策所需的字段（如客户 ID、订单数）。
* **严格拦截**：物理剔除与当前任务无关的敏感数据（如支付鉴权令牌、密码哈希）。
* **去重与格式化**：抹去接口内部的状态码、网络耗时等开发调试字段，将其整理为高信息密度的结构化文本。

### 5.3 异常数据与边界情况

物理工具在真实环境中运行，不可避免会遇到各类边界异常。工具结果治理层必须具备对以下五种异常场景的优雅容错机制：

1. **物理执行超时**：向模型返回标准的超时提示，指导模型决定是降低参数范围重试，还是切换备用工具。
2. **无匹配数据返回**：返回明确的“未找到相关记录”状态，防止模型将空结果误判为系统故障或凭空幻觉。
3. **部分数据缺失**：保留有效字段并明确标记缺失项，支持模型在部分信息下进行降级推理。
4. **服务完全不可用**：返回明确的工具服务故障信息，引导智能体向用户解释情况或寻找替代方案。
5. **数据格式异常**：捕获解析错误，阻断坏数据进入上下文，保障智能体主循环的稳定运行。
